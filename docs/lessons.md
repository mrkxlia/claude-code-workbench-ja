# lessons — このリポジトリで繰り返さない判断

過去の PR から蒸留した教訓。**`git log` で根拠を引けるものだけ**を載せる（推測では書かない）。
新しいセクション・ツール・自動化を作る前に、この一覧を読んでから決める。

各項目は「1行要約 / なぜ問題だったか / 根拠」の3点。根拠の PR 番号は `git log --oneline` で辿れる。

---

## 1. 作る前に「本体・公式プラグイン・著名 OSS」の3点を確認する

**なぜ問題だったか。** 2026-08 の OSS 差別化レビュー2回（#55・#57）で削除した9セクションは、
**例外なく「Claude Code 本体の機能・公式プラグイン・著名 OSS の重複」**だった。作った時点では
どれも妥当に見えていた。

| 削除したもの | 代替 | 削除した PR |
|---|---|---|
| `plugins/ai-peer` | 本体の Task サブエージェント（薄いラッパーでしかなかった） | #55 |
| `templates/data-science` | 出典 OSS の移植で機能的な新規性が薄い | #55 |
| `templates/global-claude-md-sample` | 上流 OSS ＋一般的な安全ルールの再構成 | #55 |
| `plugins/knowledge-share` | 本体の auto memory ＋ `claude-mem` | #57 |
| `plugins/self-improve` | 公式 `claude-md-management` / `skill-creator` / `hookify` | #57 |
| `templates/plan-mode` | 本体 Plan モード（計画ファイル出力まで標準化された） | #57 |
| `spec-extract` スキル | `cc-rsg` 等の外部ツール | #57 |
| `tools/multi-model-dist`（90ファイル・3,955行） | `rulesync` | #57 |
| `tools/skill-sync` | 同期対象そのものが消えた（下の教訓2） | #57 |

**教訓。** 新しいものを作る前に、(a) Claude Code 本体が既にやらないか、(b) 公式プラグインが
無いか、(c) 広く使われている OSS（spec-kit・rulesync・cc-rsg・claude-mem 等）が無いか、を
順に確認する。重複していたら「作らない」か「その OSS へ委譲して連携部分だけ書く」を選ぶ。

## 2. 重複を自動化する前に、重複そのものを消す

**なぜ問題だったか。** `tools/skill-sync`（マニフェスト駆動のスキル生成器・約492行・CI 2ステップ）は
**10個の重複ファイルを同期し続けるため**に作られた（#50、2026-07-19）。その1か月後、
software-pipeline と task-pipeline の統合（#55）で派生ルールが12件→5件に減り、残りも #57 の
削除で消えたため、skill-sync ごと削除された。**寿命27日**。

**教訓。** 「N個のファイルがずれる」問題に対して、最初に検討するのは同期の自動化ではなく
**N を1にする統合**。統合できないと分かってから自動化する。

## 3. 既定の探索パスに最初から従う（独自レイアウトを作らない）

**なぜ問題だったか。** プラグインの資材を `.claude/skills/`・`.claude/agents/` という独自配置に
していたため、**24個のサブエージェントが `/plugin install` で1つも配信されていなかった**
（software-pipeline 7・task-pipeline 5・codex-bridge 3・ai-peer 2・agent-review-panel 4・
model-setup 3）。#49 で公式標準レイアウト（プラグインルート直下の `skills/`・`agents/`・
`hooks/hooks.json`）へ移すまで、誰も気づいていなかった。移行は115ファイルに及んだ。

**教訓。** 公式が既定の探索パスを決めているものは、最初からそれに従う。「配信されているつもり」は
実際に導入して確認するまで仮説にすぎない。この教訓は現在の規約6として明文化してある。

## 4. 分類（ディレクトリ構造）を中身より先に作りすぎない

**なぜ問題だったか。** #48 でトップレベルを `plugins/` `templates/` `tools/` `docs/` の4分類へ
再編した（224ファイル）。その1か月後、#57 で `templates/` と `tools/` の中身が全部消え、
**4分類のうち2つが空になった**。現在この2つのディレクトリは存在しない。

**教訓。** 分類は中身が2つ以上あってから作る。将来の拡張を見越した空の器は、規約として文書に
残り続ける負債になる（現在の規約1 は「対象セクションが無いため存在しない」と明記して対処している）。

## 5. 改名は参照の総ざらいを伴う。名前は最初に広く考える

**なぜ問題だったか。** `sonnet-setup` → `model-setup` の改名（`4ff4e05`）は、Opus も対象なのに
Sonnet 専用に見えるという理由で行われた。20ファイルの参照更新に加え、**プラグイン3つが
「本文で旧名に触れていた」だけの理由でパッチバージョンを上げる羽目になった**。
同種の改名は `GlobalClaudeMD-sample` → `global-claude-md-sample`（#48）、
`software-pipeline` + `task-pipeline` → `pipeline`（#55）でも起きている。

**教訓。** 名前を決めるときは「対象範囲が将来広がらないか」を先に考える。実装の詳細（モデル名・
特定ツール名）を名前に埋めない。

## 6. 空のフォローアップ PR を作らない

**なぜ問題だったか。** `b85145e`（PR #58「OSS差別化レビュー第2弾フォローアップ」）は
**変更ファイル数 0 の空コミット**で、`git diff 3a5429a b85145e` も空。PR 本文は #57 の説明を
そのまま繰り返している。作業は既に #57 に入っていた。履歴には差分ゼロの節目だけが残った。

**教訓。** PR を分けるのは差分を分けるときだけ。「区切りとして」空の PR を作らない。

## 7. モノレポから分割したものは、その場でコピーを消す

**なぜ問題だったか。** `token-usage-tracker` は 2026-06-15 に専用リポジトリへ分割されたが、
モノレポ側のコピーが**約1か月そのまま残り**、両者が乖離した。#47 でようやく削除された
（33ファイル）。同時に `power-automate-azure-foundry` も削除している（17ファイル）。

**教訓。** 分割したら、同じ PR で元の場所を消してポインタに置き換える。「後で消す」は乖離する。

## 8. 大きな移動は「移動」と「参照更新」を別コミットに分ける

**なぜ問題だったか（これは良かった判断）。** #48 の再編（224ファイル）は、コミット1で
`git mv` だけ、コミット2で参照更新、という分け方をした。その結果、移動によって壊れた
実際のバグ（`export.sh` / `test_convert.py` のパス、2階層走査が必要になった `convert.py`）を
レビューで見つけられた。

**教訓。** 大量移動は2コミットに分ける。混ぜると、移動に埋もれて実質的な変更が見えなくなる。

---

## 使い方

- 新しいセクション・ツールを提案するとき、教訓1・2・4 に当たらないかを確認する
- 名前を決めるとき、教訓5 を確認する
- 削除・統合の判断を下したら、`docs/decisions/` に日付つきで記録する（この一覧は「繰り返さない
  判断」の要約であり、個々の決定の経緯は決定記録が持つ）
