# 2026-09-06 — self-correct に停止ルール2件（リグレッション検出・進捗なし検出）を追加した決定

## 背景

同日の[記事レビュー記録](2026-09-06-self-correct-article-adoption.md)で、先行 OSS
[sdsrss/loop_eng](https://github.com/sdsrss/loop_eng)（MIT・2026-09-06 取得）が停止ルールを
6件持つのに対し、`self-correct` の Phase 3 には**2件が無い**ことが分かり、積み残しとして
記録した。その2件を今回採る。

| loop_eng の停止ルール | self-correct（従来） |
|---|---|
| すべての基準が満たされた | あり（`PASS`） |
| ラウンド数が尽きた | あり（`ESCALATE`） |
| 同一失敗が連続2回 | あり（同じ指摘 ID の2ラウンド連続で `ESCALATE`） |
| **リグレッション** | **無かった** |
| **2ラウンド連続で進捗なし** | **無かった** |
| 能力の限界到達 | 採らない（下記） |

無かった2件は、どちらもこのプラグイン自身が**最大の失敗モード**と名指ししているもの
（「問題のない箇所を書き換えて、前ラウンドで通った基準を壊す」— `SKILL.md` Phase 4・
`loop-builder.md` 作業原則5）に対応する。にもかかわらず検出手段が無く、**壊れたことにも、
直っていないことにも気づかないまま上限まで回る**状態だった。規律を文章で書いておきながら、
違反を機械で検出していなかったことになる。

## 決定1: 判断はスキル、ゲートはフックの「数値2つ」

`loop-stop-check.sh` は jq が無い環境（Windows の Git Bash 等）向けに grep/sed の
フォールバックを持つ。**配列の集合演算をシェルにやらせない**という制約を優先し、次の分担にした。

- **Manager（`self-correct` スキル）** — Judge の `Passed` を前ラウンドと突き合わせ、
  リグレッションと進捗なしを**計算する**
- **状態ファイル** — 結果を `passed_ids` / `regressed_ids`（配列）と
  `regressed_count` / `no_progress_streak`（数値）に落とす
- **フック** — 数値2つだけを読んでゲートを判定する（既存の `json_num` をそのまま使う）

新フィールドは**無いのが正常**（旧版の状態ファイル・ループ初回）なので、未設定・非数値は
0 に倒す。既存の `attempt` / `max_attempts` が壊れていたら素通りする扱いとは意図的に変えている
（無いことを異常と見なすと、旧版の状態ファイルで毎回ゲートが誤発火する）。

## 決定2: リグレッションは即 ESCALATE にせず、まず差し戻す

- リグレッション検出 → `REVERT`（指摘外の箇所に入った変更を差し戻してから、FAIL 指摘だけ
  直し直す）。**同じ基準が2ラウンド連続で転んだら `ESCALATE`**
- 差し戻しも `attempt` を消費する（無限に戻し続けられてはいけない）

即 ESCALATE にしなかったのは、リグレッションの多くが Builder の**1か所の書きすぎ**であり、
自動で1回回収できるため。中リスク用途（記事・調査レポート）で人間の呼び出し回数が増えると、
このプラグインの目的（人間が確認すべき場所だけを残す）と逆行する。

## 決定3: 進捗なしの閾値は2ラウンド連続

既定の上限が3ラウンドなので、3連続にすると上限到達の `ESCALATE` とほぼ同時になり、
ルールとして機能しない。2連続なら、**無駄な3回目を撃つ前**に止まる。

## 採らなかったもの

| 案 | 却下理由 |
|----|---------|
| loop_eng の「能力の限界到達」 | 判定が主観的で、機械可読な条件に落とせない。「できない」の自己申告を停止条件にすると、難しいタスクを避ける方向に働く |
| リグレッション判定をフック側で配列比較する | jq 無し環境で成立しない。ゲートが環境によって効いたり効かなかったりするのが最悪 |
| 差し戻しを `attempt` に数えない | 「戻す → 直す → また壊す」で上限に到達しなくなる |
| Judge に前ラウンドの `Passed` を渡して自分で比較させる | アンカリングを持ち込む（`loop-judge` に前ラウンドの判定結果を渡さないのが設計の要）。比較は Manager の仕事 |
