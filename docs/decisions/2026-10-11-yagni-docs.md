# 2026-10-11 文書の重複を削り「1つの事実は1か所」にする

## 何が起きていたか

プラグインの中身（スキル・エージェント・フックの名前と数、使い方、コピー導入の手順）が、
ルート `README.md`（約50KB）・`CLAUDE.md` のファイル単位のツリー・`docs/README.md` の決定記録の長い要約・
各プラグインの README に**最大4重**に書かれていた。結果、整理時点で次のずれが見つかった。

- ルート README の図が、削除済みの「AGENTS.md 自動生成」をフックの代表例に挙げていた
- ルート README のコピー導入手順が、adoption-review のエージェントを「2種」と書いていた（実際は1種）
- `CLAUDE.md` の規約1が、存在しない `templates/` を「将来追加しうる」分類として持ち続けていた（lessons 教訓4 に反する）
- 利用者向けの文書に「旧〇〇は 2026-10-06 に削除」の経緯が散らばり、今あるものの説明を読みにくくしていた

lessons 教訓2（N個のファイルがずれるなら、まず N を1にする）と同じ構造。

## 決めたこと

1. **ルート README は索引にする** — 1プラグイン1行の一覧・このリポジトリが持たないもの・出典の要約だけ（約50KB → 約9KB）。
   プラグインごとの長い説明・コピー導入のコマンド・仕様駆動開発の比較は削った。
   SDD の比較は唯一の持ち主である `plugins/pipeline/README.md` へ移し、feedback-rules の README にはルート README にしか無かった
   スキル・エージェントのコピー手順を足した。
2. **CLAUDE.md は骨格と規約だけにする** — ファイル単位のツリーをやめ、`plugins/<name>/` の型だけを示す。
   規約1から `templates/` の予約を外し、規約5からプラグイン名の列挙を外した。
3. **規約7「1つの事実は1か所にだけ書く」と規約8「作る前に削る理由を探す（YAGNI）」を足した** — 今後の追加で同じずれを作らないため。
4. **docs/README の決定記録一覧は1行の主題だけにする** — 要約は各記録の冒頭にある。
5. pipeline-setup の SKILL.md から削除の経緯を外した（読み込むたびに文脈を使うため。pipeline 5.2.1）。

## 意図的に変えなかったもの

- プラグイン・スキル・エージェント・フック・CI の**機能**は削っていない（利用実績の判断が要るため）。
- 移行の案内として利用者に必要な経緯（model-setup の旧名からの入れ替え手順など）は残した。
- 決定記録の本文は変えていない（記録は書いたら変えない）。

## 追記（同日）: 候補のうち2件を片づけた

- **`docs/skills-guide/` を削除した** — 外部スキルの推奨リストで、上流の改名・削除に追い続ける必要があった。
  私用PC・会社PCの使い分けは model-setup が持つので、ルート README からはそちらへ案内する。
- **task-pipeline の進み具合の表示を task-band に取り込んだ（task-band 0.2.0）** — `tools/progress`（Python・statusline の設定・
  HTML ダッシュボード）と task-band（帯）が同じ「いまどこまで進んだか」を別々の仕組みで出していた。task-band が mod の `$.fs` で
  `docs/task-pipeline/*/status.md` を読み、フェーズ・承認待ち（🛑）・差し戻し回数を帯の左に出す。判定（成果物が保存済みの関門だけを
  承認待ちにする）は progress.py と同じ。これで Python も statusline の設定も要らず、タスクツール（`CLAUDE_CODE_ENABLE_TODO_TOOLS=1`）が
  無効な現行モデルでもパイプラインの表示は出る。HTML ダッシュボードは持ち込まなかった（帯で足り、ブラウザを開いたままにする使い方の実績が無い）。
  `tools/progress/` の削除は別に確認を取ってから行う。
- 大きいプラグイン README（pipeline・model-setup・cli-bridge）から削除の経緯を外し、移行に必要な手順だけを残した（規約8）。
