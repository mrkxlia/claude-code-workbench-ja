# 2026-09-05 — 自己修正ループを self-correct プラグインとして実装した決定

## 背景

AI に仕事を任せても、最後に人間が全件チェックしているなら、確認する人間がボトルネックになる。
Anthropic が実用的なエージェント設計として紹介している **Evaluator-Optimizer**（生成した成果物を
別の評価プロセスが検査し、そのフィードバックで改善する）を Claude Code だけで組めるようにしたい、
という要望から検討した。

## 教訓1（作る前に本体・公式・OSS を確認する）の適用

`docs/lessons.md` の教訓1に従い、まず「本体が既にやらないか」を確認した。結果、
**本体は必要な部品をすでに持っている**ことが分かった。

| 本体機能 | できること |
|---------|-----------|
| `/goal` | セッションの完了条件を宣言し、ターン終了ごとに別モデルが達成を評価して未達なら続行させる |
| Stop フック | 停止してよいかを毎回評価する（prompt 型・command 型） |
| Task サブエージェント | 別コンテキスト・別ツール権限での委譲 |
| Permissions | 危険操作の制限 |

したがって **`/goal` の再実装は行わない**。これは「作らない」を選ぶべきかどうかの分岐点だった。

## 決定: 本体が構造的にできない3点だけを実装する

本体機能を調べた結果、次の3点は本体では埋まらないことが分かった。プラグインの範囲はここに限定する。

1. **`/goal` の評価器はツールを持たない。** 判定材料は Claude が会話に出した内容だけであり、
   評価器自身がテスト結果を開く・元資料を読む・公式ページを見ることはできない。
   「テストが通ったと報告した」は評価できても、「本当に通ったか」は評価できない。
   → **実ファイル・テスト結果・元資料に基づく検査は `loop-judge` サブエージェントが担う。**
   prompt 型 Stop フックも同じ制約を持つため、代替にならない。

2. **生成と評価の分離を、約束ではなく権限で担保する仕組みが無い。**
   「Judge は編集しないでください」はプロンプト上の約束にすぎず、破れる。
   → **`loop-judge` に Edit / Write を与えない**（frontmatter の `tools`）。
   指摘した箇所を自分で直して合格させることが構造的にできなくなる。
   同じ理由で、判定の根拠（Ground Truth）への書き込みも `guard-ground-truth.sh` が exit 2 で拒否する。
   根拠を成果物に合わせて書き換えられると、ループは動いたまま無意味になる。

3. **停止条件を機械可読な状態として持つ場所が無い。**
   「最大3回」「同じ FAIL が2回続いたら人間へ」は会話の記憶に依存し、圧縮や長いセッションで失われる。
   → **`.claude/self-correct/state.json`** を単一の現在地とし、`loop-stop-check.sh`（Stop フック）が
   それを読んで決定的に判定する。同じ状態への再通知は1回だけに制限し、無限ループを防ぐ。

## 却下した案

| 案 | 却下理由 |
|----|---------|
| `/goal` 相当のループ制御をスキル内に自前実装する | 教訓1の重複。本体の完了判定を再発明することになる |
| prompt 型 Stop フックを同梱する | 本体の Stop フックそのままで、プラグインが足す価値がない。しかもファイルを開けない |
| Judge に Edit を与え、検出と修正を1体でやらせる | 生成と評価が混ざり、このプラグインの存在理由が消える |
| `agent-review-panel` に「修正ループ」モードを足す | 目的が違う。パネルは合否ではなく論点と対立を出すもので、合否ゲートを持たせると両方の役割が濁る（教訓5 の「対象範囲」の考え方） |
| `verify-fresh` を拡張してループ化する | `verify-fresh` は「1回の検証」であることが売り。ループ・停止条件・Ground Truth 設計を足すと別物になり、既存利用者の期待を壊す |

## 既存プラグインとの住み分け

| プラグイン | 出力 | ループ | 修正 |
|-----------|------|--------|------|
| `verify-fresh`（model-setup） | 完了条件との突合結果 | なし（1回） | しない |
| `review-panel`（agent-review-panel） | 論点・対立・裁定 | 討論1往復 | しない |
| `feature-pipeline`（pipeline） | 工程連鎖の成果物 | なし（人間承認で進む） | 工程内で行う |
| **`self-correct`** | 合否判定と合格した成果物 | **あり（既定3回）** | **FAIL 箇所だけ** |

`pipeline` の成果物作成フェーズの内側で `/self-correct` を回し、パイプラインの承認
チェックポイントには合格した成果物だけを載せる、という併用も想定する。

## Judge を検定する（judge-eval）

自己修正ループの最大の弱点は、**Judge が間違えばループ全体が静かに壊れる**ことである。
見逃せば欠陥が「合格」として出荷され、過検出すれば Builder が問題のない箇所を書き換えて
成果物を壊す。にもかかわらず、Judge の精度を測る手順は本体にも既存 OSS にも見当たらなかった。

そこで `judge-eval` スキルと `judge-auditor` エージェントを置き、正解が分かっているサンプル
（合格例・不合格例）に Judge をブラインドでかけ、見逃し・過検出・重大度誤り・根拠欠落を
集計して本番投入の可否を判定する。**これが他のレビュー系プラグインとの最も大きな違い**である。

## 教訓4・5 への配慮

- **教訓4（分類を中身より先に作りすぎない）** — `templates/`・`tools/` は作らず、既存の
  `plugins/` に7つ目として追加した。スキルは3つ、エージェントは3つ、フックは2つに絞り、
  「将来使うかもしれない」ものは入れていない
- **教訓5（名前は最初に広く考える）** — `self-correct` はタスク種別（記事・コード・調査）にも
  モデル名にも依存しない。実装の詳細（`goal-loop`・`builder-judge` 等）を名前に埋めなかった

## 残課題

- `docs/evals/` に `self-correct` と `judge-eval` の期待挙動シナリオを追加していない。
  他スキルと同様、Sonnet 5 / Opus 5 のパリティ実測が必要になった時点で追加する
- フックは bash のみ（`.ps1` を用意していない）。pipeline と違い、Windows ネイティブ環境での
  利用要望が出た時点で検討する。現状は Git Bash / WSL を前提とする（codex-bridge と同じ扱い）
