### 1. html-plan を同梱しない理由

すでにプラグインなので、同梱や mod 化をする作業が無い。使うならそのまま入れればよい。一時は progress-pane が html-plan のページと回答を読む形を作ったが、第3段（下記）でユーザーが単独で動くことを求めたので外した。敵対役（`adoption-challenger`）の
反論のうち根拠が確認できたもの:

- SKILL.md が計画の文章を **ASD-STE100（英語の Simplified Technical English）に固定**し、`pack.mjs` の lint も
  英語だけを検査する。日本語の読み手に「1分で読める」は成り立たない（最も効く1件）
- 公開から1週間で画面構造と執筆規則が2回大きく変わったが、`version` は 1.0.0 のまま（2026-10-08 の clone で確認）
- 計画1件ごとに SKILL.md（約12KB）・blocks.md・例（約15KB）を読み、ランタイム約200KBを埋め込んだ HTML を作る。
  Plan モードのテキストより重い。回答の戻しはクリップボードへのコピーだけ
- 効果（1分で確認できる・誤解が減る）を裏付ける計測や第三者評価は確認できなかった

試すなら、UI がある複数ファイルの変更で Plan モードと並べ、手戻りの数を比べる。

### 2. 進捗ダッシュボードを progress-pane にした経緯（3段階）

前回は「判断待ちを既定で進める」がルール2と矛盾するとして、表示だけの `tools/progress/` を作った
（[2026-10-03 skill-usability](2026-10-03-skill-usability-and-mattpocock.md)）。ただしそれは task-pipeline の
`status.md` しか読まないので、**普通のセッションでは何も出ない**。

**第1段（stuck-watch）。** 敵対役の最も効く反論は「mod が観測できるのは本体がすでに出している情報（タスクリスト・
質問ダイアログ）だけで、出し直しにしかならない」だった。これを受けて、本体に無い信号（ツールの3回連続失敗・
未完了タスクのまま15分完了なし）だけをステータスラインに出す `stuck-watch` を作った。本体のステータスラインに渡る
JSON にタスクの進捗も失敗回数も無いこと（[公式 Docs: status line](https://code.claude.com/docs/en/statusline)、
2026-10-08 取得）、近い既存品の everything-claude-code の agent-introspection-debugging は**指示で動くスキルで
ツール呼び出しを観測しない**こと（[claudepluginhub](https://www.claudepluginhub.com/skills/centaurioun-everything-claude-code/agent-introspection-debugging)、
2026-10-08 取得）を確認した。

**第2段（html-plan と組み合わせたペイン）。** ユーザーから「見づらいのでペインで進捗が見えた方がいい。html-plan と
うまく混ぜて」と指示があり、敵対役の R1（出し直し）を**ユーザーの判断で覆した**。html-plan の計画ページ（主張・決定）と
Respond の回答を読み、件名に `[1.2]` と主張番号を付けたタスクを主張の下にまとめるペインを作った。

**第3段（単独で動くダッシュボード）。** ユーザーから「html-plan と併用するのではなく単独で動いてほしい」「ビジュアルを活かした
わかりやすいダッシュボードにしたい」「エージェントの地図も見たい」と指示があり、html-plan の読み取りを外して作り直した。
mod の描画要素を調べ直したところ、テキストの行だけでなく、枠つきのカード（`Box` の `borderStyle`）・ボタンのタブ・端末の
`Raster`（セル単位の色つきブロック。スパークラインやヒートマップ用）・デスクトップとモバイルの `Svg` が使えた。本体の
`$.agent.list()` が各エージェントの id・種類・説明・状態・親の id を返し、各ツール呼び出しが `agentId`（どのループか）を
持つので、**親子の木（エージェントの地図）**を本体の情報だけで作れることも分かった。

| タブ | 出すもの | 本体との違い |
|---|---|---|
| 1 概要 | タスクの進捗バー・実行中のタスクと経過時間・順調／詰まりのカード・エージェントの集計・直近30分のツール実行グラフ・経過時間／文脈／費用 | 本体のタスクリストは平らな一覧。進捗の割合・経過時間・詰まり・実行のグラフは無い |
| 2 エージェント | 親子の木。状態・経過時間・ツール回数・失敗数・**いま使っているツール** | 本体の agent view はセッションと背景エージェントの一覧で、入れ子の親子とループごとのツールの動きは出さない |
| 3 ログ | よく使ったツール・どのエージェントで起きたかつきの直近の失敗 | 本体に無い |

詰まりは「どれかのループで3回連続失敗」に広げ（並列のエージェントの失敗を混ぜて数えないよう、ループごとに数える）、
15分完了なしは2秒ごとの時計で見るようにした（ツール呼び出しが止まっていても気付く）。

原典の要素の扱い:

| 原典の要素 | progress-pane での扱い |
|---|---|
| opus のサブエージェントが HTML を作り直す | 採らない。フックがツールの入出力と本体の一覧から決定的に数える（トークン0） |
| タスクと状態の一覧 | 採る（進捗バーと経過時間つき） |
| 詰まり | 採る（ループごとの連続失敗・15分完了なし） |
| 自分への質問と既定動作 | `AskUserQuestion` が開いている間「回答待ち」を出す。**既定で進めるのは採らない**（ルール2と矛盾） |
| 最新の成果物 | 採らない。LLM の要約が要り、トークン0の範囲で作れない |

### 3. 敵対的検証と先行事例の調査（第3段のあと）

ユーザーの指示で、progress-pane そのものを `/adoption-review` の枠組み（代替手段・コスト・敵対役）と、コードの敵対的レビューと、
`/deep-research`（4領域を並列調査）にかけた。

**先行事例（2026-10-08 取得）。** 部品ごとにはすべて先例があった。

| 機能 | 先例 | 判定 |
|---|---|---|
| エージェントの地図 | 本体のサブエージェントパネル（入れ子の木・`(+N)`・状態・トークン・経過時間）、mod の Charlie0113-T/claude-agent-flow・davila7 agent-flow・agent-atc、VS Code 拡張の agent map | **新しくない**。残る差分はエージェントごとの失敗数と、終わったエージェントを消さずに残すことだけ |
| タスクの進捗 | 本体の Ctrl+T（最大5件・バー無し）、claude-hud の `(2/5)` | 新規性は低い。しかも**現行モデル（Opus 4.8・Sonnet 5・Fable 5 以降）ではタスクツールが既定で無効**で、`CLAUDE_CODE_ENABLE_TODO_TOOLS=1` が要る（changelog・tools-reference で確認） |
| 1分ごとのツール実行グラフ | Claude Code の外（clorch・disler） | Claude Code 内では新規。価値は小さい |
| ループごとの3回連続失敗 → 人に知らせる | Citadel・sextant も閾値3だが、知らせる相手はモデル。unstuck は点数化して人とモデルの両方に出し、脱出操作まで持つ | ループ単位で数えて人に知らせる点だけ新規 |
| ターン中15分完了なし | 直接の先例なし（既存は「無活動 N 分」） | 新規。ただし長い単一タスクでは誤報しうる |

**コードの敵対的レビュー。** 確定した欠陥11件をすべて直し、再発防止のテストを足した（7件→18件）。主なもの:
並列のツール呼び出しで詰まりのトーストが何度も鳴る、一覧に出ない内部のフォーク（compaction・memory）が「実行中」のまま残り続ける、
ドックした狭いペインで端末全体の幅を使ってはみ出す、前の完了から時間がたってタスクを足した瞬間に詰まり扱い、中断・例外で
回答待ちが残る、バックグラウンドの完了通知や `/loop` を人の介入と数える、人の番で待っている時間を15分に数える、閉じたペインを
開き直す、TodoWrite のたびに経過時間が0に戻る、完了したタスクを進行形で出す、変化が無くても2秒ごとに描き直す。
あわせて、`/clear`・resume で前の表示を捨てる、一覧から消えたエージェントを「完了」でなく「一覧から消えた」と出す、
同期が失敗したら「同期できていません」と出す（API が変わっても黙らない）、を入れた。

**敵対役（adoption-challenger）の指摘のうち根拠が確認できたもの。** 実機で描画を確かめていない（最も効く）、壊れても黙る
（→ 同期の健康状態の表示で一部対処）、先行 OSS の部分集合に近い、VS Code・モバイルでは十分に動かない。
「CLAUDE.md が7プラグインのまま」は誤り（このブランチでは8に更新済み）。「サブエージェント内のツール呼び出しはフックに来ない」は
従来のフックの話で、function hooks の型定義は「a subagent's tools raise their own `tool.call`」と書いている。ただし実機では未確認。

**adoption-review の結論: 試す価値はあるが常用は微妙 → 小さく検証する。** 中心の売りだった「エージェントの地図」は本体と既存の
mod で足り、タスクの進捗は現行モデルでは既定で空になる。残る価値は「ループごとの連続失敗とターン中15分完了なしを人に知らせる」
「何も保存しない1枚のまとめ」で、これだけで marketplace の8プラグイン目として配る根拠には足りない。**実機で長時間タスクを流して
誤報・見逃しを数えるまで、main にはマージしない**（ブランチに置いて検証する）。

### 4. 公開 mod の読み比べと、task-band への縮小（2026-10-10）

ユーザーの指示で、公開されている mod を取得して読み比べた（6リポジトリ・68 mod、ソースを読むだけで実行していない）。

| 公開 mod | 何をするか | progress-pane との比較 |
|---|---|---|
| [Charlie0113-T/claude-agent-flow](https://github.com/Charlie0113-T/claude-agent-flow)（Apache-2.0、2026-10-08 更新） | サブエージェントの木。状態・いまの作業とその経過時間・承認待ちの強調・`[+]` で詳細（モデル・プロンプト・直近のツール・トークン）・一覧に出ない内部のループを畳んで出す・VS Code と `-p` では文字で出す・狭いときは要注意の行だけ | 地図はこちらが上 |
| [sniperunder123/unstuck](https://github.com/sniperunder123/unstuck)（MIT、2026-10-08 更新） | 同じエラーの繰り返し（行番号などを正規化）・同じコマンドの失敗・「直した」直後の同じ失敗・消したコードの書き戻し・エラーの握りつぶし・文脈80%超を点数化し、帯・トースト・ステータスラインで知らせ、Claude にも止まって仮説を立てさせる。元に戻す・やり直し・別エージェントの見立てを1キーで | 詰まりの検知はこちらがはるかに上 |
| davila7/claude-code-templates の agent-flow、tinyorbit-ai の agent-atc、hamzafer の agent-radar・mission-control | エージェントの木・1行の一覧・触ったファイルの地図 | 地図は飽和している |
| hamzafer の context-bar・token-weather・usage-meter・where-am-i | 文脈・費用・「いま何をしていて何が待っているか」を帯で出す | 文脈と費用は足りる |

あわせて分かった作り方の傾向: いつも見る情報はプロンプトの上の1行の帯（`AbovePrompt`）で出し、ペインは開いて詳しく見るときに
使う。トランスクリプトの行そのものに書き足す mod（tool-timing-badge の `ToolUse`）や、`Client`・`Image`・`ui.blit` で絵を描く mod
（ゲーム、flowpane）もあり、見た目の表現は広い。

**タスクの進捗（TaskCreate・TodoWrite）を出す公開 mod は見つからなかった**（mission-control はタスク系ツールをわざと表示から外している）。
そこで、地図・グラフ・ログ・連続失敗の検知・エージェント一覧の同期を削り、**タスクの進捗だけをプロンプトの上の帯で出す task-band** に
縮めた。詰まりは unstuck に無い軸（エラーは出ていないのに、ターン中15分どのタスクも完了しない）だけを帯の色とトーストで残した。
第3段で直した欠陥のうち、残った部分に効くもの（トーストを1度だけ・人の番の時間を数えない・新しい仕事で起点を戻す・中断で数を戻す・
バックグラウンド通知を介入と数えない・`/clear` で捨てる・経過時間の引き継ぎ・完了は件名で出す）はそのまま持ち越した。
