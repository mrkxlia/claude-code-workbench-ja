# 2026-09-06 — 外部技術の採用可否レビューを adoption-review プラグインとして実装した決定

## 背景

「流れてきた技術（OSS・AI ツール・SaaS・開発手法・論文・スライド・X ポスト）を敵対的に
レビューし、**実務で採用する価値があるか**だけを判定する」長文プロンプトを毎回貼っていた。
そのプロンプトの核は次の5点。

1. **結論を最初に書く**／**良い点より先に「採用しない理由」を探す**（評価の順序が逆）
2. 話題性・権威・スター数・フォロワー数・紹介者・肩書きを**採用理由にしない**
3. URL やツール名だけでも**可能な限り Web 検索**し、一次情報で裏を取る
4. **不明な点は推測で埋めず「確認できなかった」と書く**
5. 代替手段（既存 OSS・本体機能・**何もしない**）と、導入/運用/学習/**撤退**コストを必ず見る

このうち 1・2・4 は「良い評価が出やすい方向へ流れる」失敗を構造で止めるもので、
毎回プロンプトを貼り直す運用では守られたり守られなかったりする。スキル化の動機はそこにある。

## 教訓1（作る前に本体・公式・OSS を確認する）の適用

2026-09-06 に調査した。**カタログサイト経由で確認したものは、それ自体が二次情報**である点を
明記しておく（本スキルの「一次情報を優先する」規則を、この記録自身にも適用する）。

| 調べたもの | できること | 本スキルとの差 |
|---|---|---|
| 本体 `/code-review`・Task サブエージェント | 自分のコードのレビュー、単発のセカンドオピニオン | 対象が**自分の成果物**。外部技術の採用可否も、Web 一次情報の収集手順も持たない |
| 本リポジトリ [`agent-review-panel`](../../plugins/agent-review-panel/) の `/review-panel` | 差分・計画・ドキュメントを複数ペルソナで討論 | 同上（対象が自分の成果物）。討論はするが**証拠を外から集めない** |
| [ThoughtWorks Technology Radar](https://www.thoughtworks.com/radar) の Adopt/Trial/Assess/Hold | 組織の技術方針を4リングに分類する枠組み | **枠組みであって手順ではない**。個別対象の証拠検証・反証は人間の議論に委ねられる |
| tech-radar スキル（[claudeskills.info の紹介ページ](https://claudeskills.info/skills/mohitagw15856/pm-claude-skills/tech-radar/) 経由・2026-09-06 取得） | チームの技術レーダー文書（4象限×4リング）を生成 | 入力が**内部コンテキスト**（自チームのスタック・戦略）で Web 検索の記載なし。紹介ページ自身が「単一ツールの査定には向かない」と書いている |
| Tech Stack Evaluator スキル（[claudedirectory.org の紹介ページ](https://www.claudedirectory.org/skills/claude-skills-tech-stack-evaluator) 経由・2026-09-06 取得。配布元 [alirezarezvani/claude-skills](https://github.com/alirezarezvani/claude-skills)・MIT） | 技術比較・5年 TCO・エコシステム健全性スコア・セキュリティ評価・移行見積もり | **Web 検索を行わず**既存メトリクスの静的分析。**敵対的批判（採用しない理由の先制探索）を含まない**。評価軸は近いが、順序と懐疑の型が違う |
| [breckenedge/claude-code-radar](https://github.com/breckenedge/claude-code-radar) | Claude Code エコシステムの成熟度をコミュニティで追う radar | 対象が Claude Code 周辺に限定。個別対象を評価する**手順**ではない |

**結論**: 「技術を採点する」ものは既にある。無いのは **(a) 良い点より先に採用しない理由を
探す順序**、**(b) Web の一次情報を集めてから判定する手順**、**(c) 確認できなかったことを
推測で埋めない規律**の3点。ここだけを実装し、TCO 計算や radar 生成は作らない。

## 決定1: 「敵対の順序」「一次情報」「確認できなかったの明示」の3点だけを実装する

先行事例と重なる部分（評価軸・スコア表・比較表）は珍しくないので、それ自体を売りにしない。
本スキルが機械的に守るのは次の3つ。

- **順序** — Step 3（敵対的批判）を Step「本当に良い点」より先に置き、良い点は最後まで
  残った主張からしか書けないようにした
- **一次情報** — Step 1 で `adoption-researcher` を並列起動し、**外部評価（Hacker News・
  Reddit・実運用事例）の担当を必ず1体立てる**。数値（Star 数・引用数・フォロワー数）は
  「記録するが採用理由にしない」とスキル本文・エージェント定義の両方に明記した
- **空白の明示** — 出力に「確認できなかったこと」節を常設し、スコアも「確認できなかった観点は
  **判定不能**（低い点で埋めない）」とした。情報が無いことを良い材料にも悪い材料にもしない

## 決定2: サブエージェントは2種に絞り、challenger は条件付きで起動する

- **`adoption-researcher`（並列・read-only）** — 1スコープだけを調べ、**事実と出典 URL だけ**を
  返す。評価語を書かせない。メインの文脈を生ページで汚さないための分離でもある
- **`adoption-challenger`（条件起動）** — 結論が**肯定寄り**（採用候補・条件付きで有用）に
  なったときだけ起動し、「採用しない論拠」だけを構築する。呼び出し側の結論は渡さない

**なぜ条件付きか** — 否定寄りの結論にさらに敵対役を当てても新しい論点は出ず、Task 1回分を
捨てるだけになる。危ないのは「良く見えてしまったとき」なので、そこにだけ当てる。
`self-correct` の「作る役と検査する役を分ける」、`review-panel` の「討論に非関与の裁定者」と
同じ発想を、対象が外部技術の場合に置き換えたもの。

## 決定3: `agent-review-panel` に同居させず、独立プラグインにする

| 対象 | 住み分け |
|---|---|
| `agent-review-panel` | 対象は**自分の成果物**（差分・計画・ドキュメント）。パネル用エージェント5種と討論プロトコルが本体 |
| `adoption-review` | 対象は**外部の技術**。パネルは不要で、必要なのは Web 証拠収集と敵対的な判定順序 |

同居させると、採用可否だけが欲しい利用者に不要なパネル5エージェントが配信され、プラグインの
説明も「自分の成果物にも外部技術にも効く」と曖昧になる。インストール粒度を優先した。
なお名前は教訓5（名前は最初に広く考える）に従い、対象を特定ツール・特定モデルに縛らない
`adoption-review`（採用可否）とした。

## 実装しなかったもの（線引き）

- **パネル討論** — `/review-panel` と重複する。多視点が要るなら本スキルの結論をそちらへ渡せばよい
- **レポートのファイル出力** — 会話内で完結させる。記録が要るなら利用者が貼れば済む
- **TCO 計算・スコアの自動集計** — 先行事例（Tech Stack Evaluator）が既にやっており、
  数値の精度は入力の精度を超えない。本スキルはコストを**分類して見積もる**ところまで
- **技術レーダー（Adopt/Trial/Assess/Hold）の生成** — 組織の方針文書であり、本スキルの
  「1件の採用可否」とは粒度が違う
- **対象のインストール・実行・ベンチマークの実測** — 評価のみ。手順の提示までに留める
- **フック** — 常時発火させる対象が無い（プラグイン導入で勝手に動くものは持たない）
