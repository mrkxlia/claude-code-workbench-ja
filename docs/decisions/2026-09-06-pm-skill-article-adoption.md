## 取り込んだ差分（2点）

### 1. 生成物に鮮度情報と再確認手順を持たせた（codebase-setup 0.3.0）

`codebase-map` と `project-catchup` の**成果物ヘッダ**に生成時点のコミットを記録し、
再確認コマンドを**成果物自身に書く**。

**記事の構造をそのまま移せない理由がここにある。** 記事では「辞書を使う＝その Skill を起動する」
ため、差分チェックの指示は必ず読まれる。一方このリポジトリの地図は
`codebase-map` の中核ルール1により **CLAUDE.md からポインタ1行で参照される**＝
**スキル本文が読まれていない状態で開かれるのが正常系**。手順をスキル側にだけ書くと発火経路が無い。
そこで置き場所を成果物側へ移し替えたうえで採った。

併せて、challenger の反論に対応する制約を同時に入れた:

- 差分は `git diff --name-status <SHA>..HEAD -- <パス>` で**パス単位**に取る
  （`git log --oneline` のコミット件名からは、どの記述が古くなったかは決まらない）
- SHA を解決できないとき（shallow clone・ブランチ削除・force-push・`git fetch` 未実施）は
  **鮮度不明**として扱い、「確認済み」とは書かない。`project-catchup` の対象は
  「自分が書いていないコードベース」であり、履歴の事情を自分で制御できない
- 「コミット一覧を見ただけ」と「実ファイルを読み直した」を区別して報告する
- 既存の「更新日」コメントに SHA を**併記**する（鮮度指標を2つ並べない）

`project-catchup` には「出す前の自己検査」に1行（ヘッダの有無）と、連携表に `deep-understand`
（learning-coach）の行を足した。後者は記事が挙げた失敗「調べる作業が減り、全体を線で捉える力が
落ちる」への対応で、[はてなブックマーク](https://b.hatena.ne.jp/entry/s/tech.talentx.co.jp/entry/2026/08/07/100027)
でも同じ懸念が言及されている（2026-09-06 取得）。

### 2. `【要確認】` を「人にしか答えられないこと」に絞った（pipeline 2.3.1）

`design-docs` の「【要確認】の運用」に1行足した — Grep/Glob・マイグレーション・スキーマ定義で
確かめられるもの（クラス名・パス・テーブル名・カラム名・エンドポイント）はその場で確認し、
`ファイル:行` の根拠つきで本文に書く。

記事の該当挙動は「辞書に無いコード値を推測で埋めず、確認用の SQL を人間に実行してほしいと返した」＝
**AI が実行権限を持たない対象**の話であり、確認手順を設計書の欄として持たせる話ではなかった。
`【要確認】` に「確認方法」欄を足す案は不採用とし、代わりに**タグを立てさせない側のルール**として
書いた。理由は、[`clarify`](../../plugins/pipeline/skills/clarify/SKILL.md) が既に
「調べればわかることは聞かない」を持っており、欄を足すと「確認方法つきの【要確認】」が正規の状態になって、
`design-doc-checker` が末尾で報告する「未回収の【要確認】: N件」と
「`【要確認】` が1件でも残っている設計書はドラフト」という判定が水増しで機能しなくなるため。
**書式（`確認先` / `現在の仮定`）は変えていない** — 変えると `templates.md`（6箇所）・
`consistency.md`・`design-doc-checker.md`（3箇所）・README に波及し、checker が検出する
「テンプレ逸脱」を自作することになる。

## 取り込まなかったもの（と理由）

| 記事の要素 | 理由 |
|---|---|
| 要件定義の5フェーズ・「まだ解決策は書かないでください」 | `requirements-writer` の禁止文言・`design-docs` のフェーズ境界・🛑CP1 が上位互換。記事の5フェーズは**執筆プロセス**、`design-docs` の5フェーズは**成果物の種類**で、そもそも別物 |
| 調査フェーズでの既存実装・依存の洗い出し | `researcher` が呼び出し連鎖・依存・既存実装・類似機能・SPEC 整合を必須出力として持つ |
| 「ここは人間が決めてください」の明示 | `【要確認】`・「未解決の質問」・ハードルール6 で実装済み |
| 要件定義書に「放っておくとどうなるか」を足す | 放置時の帰結（発生件数・損失・期限）は**書き手（Claude）が持たない情報**。必須項目にすると「推測で埋める」か「【要確認】を量産する」の二択になり、`design-docs` の「不明点を仮置きして埋めない」と衝突する。加えて1章「背景・目的（なぜ今これをやるのか）」と同義の記述が並ぶ |
| DB 辞書の生成＋SQL 生成スキルの新設 | `plugins/` 配下に SQL・データ抽出の記述は0件＝新規ドメイン。dbt のセマンティックレイヤー・データカタログ製品・MCP の DB サーバという既存手段があり、[教訓1](../lessons.md)（本体・公式・著名 OSS の重複を作らない）に当たる |
| 辞書の夜間自動更新（cron でローカルのコピーを最新化） | 対象リポジトリ側の運用であり、プラグインとして配布できるものが無い。鮮度の考え方だけを上記1で採った |

## challenger の反論と処理（1往復で確定）

| 反論 | 処理 |
|---|---|
| **A-1（高）** 鮮度チェックの指示をスキル本文に書くと、成果物を使う瞬間に読まれない | **採用。設計を変えた** — 指示を成果物ヘッダへ移した |
| **A-2（中）** shallow clone・ブランチ削除・fetch 未実施で SHA が解決できない／偽陰性になる | **採用** — 「鮮度不明」の扱いを明記した |
| **A-3（中）** `git log --oneline` の件名では、どの章が古くなったか決まらない | **採用** — `git diff --name-status` のパス単位に変え、「見ただけ」と「読み直した」を区別させた |
| **A-4（低〜中）** 「更新日」と「生成 SHA」の二重管理になる | **採用** — 既存の更新日コメントに併記する形にした |
| **B-1（高）** 「確認方法」欄は、自分で確かめられることをタグに置く口実になる | **採用。案を反転させた** — 欄の追加をやめ、タグを立てさせない側のルールにした |
| **B-2（中）** 記事の挙動は「自分で確かめられない」側の話。設計書に移す先が無い | **採用**（同上） |

| **C-1/C-2/C-3** 「放っておくとどうなるか」は既存章と重複し、書き手が持たない情報を要求する | **採用 — C は不採用にした** |

  効いたかを測る手段は用意していない。指示を足すコストを自リポジトリが2つの棚卸し機構

  再利用されないなら鮮度の仕組みの前提そのものが弱くなるが、リポジトリ内に利用実績のデータは無い
