# 2026-09-05 設計書サブエージェントは「既存流用＋2点追加」に絞る

## きっかけ

外部記事（2026-08-11）が、設計書のフォーマットがブレる問題への対策として、
**フェーズ別サブエージェント5体**を提案していた:
`requirements-writer` / `basic-designer` / `detailed-designer` / `db-designer` / `diagram-writer`。

これをこのリポジトリにサンプルとして取り込むか検討した。

## 既存資産との照合

| 記事のエージェント | このリポジトリの既存資産 | 判定 |
|---|---|---|
| requirements-writer | `plugins/pipeline/agents/requirements-writer.md`（**同名**。成果物モードで受け入れ基準つき要件を書く） | そのまま流用。複製・改変しない |
| basic-designer | `brief-writer`（設計）＋ `deliverable-builder`（Read/Grep/Glob/Write を持ち成果物を書く） | 役割は既存。**章立ての型だけが無い** |
| detailed-designer | 同上（コード参照は researcher と builder の Grep/Glob で可能） | 同上 |
| db-designer | 同上（マイグレーション逆引きも Grep/Glob の範囲） | 同上 |
| diagram-writer | 同上（Mermaid は標準で書ける。`.drawio` は Skill ツールで drawio スキルに委譲） | 同上 |

一方で、記事が挙げる運用上の「つまずきポイント」（フェーズ間の内容矛盾・用語のブレ・
詳細設計と実装の食い違い）は**既存の穴**だった。`final-reviewer` の検査項目は
「承認済みの要件・ブリーフとの照合」であり、前段設計書との整合・用語ゆれ・実コード乖離は入っていない。

## 決定

新規プラグインは作らず、`plugins/pipeline` に次の2つだけを追加する（pipeline 2.3.0）。

1. **スキル `design-docs`** — 5フェーズ（要件定義/基本設計/詳細設計/DB設計/図表）の章立てを固定する。
   `references/templates.md` にフェーズ別テンプレート、`references/consistency.md` に
   前段引き継ぎ・用語集・コード乖離の検出手順を分冊（1回の実行では条件付きにしか読まないため）
2. **エージェント `design-doc-checker`** — 設計書を前段設計書・用語集・実コードに突き合わせ、
   フェーズ間矛盾／トレーサビリティ／用語ゆれ／コード乖離／未回収の `【要確認】`／テンプレ逸脱を
   深刻度つきで報告する read-only エージェント

あわせて `CLAUDE.task.md`（成果物モードの CLAUDE.md サンプル）に**用語集セクション**を新設した。
用語集は導入先の CLAUDE.md に1か所だけ置き、設計書側に複写しない。
「使わない言い換え」列を持たせることで、`design-doc-checker` が機械的に検査できる形にしている。

## フェーズ別エージェント4体を作らなかった理由

記事の basic / detailed / db / diagram の4体は、このリポジトリの設計に落とすと
**許可ツールも書き込み範囲もモデルも同一**で、違いは本文の章立てだけになる。
つまり `deliverable-builder` の薄いラッパーが4本増える。

- [`lessons.md`](../lessons.md) 教訓1 — 削除した9セクションは例外なく「本体機能・公式プラグイン・
  既存資産の重複」だった。`plugins/ai-peer` は「本体の Task サブエージェントの薄いラッパー」を理由に削除している
- 教訓2 — 「N個のファイルがずれる」問題には、同期の自動化ではなく N を1にする統合を先に検討する。
  章立て4種は**テンプレートの節4つ**に統合でき、エージェント定義4本にする必要がない
- 教訓4 — 分類（新規プラグイン `design-docs`）は中身が2つ以上あってから作る。
  今回の中身はスキル1・エージェント1で、既存の成果物モードにそのまま乗る

記事の主張「フェーズごとに読者と粒度が違うので分けるべき」自体は採用している。
分ける単位を**エージェント**ではなく**テンプレートの節＋1フェーズ1起動のルール**にした、という違いである。

## 見送ったこと

- **`model: haiku` の図表専用エージェント**（記事はコスト最適化のため haiku を推奨）。
  このリポジトリのエージェントは `inherit` / `sonnet` で階層化済みで、図表だけを別モデルにする
  実測根拠がない。必要になったら `deliverable-builder` の `model:` を環境ごとに変える方が安い
- **設計書専用の書き込みエージェント**（`design-doc-builder` のようなもの）。
  `deliverable-builder` と担当範囲・ツールが完全に重なるため作らない

## 覆すときの目印

- `deliverable-builder` に設計書向けの分岐が増えて本文が肥大したら、フェーズ別ビルダーへの分割を再検討する
- `design-doc-checker` の指摘が `final-reviewer` と実際に重複し始めたら、両者の統合を検討する
  （現時点の検査対象は重なっていない）
