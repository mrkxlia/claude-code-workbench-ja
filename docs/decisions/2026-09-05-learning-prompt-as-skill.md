# 2026-09-05 — 学習用プロンプトを learning-coach プラグインとして実装した決定

## 背景

2026-08-11 に共有された **Anthropic メンバーの「仕事の学習用プロンプト」**（日本語訳）を
このリポジトリに取り込みたい、という依頼から検討した。

原型は、Claude を**教師役**に固定し、セッションで起きたことを**ユーザー自身が説明できる状態**に
なるまで段階的に教えさせる都度貼りプロンプトである。要点は次の4つ。

1. **診断が先、講義は後** — まずユーザー自身に現在の理解を述べさせ、その差分を埋める
2. **3層のチェックリストを常時維持** — ①問題（なぜ起きたか・取りえた別解）②解決（なぜその方法か・
   設計判断・エッジケース）③広い文脈（なぜ重要か・何に影響するか）。**①の理解が最も重要**
3. **クイズで実証させる** — オープンエンドと多肢選択を混ぜ、**正解の選択肢の順番を毎回変え**、
   **全問を提出し終えるまで答えを明かさない**
4. **チェックリストの全項目が実証されるまでセッションを終えない**

都度貼りで使うには長く、貼り忘れれば効かない。`plugins/model-setup/README.md` の
「プロンプトは一時的、構造は永続的」に従い、**スキルとして常設化する**ことにした。

## 教訓1（作る前に本体・公式・OSS を確認する）の適用

`docs/lessons.md` の教訓1に従って重複を確認した。

| 確認先 | 結果 |
|---|---|
| Claude Code 本体 | `/goal` がセッションの完了条件を宣言し、ターン終了ごとに別モデルが達成を評価する。**チェックリストの完了判定は持つが、診断・段階指導・出題・合格判定は持たない** |
| 公式プラグイン | 学習・指導を目的としたものは見当たらない（`skill-creator` はスキルを作るためのもの） |
| 著名 OSS | レビュー・SDD・記憶系はあるが、「人間に理解させる」ことを目的にしたものは見当たらない |

したがって **`/goal` は再実装しない**（`self-correct` と同じ線引き）。本スキルは項目の管理と指導を
担当し、「全部済んだか」の宣言を `/goal` に任せる併用ができる形にした。

## 決定1: 既存プラグインに入れず、新規プラグインとして独立させる

既存8プラグインはすべて「**Claude に良い仕事をさせる**」ための道具である。

| プラグイン | 目的 |
|---|---|
| pipeline / self-correct | Claude に成果物を作らせ、検査させる |
| codex-bridge / kiro-bridge / agent-review-panel | Claude の成果物を別の目で検査させる |
| model-setup / feedback-rules | Claude の振る舞いを常設化する・人間の指摘で縛る |
| codebase-setup | **Claude が**リポジトリを読みやすくする足場を作る |

本スキルだけが「**人間の側の理解を作る**」ことを目的にしており、どのプラグインの主題にも
収まらない。規約1（セクションはディレクトリ単位）に従い、`plugins/learning-coach/` として独立させた。

検討したが採らなかった配置:

- **model-setup に追加** — 個人の運用ルールという括りには収まるが、プラグインの主題
  「上位モデルの振る舞いを常設化する」から外れる。将来この主題で増えるスキル
  （例: 学習履歴の管理）の置き場にもならない
- **pipeline に追加** — パイプライン完走後の引き継ぎフェーズとして位置づけられるが、
  パイプラインを使っていない普段の変更では発動対象外に見えてしまう

名前は教訓5（実装の詳細を名前に埋めない・対象範囲が将来広がらないか先に考える）に従い、
特定モデル・特定ツールを含まない `learning-coach` とした。

## 決定2: エージェント・フックを持たせない

- **サブエージェント** — 理解はユーザーとの往復でしか作れない。説明役を別コンテキストに
  切り出すと、直前の回答・診断結果・チェックリストの状態を毎回渡し直すことになり、
  委譲の利点（メイン文脈を汚さない）より欠点（往復の分断）が大きい
- **フック** — 学習セッションは明示的に始めるものであり、自動発火させる対象ではない。
  `self-correct` の Stop フックのような「未完了で止めない」構造は魅力的だが、
  ユーザーが打ち切る自由を奪う（原型も「ユーザーが質問する／レベルを指定する」対話を前提にしている）

結果として、プラグインは README・plugin.json・SKILL.md の3ファイルになった。

## 決定3: 「答えを明かさない」をツールの構造で担保する

原型の「質問をすべて提出するまで答えを明かさない」は、プロンプト上の約束にすると破れる
（1問ずつ出して都度答え合わせをすれば、後の設問のヒントになる）。

`AskUserQuestion` は**1回の呼び出しに最大4問をまとめて出し、全問の回答が返ってから続きを書く**
という構造を持つ。SKILL.md ではこれを規範として明記し、出題を1回の呼び出しにまとめさせている。
`self-correct` が「Judge に Edit / Write を与えない」で分離を権限として担保したのと同じ発想である。

## 住み分け

| 目的 | 担当 |
|---|---|
| 1つの疑問に答える | 通常の応答（1問1答に教師役は過剰。SKILL.md に否定トリガーとして明記） |
| コードの欠陥・改善点を挙げる | `/code-review`・`codex-bridge`・`agent-review-panel` |
| 成果物が完了条件を満たすかの検証 | `verify-fresh`（model-setup）。**理解の検証とは別物** |
| Claude 側の読みやすさの足場 | `codebase-onboard`（codebase-setup） |
| 理解した内容の記録 | `notes`（pipeline）。理解の実証が済んでから |

## 意図的にやらなかったこと

- **`references/` への分冊** — 1回の実行で全節を順に使う（診断→チェックリスト→指導→クイズ→
  完了判定）ため、`skill-authoring.md` の分冊基準（条件付きにしか読まないものだけ切る）に
  該当しない
- **`disable-model-invocation`** — 明示専用にしない。「この変更を理解したい」という自然文で
  発動してほしいスキルであり、誤発動しても被害が無い（説明が始まるだけ）
- **`docs/evals/` へのシナリオ追加** — evals は主要4スキルのパリティ実測用。まず実運用で
  発動精度を見てから判断する
