- 状態: **採用・実装は未着手**（実装は `docs/backlog-2026-09.md` のブリーフ B-1 / B-2 として Sonnet/Opus に委ねる。
  実装されるまで、long-run ルール5 の手動再読と `PROMPTS.md` #10 が運用上の代替）
- 決定者: Fable 5.1（本リポジトリの再現対象モデル自身）。敵対的レビュー3名（下記「レビュー記録」）を経て 2026-09-04 に確定

  `docs/pipeline-spec-alignment-proposal.html` 穴②・残リスク②

## 背景

model-setup は「上位モデルの振る舞いを CLAUDE.md・スキル・サブエージェントで再現する」テンプレートだが、
次の2件は「プロンプトでは完全には埋まらない」と正直に書いたまま残っていた。

1. **長時間作業での序盤制約の保持** — 承認したブリーフ（完了条件・スコープ・制約）が、コンテキストの
   自動圧縮（コンパクション）や長いセッションの後半で薄れる。`/long-run` ルール5（作業メモに固定して
   区切りごとに再読）は「モデルが再読を忘れなければ」効く、というプロンプト依存の対策だった。
2. **SPEC.md の必須ロード保証**（pipeline） — researcher / final-reviewer に「SPEC.md を一次参照せよ」と
   書いてあるが、読む義務はプロンプト指示ベースで、構造的な保証がない（提案資料の穴②。案A 採用時の
   残リスク②として自認していた）。

2026-09-03 に Claude Code 公式 hooks ドキュメントを確認した結果、両方とも**フックで構造的に**解ける
ことが分かった。根拠となる仕様:

| 仕様（公式 hooks ドキュメント） | 使い方 |
|---|---|
| `SessionStart` は `source` が `startup` / `resume` / `clear` / `compact` / `fork` で発火し、`matcher` で `compact` だけに絞れる | コンパクション直後に発火させる |
| `SessionStart` の出力 `hookSpecificOutput.additionalContext` は「会話の先頭・最初のプロンプトの前」に Claude の文脈へ注入される（10,000 字上限。超過分はファイルに退避してパスを渡す） | ブリーフ／SPEC 要約を注入する |
| CLAUDE.md・`.claude/rules/` などの instruction files はコンパクション後に**再ロードされる**（`InstructionsLoaded` の `load_reason: "compact"`） | 恒久ルールは CLAUDE.md に置けば圧縮で消えない |
| `PreCompact` は `trigger`（manual/auto）と `custom_instructions`（`/compact` の引数）を受け取るが、**要約指示を追加・変更する出力は持たない** | 手動 `/compact` の引数で保持指示を渡す以外に圧縮側は制御できない |
| `SubagentStart` の出力 `additionalContext` は「サブエージェントの会話の先頭」に注入され、`matcher` でエージェント種別を絞れる | 特定エージェントに SPEC 要約を必ず渡す |
| `PreToolUse` の入力に `agent_id` / `agent_type` が含まれ、サブエージェントの frontmatter に `hooks:` を宣言できる（そのサブエージェント実行中だけ有効） | （別件 B-3: ビルダーの担当外パスガード） |

## 決定1: 序盤制約の保持は「3層」で構造化する

| 層 | 何を | どう |
|---|---|---|
| 1. 恒久ルール | 行動ルール（ルール1〜15） | CLAUDE.md に置く（既存どおり）。コンパクション後に自動で再ロードされるので対策不要 |
| 2. タスク固有のブリーフ | 完了条件・スコープ・制約・未解決 | `/long-run` 開始時にファイルへ固定（例: `docs/long-run/brief.md`）。**`SessionStart`（`matcher: "compact"`）フック**がそのファイルを `additionalContext` として再注入する。ファイルが無ければ何もしない（無害）。`resume` は対象にしない — 再開時は圧縮直後の注入がトランスクリプトに残っており、二重注入になるため |
| 3. 手動圧縮 | 圧縮時に落としたくない事項 | `/compact` の引数に `PROMPTS.md` #10 の保持指示を渡す（自動圧縮には効かないので層2が主） |

**採用理由**: 層2はモデルの記憶や再読の意思に依存しない。フックは決定論的に発火し、注入はシステム
リマインダーとして届く。コストは圧縮1回につきブリーフ1枚分の入力トークン（キャッシュ対象）だけ。
複数回の圧縮では、前回の注入は要約側に吸収され、新しい注入が1枚乗るので、累積は「要約中の言及＋
最新1枚」に収まる。

**却下した案**:
- 「区切りごとに再読」の指示強化だけ — プロンプト依存のまま。低 effort・長時間で劣化する
- TodoWrite への固定 — コンパクションで消える（ファイルではない）
- `PreCompact` で要約指示を差し込む — 仕様上できない（出力に指示フィールドが無い）
- `UserPromptSubmit` で毎ターン再注入 — 動くが、圧縮が起きていないターンにも毎回注入して
  文脈を汚す。`SessionStart(compact)` は必要なときだけ発火するので優先

**残る限界**:
- 承認後にユーザーが口頭で追加した制約は、ブリーフファイルに追記しない限り再注入されない。
  `/long-run` ルール5 に「制約が増えたらファイルを更新する」を明記して運用で埋める（ルール8 の延長）。
- **model-setup には pipeline-setup 相当の自動配線スキルが無い。** フックは `~/.claude/settings.json`
  への手動マージで配線する。JSON を壊すと全フックが止まるため、B-1 は検証コマンドとバックアップ手順を
  必須にする。git の無い会社 PC では特に注意。
- ユーザースコープに置くと、無関係なプロジェクトの圧縮時にも発火する（ブリーフファイルが無ければ即終了
  するので実害は小さい）。プロジェクト単位に限定したいなら `.claude/settings.json` 側に配線する。
- 実装されるまで（backlog B-1）は、自動圧縮に対する手当てが無い。手動 `/compact` の #10 と区切りごとの
  再読で運用する。
- Windows（bash 無し）では `.ps1` 版が要る。B-1 は `.sh`/`.ps1` の対を要件にする。
- 区切りごとの手動再読（long-run ルール5）はフック導入後も残す。圧縮以外の区切りでの再読は安価で、
  フックが担うのは圧縮直後だけ。

## 決定2: SPEC.md の必須ロードは「セッション先頭注入＋エージェント先頭注入」で保証する

| 層 | 何を | どう |
|---|---|---|
| 1. セッション | SPEC.md の所在・更新日・`[確定]` 要件の ID と見出し一覧（本文全体ではない）＋「これは目次であり本文ではない。判断の前に本文を読むこと」の1行 | **`SessionStart`（`matcher: "startup\|compact"`）フック**が `additionalContext` として注入（`resume` は二重注入になるので対象外）。SPEC.md が無ければ「SPEC.md なし。cc-rsg 等での作成を推奨」を1行注入。pipeline-setup が配線するので、発火するのは pipeline 導入済みリポジトリだけ |
| 2. エージェント | 同じ要約 | **`SubagentStart`（pipeline の全エージェント名を `^name$` でアンカーした matcher）フック**が各エージェントの会話先頭に注入。読む側（researcher / requirements-writer / brief-writer / final-reviewer）だけでなく、書く側（backend/frontend/deliverable-builder・test-verifier）にも入れる — pipeline ハードルール7「既存仕様に黙って反しない」は実装フェーズでも効かせる。プロンプトの「一次参照せよ」は残す（読む動機づけ）が、所在と要件一覧は指示に頼らず届く |
| 3. 既存 | `spec-sync-reminder`（更新漏れの通知） | 変更なし。上記は「読む側」、これは「書く側」の保証 |

**採用理由**: 提案資料の穴②「規約層が任意のポインタ」は、ポインタを「注入」に変えれば消える。本文全体
ではなく要件 ID 一覧を注入するのは、10,000 字上限と文脈汚染を避けるため（全文が要るときはエージェントが
パスを見て読む）。要約が「読んだ気」を生むリスクには、注入文に「目次であり本文ではない」を含めて対処する。
pipeline-setup が既に `.claude/settings.json` へフックを配線する仕組み（重複防止・sh/ps1 振り分け・JSON
検証つき）を持つので、**決定2 に限り**導入経路は増えない（決定1 は手動配線）。

**却下した案**:
- エージェント frontmatter での「読み込み必須化」 — そのようなフィールドは無い（公式）
- `PreToolUse` で「SPEC.md を読むまで Edit を拒否」 — 実現はできるが、read の有無をフック側で
  追跡する状態管理が要り、誤検知で作業を止めるリスクが便益を上回る
- 現状維持（プロンプト指示のみ） — 上位モデルほど短い指示で従うが、本テンプレートの対象は
  Sonnet/Opus であり、長いセッション・低 effort での取りこぼしを構造で防ぐのが本セクションの方針

**残る限界**:
- SPEC.md の内容そのものの品質（`[推定]` が多い等）は保証しない。それは cc-rsg 等の外部ツールと
  Phase 7 の増分更新の責務。
- ID 抽出ロジックを `.sh`/`.ps1` の両方で保守するコストがある。正規表現は `references/` に1か所で
  定義し、片方だけ更新される事故を防ぐ（B-2 の制約）。
- ハイフンを含むエージェント名の matcher は Claude Code 2.1.195 未満では正規表現として部分一致し得る。
  `^name$` でアンカーする。
- PowerShell 5.1 の起動が遅い環境では `startup` ごとの発火がレイテンシに乗る。実測して無視できなければ
  `compact` のみに絞る。
- headless（`claude -p`）での stdout/stderr の扱いは実装時に確認する。
