# 2026-10-08 運用設計ラボ「ミスを許さない手順書」の採否と ops-manual スキル

## 対象

- 「「ミスを許さない手順書」を作ってみた 〜 個人的にはこれ以上できることはあまりなさそう」
  波田野裕一（運用設計ラボ合同会社）、ssmjp online #53。表紙 2026-04-17、Speaker Deck 公開 2026-08-27
  — https://speakerdeck.com/opelab/20260827-ssmjp-operation-procedure-update （2026-10-08 取得）

  — https://speakerdeck.com/opelab/20181106-ssmjp-operation-procedure （2026-10-08 取得）

想定用途（仮置き）: 運用エンジニア・情シス担当が運用手順書・作業マニュアルを書く／直すときの型と検査基準として採り入れ、
Claude Code のスキルで支援する。置き換える対象は「一本道の Word/Wiki 手順書を各自の流儀で書いている現状」。

## 評価の手順

`/adoption-review` の手順で評価した。`/deep-research` workflow はこのセッションで使えなかったため、
メインが WebSearch / WebFetch で集めた（**ソース同士の照合なし**）。結論が肯定寄りだったので
`adoption-challenger` の役割（採用しない論拠だけを作る敵対役）を1回当て、反論を差し戻した。

## 結論

**条件付きで有用 → 特定用途だけ使う。**

- 採るもの: **文書の型**（シナリオ／タスク／I/O の3層、分岐はシナリオ・共通化はタスク、目的を完了条件に・前提を事前条件に、
  タスク共通の構造＝ヘッダ・設定値・前処理/主処理/後処理、設定値の指定と実行の分離）と、**3レベルの検査観点**
- 条件つきで採るもの: **実行時のガード**（全前提の確認が通らないと主処理を実行させない）は、作業が CLI で完結するときだけ
- 採らないもの: 「この構造にすればミスが起きない」という暗黙の主張（効果測定が無い）

## 敵対役の反論と、スキルへの反映

| 反論（重大度） | 反映 |
|---|---|
| 「ミスを許さない」効果を支えるのは著者本人の実践だけ（高） | スキルは効果を主張しない。試走計画（未経験者・本番以外・事前条件の破壊テスト）を必ず添えて返し、効果は導入先で確かめる |
| ミス防止の中心はシェル実装で、文書の型だけでは再現できない（高・**最も効く1件**） | 型を3つに分け、CLI 主体の作業にだけ「完全版＋実行ガード」でシェル関数の骨格（`references/shell-guard.md`）を添える。GUI・Windows の画面操作には付けない。発表に実装は公開されていないので、骨格は再構成であると明記（ターミナルを閉じる代わりに、タスクを新しいプロセスで実行して変数の漏れを防ぐ） |
| 記述量が重く形骸化しやすい（中） | 簡易版（1ファイル）を既定にし、分岐・中断・再利用が要るときだけ完全版へ上げる。タスクの簡易版は繰り返す作業にだけ付ける。「空欄だらけの完全版は簡易版より悪い」を中核ルールに置いた |
| 一般的な runbook テンプレートで大半を代替できる（中） | 一般的な実践は検査項目の「一般」区分に取り込んだ。本スキルの差分は、定常の変更作業を**タスクに部品化して再利用し、タスク間の事前/完了条件の一致で矛盾を見つける**ことに絞る |
| L3（伝承的）に基準がない（低〜中） | L3 の検査項目は「[補完]」と明示し、Critical を付けない |
| 公開実装が無く独自解釈になる（低） | 検査項目に出典区分（[OpsLab]／[一般]／[補完]）を付け、原典との対応を追えるようにした |

## 作ったもの

pipeline プラグインのスキル `ops-manual`（pipeline 5.1.0）。

- `SKILL.md` — 中核ルール7つ・型の選び方・作成とレビューのフロー
- `references/templates.md` — 簡易版／完全版（シナリオ・タスク・I/O）の章立て
- `references/checklist.md` — 3レベル＋一般の検査項目と報告書式
- `references/shell-guard.md` — CLI 作業向けの実行ガードの骨格（4つの終了経路をこのリポジトリで実行して確認済み）

発火の確認: `docs/evals/triggers.md` に ops-manual の4ケース（should 2・not 2）を足し、衝突する `task-pipeline` の
「運用手順書を工程を踏んで作って」と合わせた5ケースを `claude plugin eval`（Sonnet 5.5・各3回）で流し、全件合格
（with 1.00。should は without 0.00 で Δ +1.00）。

新しいプラグインにしなかった理由: 手順書は pipeline の「コード以外の成果物」に入り、`task-pipeline` の連結モード
（ブリーフの構成案に型を転記する）と `design-docs` の `【要確認】` 書式をそのまま使えるため（教訓4）。

- 著者以外の組織での採用事例と、ミス件数などの効果測定

- 「全フラグチェック」「ターミナルを閉じる」の実装の詳細
- GUI・Windows 手順への適用方法（発表に言及なし）
- 1手順あたりの記述量・作成時間が単構造や一般的な runbook と比べてどれだけ増えるか
- 証拠は単独の経路で集めた（`/deep-research` の照合を経ていない）

## 試すなら検証方法

- 対象: 導入先で実際に行う定常作業の手順書2〜3本
- 手順: 同じ作業を「現行の書き方」と「ops-manual の型」で書き、手順書を書いていない人に本番以外で試走してもらう
- 成功条件: 迷った箇所・聞き返した箇所・書かれていない権限や値の件数が現行より減る。事前条件の破壊テストで止まれる
- 失敗条件: 記述量が増えたのに上の件数が減らない、または書き手が型を空欄のまま運用する
- メトリクス: 試走での質問・停止の件数、作成時間、改訂時に直したファイル数
