# 2026-09-06 — 「CLAUDE.md に1行足して FOR[yourname].md を自動生成させる」の採用可否レビュー: 手法は不採用、差分1点を反映

## 対象と想定用途

- **対象**: X ポスト（2026-08-11 付。本文の貼り付けで受領。URL・投稿者名なし）。
  CLAUDE.md に `For every project, write a detailed FOR[yourname].md file that explains the whole
  project in plain language.` の1行を恒久指示として置き、作業のたびにプロジェクト解説
  ドキュメント（技術アーキテクチャ・コードベース構造・**技術選定の理由**・よくあるバグ・
  落とし穴・ベストプラクティス）を自動生成させる、というもの。生成物は類推や逸話を交えて
  記憶に残るように書かれ、`.gitignore` 推奨。応用として `FORjunior.md` / `FORsenior.md` で
  読者別のオンボーディング資料を作る
- **想定用途**: 「Claude Code を使う個人開発者・チームが、既存/新規プロジェクトの
  **なぜそうなっているか**を含む解説ドキュメントを恒久指示で自動生成させ、人間の理解と
  オンボーディングに使う」。このリポジトリの文脈では
  **`plugins/codebase-setup/`・`plugins/learning-coach/` にまだ無い要素があれば取り込む**

`/adoption-review` の手順（Step 0 → Step 7）で評価した。X 本文は取得できなかったため、
一次情報は貼り付け本文で代替し、証拠収集（`adoption-researcher` 相当）は外部評価スコープ1体に
割り当てた（種別「X ポスト1件」の規定どおり）。

## 結論: 面白いが実務採用は弱い（手法は採用しない）。論点1件だけを既存スキルに反映した

**採用しないもの**: CLAUDE.md への恒久指示という**形式**と、設計理由を LLM に**生成させる**という
**中身**。どちらもこのリポジトリの既存の判断と正面から食い違う（下記）。

**取り込んだもの**: 投稿が指している問題設定 — 「一番学びにくいのは判断の理由」 — は妥当で、
`project-catchup` の章立て（9章）にその置き場が**無かった**。出典の規律を付けたうえで
1章を追加した。

## 一次情報で検証した事実（2026-09-06 取得）

出典: [Claude Code Best practices](https://code.claude.com/docs/en/best-practices)

| 事実 | 判断への効き方 |
|---|---|
| 「CLAUDE.md is a special file that Claude reads at the start of every conversation」「loaded every session」 | 1行が毎セッション届くこと自体は事実。投稿の前提は正しい |
| 「Keep it concise. For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it.」 | この1行は**消しても Claude は間違えない**（作業の失敗を防ぐ指示ではなく、副産物を作らせる指示）。公式の採否基準に照らして常駐の正当化が立たない |
| 「Bloated CLAUDE.md files cause Claude to ignore your actual instructions!」「The over-specified CLAUDE.md ... Claude ignores half of it」 | 恒久指示を足すコストは行数ではなく**他の指示の遵守率**で払う |
| ❌Exclude に「Long explanations or tutorials」「File-by-file descriptions of the codebase」 | 投稿は解説を**別ファイル**に出すので直撃はしない（構造上の違い）。ただし公式が CLAUDE.md に置く価値を認めていない種類の内容ではある |
| `/init` の生成物は build/test コマンド・アーキテクチャパターン・コーディング規約が中心 | **本体は設計判断の理由を生成しない** — 投稿の中核は本体機能の重複ではない（教訓1の3点確認: 本体 ✗・公式プラグイン ✗・著名 OSS は下記） |

## 否定側の根拠（「確認できなかった」は根拠にしていない）

投稿固有の第三者報告は**0件**（HN Algolia 0件・技術ブログの実運用報告0件）だが、
`adoption-review` 中核ルール11 に従い、これは減点材料にしていない。減点の根拠は次の3つ。

### 1. 「なぜ」はコードに書かれていない ＝ 生成させると必ず作文になる

このリポジトリは**すでにこの分類を持っている**。
[`project-catchup/references/interview.md`](../../plugins/codebase-setup/skills/project-catchup/references/interview.md)
の「コードには絶対に書いていないこと（聞くしかない項目）」に **判断の理由 — この構成を選んだ理由・
代替案を却下した理由** が入っている。投稿はそれを LLM に書かせる提案であり、方向が逆。

### 2. コードに書いてある事実ですら誤る、という実証がある

同種パターン（LLM によるリポジトリ解説の自動生成）の第三者報告:

- DeepWiki（Cognition・2025-04 ローンチ）で、LibreOffice の保守者がビルドシステムを
  **Buck と誤記載**（実際は Make）と報告。LLVM では TableGen・InstCombine パス等の重要
  コンポーネントが省略され重要度の低い部分が強調された、Compiler Explorer のプロパティ
  ファイル説明の誤り —
  [BigGo, DeepWiki Accuracy Concerns](https://biggo.com/news/202508270142_DeepWiki_Accuracy_Concerns)（2026-09-06 取得）
- 学術評価 CIAO は22名の開発者が自分の関与リポジトリの LLM 生成アーキテクチャ文書を
  レビューし、概ね価値がある・broadly accurate と評価する一方、**図の品質・高レベルの
  文脈モデリング・デプロイメントビューに限界**があると報告。生成は1リポジトリ平均約3分・
  API 費用約1.19ドル — [arXiv:2604.08293](https://arxiv.org/abs/2604.08293)（同）

コードから読める事実の誤りがこの水準で報告されている以上、**コードに書かれていない設計理由**は
検証手段のない作文になる。CIAO で「broadly accurate」と評価できたのは**関与した開発者**であり、
投稿の想定読者（初心者・新人）は誤りを検出できない層である。ここが最も効く反論で、
**読みやすさ（類推・逸話）は誤りの検出をさらに難しくする**方向に働く。

### 3. 形式が、このリポジトリの既存方針と食い違う

[`context-audit`](../../plugins/codebase-setup/skills/context-audit/SKILL.md) の5分類では、
「手順・チェックリスト」は**分類 D（常時ロードが過剰）＝ スキルへ移設**、「CLAUDE.md は強制力を
持たない」と明記している。投稿の1行はまさに手順であり、スキルに置くべきものを常駐指示に置く形。

## 取り込んだ差分（1点）

**`project-catchup` に「9. 設計判断の理由」章を追加した**（`未確認` は10章に繰り下げ）。

- 書けるのは**出典のあるものだけ** — ADR・設計ドキュメント／PR・issue／`なぜ` を書いた commit ／
  コード・設定のコメント／人に聞いた答え（`（日付・誰に確認）`）。**構成や採用技術からの
  推測は書かない**（書けないものは10章へ落として Step 6 で人に聞く）
- 他章と同じく**悪い例／良い例**で具体度の下限を縛った。却下された代替案が最も価値が高いと明記
- 理由が1件も無い場合も**章は残し、探した範囲**（ADR の有無・`git log` を追った期間）を書く
  — 探して無かったのか探していないのかを読者が区別できるようにするため
- 中核ルールに5番目（「なぜ」は出典のあるものだけ）、自己検査に1行、「やらないこと」に1行を追加
- `interview.md` の「判断の理由」節に、答えの行き先（9章）と ADR の所在を聞く項目を追加

投稿の中核（自動生成）ではなく、投稿が指した**問題設定だけ**を、このリポジトリの規律
（根拠のない記述を書かない）に載せ替えた形になる。

## 取り込まなかったもの（と理由）

| 投稿の要素 | 理由 |
|---|---|
| CLAUDE.md への恒久指示（`For every project, ...`） | 公式の採否基準（消して間違えるか）に照らして常駐の正当化が立たず、`context-audit` の分類でも「スキルへ移設」側。遵守率という見えないコストを他の指示から取る |
| 設計理由を LLM に生成させること | このリポジトリが「聞くしかない項目」に分類済み。DeepWiki の誤記実証を踏まえ、出典を必須にする形でのみ採った |
| 類推・逸話で記憶に残す書き方 | 引き継ぎレポートでは、読みやすさが誤りの検出を妨げる方向に働く。**記憶に残す役割は `deep-understand`**（クイズで実証する）が持つ |
| `FORjunior.md` / `FORsenior.md`（読者別） | `deep-understand` の ELI5 / ELI14 / ELII が上位互換。`project-catchup` の Step 0 にも読者確認がある。教訓4（分類を中身より先に増やさない） |
| `.gitignore` 推奨 | `project-catchup` Step 0 に「出力先（コミット/`.gitignore` 済み/チャットのみ）を確認してから書き始める」として実装済み |
| ドキュメント自動生成そのものを新スキル/フックにすること | 教訓1・4。`project-catchup` の明示起動で足り、常時発火させる理由が無い |

## 教訓との照合

- **教訓1（本体・公式プラグイン・著名 OSS の3点確認）** — 本体 `/init` は設計理由を生成せず、
  DeepWiki は Wiki 化ツールで対象が違う。**重複ではない**が、重複でないことは採用理由にならない。
  今回は「自リポジトリの既存実装」で中身の大半が消え、残った1点だけを反映した
- **教訓4（分類を中身より先に増やさない）** — 読者別ファイル（FORjunior / FORsenior）は
  ファイルの数を増やすだけで、粒度の出し分けは既存スキルが持っている
