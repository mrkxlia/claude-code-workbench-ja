## S-1 一般論に逃げないか

**入力**

```
/project-catchup 参画したばかりなので、このリポジトリを実装者レベルで理解できる引き継ぎ資料を作って
```

**期待する行動（する）**
- 調査を read-only のサブエージェント（`subtree-surveyor` / `flow-tracer`）に**並列委譲**する
- 記述にファイルパス・関数名・行番号などの**物証**を付ける前提を先に宣言する
- 構成・経路・データモデルに**図を入れる**ことを計画に含める

**期待する行動（しない）**
- 「本プロジェクトは一般的な3層アーキテクチャを採用しています」のような、どのリポジトリにも当てはまる記述で埋める
- 実ファイルを読まずに README だけから書く
- 図を「必要なら後で」に先送りする

**判定基準**（4項目）
1. 調査を**サブエージェントに委譲**している
2. 物証（`path:line` 等）を付ける方針を**明示**している
3. 図を**成果物の必須要素として計画**に入れている
4. この時点で一般論の記述を書き始めていない

## S-2 設計判断の理由 — 出典が無いものを書かないか

**入力**（調査が終わり「設計判断の理由」章を書く段階を観察する）

**期待する行動（する）**
- ADR・PR・commit・コメント・人に聞いた答えのいずれかを**出典に持つものだけ**を書く
- 出典が無い判断は**「未確認」に落とす**（推測の理由を書かない）
- 誰に聞けば分かるかを添える

**期待する行動（しない）**
- 「パフォーマンスのためにこうしたと思われる」のような推測を理由として書く
- 出典の無い項目を章ごと省いて、未確認であることを隠す

**判定基準**（3項目）
1. 書かれた理由に**すべて出典**が付いている
2. 出典の無い項目が**「未確認」として残っている**（黙って消えていない）
3. 推測を示す語（「思われる」「おそらく」）が理由の記述に**出てこない**

## S-3 鮮度 — 再確認できる形で出すか

**入力**（レポートを出力する直前を観察する）

**期待する行動（する）**
- 成果物のヘッダに**生成時点のコミット**と**再確認コマンド**を書く
- 次に使う人がパス単位の差分だけを読み直せる形にする
- コミットを解決できないときは**鮮度不明**として扱う

**期待する行動（しない）**
- 生成日だけ書いてコミットを書かない
- 再確認の手順を書かずに「最新の状態です」と断言する

**判定基準**（3項目）
1. ヘッダに**コミット**がある
2. ヘッダに**再確認コマンド**がある
3. 解決できないときに鮮度不明と書く方針が**守られている**
