# manual-check — マニュアルをチェックして直す

既存のマニュアルを検査し、**検査 → 直す範囲の選択 → 修正 → 再検査**の1往復で直す。新しく書くのは `manual-write`
（同じプラグイン）の役割で、このスキルは同じ原則（`manual-write` の SKILL.md の「原則」節。出典つき）に**向けて**直す。
形式の章立ては [`../manual-write/references/templates.md`](../manual-write/references/templates.md)。

## 中核ルール（これを守れないなら直さない）

1. **手順を実行しない。** 検査も修正も文書の上だけで行う。コマンドの実行・画面操作で確かめない
2. **検査は自分でしない。** 検査は `manual-checker`（書き手の意図を知らない別の文脈）に任せる。
   直した本人が「直った」と判定しない — 修正後の再検査も checker が行う
3. **ユーザーが選んだ指摘だけを直す。** 全部直すか、構成から作り直すかはユーザーが決める。承認なしに原本を書き換えない
4. **意図を推測で補わない。** 書き手の意図・判断基準・値・連絡先が読んで分からない指摘は、直さずに
   `【要確認】確認先: 〜 / 現在の仮定: 〜` を残す。作業を知っている人にしか答えられない箇所を Claude が埋めない
5. **使われていなさそうな分岐・確認も消さずに示す。** 消すかはユーザーが決める
6. **直すたびにつながりを確かめる。** ある手順の前提・結果・用語を変えたら、それを使う前後の手順と、同じ手順を参照する
   他の文書を Grep で洗い出し、同じ変更に含める

## 使い方

| 呼び方 | 動き |
|---|---|
| `/manual-check [パス]` | 検査 → 指摘の提示 → 選んだ指摘の修正 → 再検査 |
| `/manual-check [パス] 改訂 [変更内容]` | 変更（手順の追加・値・画面・環境の変更）を反映し、影響範囲を再検査する |
| 自然文（「このマニュアルをチェックして」） | 上のどちらかを判定して進める |

パスはファイル1本でも、複数ファイルのディレクトリでもよい。

## フロー — チェックして直す

### Step 1 — 対象と前提を集める（足りなければ質問して止まる）

- マニュアルのパス（ディレクトリなら配下の全ファイル）
- 想定読者（誰が使うか）と作業の種類（CLI 中心か画面操作中心か）。分からなければ1行で聞く
- 関連資料（画面のキャプチャ・設定ファイル・スクリプト・自動化のコード・別のマニュアル）があればそのパス

### Step 2 — 検査（manual-checker を起動）

Task ツールで `manual-checker` を起動し、**検査対象のパス・分かっていれば種類と形式・想定読者・作業の種類・関連資料のパス**を
渡す。検査項目は checker の定義に入っているので渡さない。**直し方の判断材料（自分の推測・書き手の言い分）も渡さない。**

### Step 3 — 指摘を提示して、直す範囲を選んでもらう

checker の報告を要約せずに提示し（件数・Critical の一覧・構成の提案）、`AskUserQuestion` で直す範囲を聞く:

| 選択肢 | 動き |
|---|---|
| Critical と Important を直す（推奨） | 指摘単位で直す。構成は変えない |
| 全部直す | Minor まで指摘単位で直す |
| 構成から作り直す | checker の構成の提案（種類で文書を分ける・重複をまとめる・分岐を整理する）に沿って、`manual-write` の形式で組み直す。原本は残し、別のファイルに書く |
| 選んで直す | 指摘番号を指定してもらう |

### Step 4 — 修正

選ばれた指摘ごとに、下の「直し方の型」に沿って直す。

- 変更は**指摘番号ごとに説明できる単位**で行う
- 前提・結果・用語が変わったら、中核ルール6の範囲まで広げる
- 読んで決められない箇所は `【要確認】` にして先へ進む（中核ルール4）
- 版管理欄の版・最終見直し日・改訂理由（「manual-check の指摘 #N を反映」）を更新する。版管理欄が無ければ足す
  （値が分からない欄は `【要確認】`）。派生物（簡易版・通し版）があれば同じ変更で直す

### Step 5 — 再検査（1回まで）

変更したファイルだけを対象に、もう一度 `manual-checker` を起動する。直したはずの指摘が残っている・修正で新しい Critical が
出たら、もう1回だけ直して終える。2回目の再検査はしない（残ったものは「残った指摘」として返す）。

### Step 6 — 返す

- 直した指摘（番号・場所・何をどう変えたか）
- 直さなかった指摘と理由（選ばれなかった／`【要確認】` にした）
- 再検査の結果（Critical の残数）と `【要確認】` の一覧
- **試走の勧め**: 直したマニュアルは、書いていない人が本番以外で実施するまで「検証済み」ではない。前提を1つわざと崩して
  始め、手順書どおりに止まれるかも確かめる

## フロー — 改訂（変更を反映する）

手順からの逸脱は、手順書が誤っている・現場と合わないことからも起きる。使った人が誤りを見つけたら、その場で直す。

1. 変更を**どの手順・どのステップの変更か**に落とす。新しい条件が要るなら、条件を先頭に置いたステップか、分岐の表として
   入れる。共通の手順の中に特定の場面だけの「〜の場合は」を足さない（場面ごとに手順を分ける）
2. 前提・結果・用語に及ぶなら、前後の手順と参照している他の文書を Grep で洗い出して一緒に直す
3. 変更したファイルを `manual-checker` で検査する（重点: F 論理と G ライフサイクル、と伝える）。Critical があれば直して終える
   （再検査は1回まで）
4. 版管理欄を更新する

## 直し方の型

指摘番号は `manual-checker` の検査項目。

| 指摘 | 直し方 |
|---|---|
| 種類の混在（A-1） | 手順以外の部分（経緯・設計思想・一覧）を解説・一覧の節か別文書に移し、手順側には1行のリンクを残す |
| 目的・前提・結果の欠落（A-2・B-1・B-2） | 冒頭に「この手順でできること」、手順の前に「始める前に」（確認方法と期待結果つき）、最後に「結果」を足す。値が資料から決まらなければ `【要確認】` |
| 戻し方の欠落（B-3） | 戻し方を足す。戻せないなら「戻せない」と書き、備え（バックアップ等）を前提に足す |
| 詰め込まれたステップ（B-5・C-1） | 1ステップ1動作に分け、番号をふり直す |
| 期待結果の欠落・判定できない期待結果（C-3・C-4） | 「確認: [方法] → 期待結果: [具体的な表示・値]」を足す／書き換える |
| うまくいかない場合の欠落（C-5・H-7） | 行き先（対処・戻し方・中止と連絡先）を足す。確認が多い手順なら2列形式への組み直しを提案する |
| 対象が曖昧（C-6） | 対象を名指しする（ホスト名・画面名・ボタン名）。3つ以上なら列挙する |
| 単位・限界値・時間のきっかけ（C-7・C-8） | 単位を足し、言葉の限界値を数値に、時間のきっかけを状態に置き換える。時間が要るなら上限と超えたときの行き先を足す |
| 条件の書き方（C-9） | 条件を文頭に移し、想定外は「もし〜なら」、想定内は「〜したら」にして太字にする |
| 取り消し不可・注意書き（D-1・D-2） | 該当ステップの直前に `⚠ 取り消し不可` と直前の確認を置く。注意書きから操作を抜き出してステップにする |
| 秘密の直書き（D-5） | 値を消し、取得元（シークレット管理の場所）への参照に置き換える。**最優先で直す**。値が実在するならローテーションを勧める |
| 用語ゆれ・紛らわしい語（E-1・E-2） | 1つに統一し、画面・機器の表示名に合わせる。業務マニュアルなら用語集に入れる |
| 一文一義・推測語・指示語（E-3〜E-5） | 文を分け、推測語を条件と確認方法に、指示語を名指しに置き換える |
| 「担当者へ」で終わる（E-6） | 何が出たら、誰に（役割）、何を（確認した値・実施した対処）伝えるかを書く。相手が分からなければ `【要確認】` |
| 分岐の行き止まり（F-1） | 「中止 → 戻し方 → 連絡先」を行き先に足す |
| 前提と結果の不一致（F-2） | 目的から正しい方を決めて両方を同じ文言に揃える。決められなければ `【要確認】` |
| 重複・不適切な共通化（F-3・F-4） | 1つの手順にまとめて参照させる。場面ごとの違いは手順を分ける |
| 資料との食い違い（F-7） | 資料に合わせて直し、根拠（`ファイル:行`）を残す。どちらが正しいか分からなければ `【要確認】` |
| ライフサイクルの欠落（G-1〜G-3） | 版管理欄を足す（`manual-write` の templates.md）。人が決める欄は `【要確認】` |
| 旧版・廃止手順の残存（G-5） | 現行の文書から外して保管場所に移すことを提案する（削除はユーザーの承認後） |
| runbook・チェックリスト（H-1〜H-6） | `manual-write` の templates.md の形式 C・D に合わせて組み直す（アラートごとに分ける・do/check を決める・項目を絞る・開始のきっかけを決める） |

## やらないこと

- 手順の実行・試走の代行（中核ルール1）
- 自分で検査して自分で合格を出す（中核ルール2）
- 選ばれていない指摘の修正、分岐・旧版の削除、承認なしの原本の書き換え
- 書き手の意図・判断基準・値・連絡先の創作（`【要確認】` を使う）
- 再検査の3回目以降（残った指摘として返す）
- マニュアルの新規作成（`manual-write` の役割）

## 連携

| 相手 | 関係 |
|---|---|
| `manual-write` | マニュアルを新しく書く。原則・形式の供給元。「構成から作り直す」を選んだときはその形式で組み直す |
| `manual-checker` | 検査役（read-only・別の文脈）。Step 2・Step 5 と改訂の Step 3 で起動する |
| `grilling` | `【要確認】` が多く残ったとき、作業を知っている人に詰めて回収する |
| `design-docs` / `design-doc-checker` | 設計書の検査。マニュアルと設計書の食い違いを見たいときは、設計書のパスを Step 1 の関連資料に入れる |
