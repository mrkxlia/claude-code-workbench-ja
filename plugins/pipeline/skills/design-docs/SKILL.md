# design-docs — 設計書の章立てを固定して書く

設計書がフェーズごとにブレる原因は、書き手の能力ではなく**型が無いこと**にある。
このスキルは「フェーズを選ぶ → 章立てを固定する → 前段と用語集を引き継ぐ → 整合を検査する」
の4手順を毎回同じ形で回す。

## 5つのフェーズ — 読者と粒度

| フェーズ | 主な読者 | 書く粒度 | 踏み込まないもの |
|---|---|---|---|
| 要件定義 | 発注者・PM | 業務要件・機能要件・非機能要件 | 実現手段（構成・技術選定） |
| 基本設計 | PM・リードエンジニア | システム構成・機能一覧・画面遷移の概要 | クラス名・関数名・SQL |
| 詳細設計 | 実装担当エンジニア | 処理フロー・クラス/メソッド・入出力仕様 | 業務上の是非（要件定義の領分） |
| DB設計 | 実装担当エンジニア | テーブル定義・制約・ER図 | 画面仕様・処理フロー |
| 図表 | 全員 | シーケンス図・フローチャート（Mermaid） | 図に載らない散文の説明 |

**1フェーズ＝1回の起動**。1回で複数フェーズをまとめて書かない（粒度が混ざる原因になる）。

## 使い方は2つ

### A. 単発モード — 設計書を1本だけ書く

`/design-docs [フェーズ] [対象]`（例: `/design-docs 詳細設計 通知バッチ`）。以下の順で進める:

1. **フェーズを確定する。** 引数から判定できなければユーザーに確認する（推測で決めない）。
2. **入力を集める。**
   - 前段の設計書（要件定義 → 基本設計 → 詳細設計 / DB設計 → 図表）の**ファイルパス**
   - 用語集（導入先 CLAUDE.md の「用語集」節。無ければ `references/consistency.md` の手順で作る）
   - 詳細設計・DB設計・図表では**実コード**（Grep/Glob で該当モジュール・マイグレーションを読む）
3. **テンプレートを読む。** [`references/templates.md`](references/templates.md) から
   該当フェーズの章立てだけを読み、章の順序・見出し・表の列をそのまま使う。
4. **書く。** 不明点は仮置きせず `【要確認】` として本文に残す（後述）。
5. **整合を検査する。** Task ツールで `design-doc-checker` を起動する。入力は
   「今回書いた設計書のパス＋前段設計書のパス＋用語集の場所」。
6. **人に返す。** checker のレポートと `【要確認】` の一覧を添えて提示する。
   Critical があるまま「完成」と言わない。

### B. 連結モード — task-pipeline に乗せる

設計書一式（要件定義から図表まで）を作るときは `/task-pipeline` の5工程に乗せ、
本スキルは**型の供給元**として使う:

- **Phase 3（brief-writer）** — ブリーフの「構成案」に、テンプレートの章立てを
  そのまま転記する（章立てをブリーフで確定させ、CP2 で人に承認させる）
- **Phase 4（deliverable-builder）** — ビルダーはブリーフの章立てどおりに書く。
  フェーズが複数あるときは**1フェーズ＝1ファイル**とし、前段ファイルのパスをビルダーへ渡す
- **Phase 5** — `final-reviewer`（要件・ブリーフとの照合）に加えて
  `design-doc-checker`（フェーズ間整合）を起動する。役割が違うので両方要る

## 前段の引き継ぎ（フェーズ間矛盾を防ぐ最重要ルール）

次フェーズを書くときは、**前段設計書のファイルパスを必ず入力に含める**。
「さっき書いた内容」を記憶で引き継がない（コンパクションで消える）。

- 前段と矛盾する内容を書く必要が出たら、**黙って上書きしない**。矛盾点を
  `【要確認】` として明記し、前段を直すかどうかは人に判断させる
- 前段が存在しないフェーズから始めるとき（例: 要件定義書が無いまま詳細設計）は、
  その旨を設計書の冒頭に「前提: 要件定義書なし」と明記する

## 用語集

用語のブレはフェーズをまたぐと必ず露見する。**用語集は導入先リポジトリの CLAUDE.md に置き、
全フェーズがそこを参照する**（詳細は [`references/consistency.md`](references/consistency.md)）。
設計書側に用語集を複写しない（2か所に散ると必ずずれる）。

## 【要確認】の運用

- 決まっていないことを**仮置きしない**。`【要確認】確認先: 〜 / 現在の仮定: 〜` の形で本文に残す
- `【要確認】` が1件でも残っている設計書は「ドラフト」であり、完成ではない。
  提示時に必ず件数と一覧を添える
- 回収したら該当箇所を書き換え、決まった内容を本文に反映する（タグだけ消さない）

## やらないこと

- 1回の起動で複数フェーズをまとめて書く（粒度が混ざる）
- 前段設計書を読まずに書く／記憶だけで引き継ぐ
- 詳細設計・DB設計を実コードやマイグレーションを読まずに想像で書く
- 不明点を仮置きして埋める（`【要確認】` を使う）
- 設計書の内容をコードに反映する（実装は `feature-pipeline` / `build-with-tests` の領分）
- 出力された設計書を人のレビュー無しで「確定」扱いにする

## 連携

| 相手 | 関係 |
|---|---|
| `task-pipeline` | 設計書一式を作るときの入れ物。本スキルは章立てを供給する（連結モード） |
| `clarify` | `【要確認】` が多いときに、writer 起動前に一問ずつ詰める |
| `design-doc-checker` | フェーズ間矛盾・用語ゆれ・コード乖離・テンプレ逸脱の検査（read-only） |
| `final-reviewer` | 要件・ブリーフとの照合。checker とは検査対象が違うので置き換えない |
| `feature-pipeline` | 設計書の内容をコードにするとき。本スキルはコードを書かない |
