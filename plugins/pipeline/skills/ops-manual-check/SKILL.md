# ops-manual-check — 手順書をチェックして直す

既存の手順書を検査し、**指摘 → ユーザーの選択 → 修正 → 再検査**の1往復で直す。手順書を新しく書くのは
`ops-manual`（同じプラグイン）の役割で、このスキルはその型（シナリオ／タスク／I/O、事前条件・完了条件）に
**向けて**直す。型の章立ては [`../ops-manual/references/templates.md`](../ops-manual/references/templates.md)、
方法論の出典と3レベルの考え方は `ops-manual` の SKILL.md 冒頭にある。

## 中核ルール（これを守れないなら直さない）

1. **手順を実行しない。** 検査も修正も文書の上だけで行う。コマンドの実行・環境へのログインで確かめない
2. **検査は自分でしない。** 検査は `ops-manual-checker`（書き手の意図を知らない別の文脈）に任せる。
   直した本人が「直った」と判定しない — 修正後の再検査も checker が行う
3. **ユーザーが選んだ指摘だけを直す。** 指摘を全部直すかどうか、構造ごと書き直すかどうかはユーザーが決める。
   承認なしに原本を書き換えない
4. **意図を推測で補わない。** 書き手の意図・判断基準・値が読んで分からない指摘は、直さずに
   `【要確認】確認先: 〜 / 現在の仮定: 〜` を残す。人にしか答えられない箇所を Claude が埋めない
5. **ノイズは消さずに示す。** 使われていなさそうな分岐・確認も、消すかはユーザーが決める
6. **直すたびに条件のつながりを確かめる。** タスクの事前条件・完了条件・I/O を変えたら、前後のタスクと、
   同じタスクを呼ぶ他のシナリオを Grep で洗い出し、同じ変更に含める

## 使い方

| 呼び方 | 動き |
|---|---|
| `/ops-manual-check [パス]` | 検査 → 指摘の提示 → 選んだ指摘の修正 → 再検査 |
| `/ops-manual-check [パス] 改訂 [変更内容]` | 変更（手順の追加・値の変更・環境の変更）をタスク単位で反映し、影響範囲を再検査する |
| 自然文（「この手順書チェックして」） | 上のどちらかを判定して進める |

パスはファイル1本でも、完全版のディレクトリ（`scenario.md`・`io.md`・`tasks/`）でもよい。

## フロー — チェックして直す

### Step 1 — 対象と前提を集める（足りなければ質問して止まる）

- 手順書のパス（ディレクトリなら配下の全ファイル）
- 想定読者（誰が実施するか）と作業の種類（CLI 中心か GUI 中心か） — 分からなければ1行で聞く。
  レベル3（伝承的）の判定と、実行ガードを勧めるかどうかに効く
- 関連資料（構成ファイル・スクリプト・自動化のコード）があればそのパス

### Step 2 — 検査（ops-manual-checker を起動）

Task ツールで `ops-manual-checker` を起動する。渡すもの:

- 検査対象のパス一覧
- 検査項目: このスキルの [`references/checklist.md`](references/checklist.md) の**絶対パス**
  （スキルの基底ディレクトリ ＋ `references/checklist.md`）
- 想定読者・作業の種類・関連資料のパス

**直し方の判断材料（自分の推測・書き手の言い分）は渡さない。** checker は手順書だけを見る。

### Step 3 — 指摘を提示して、直す範囲を選んでもらう

checker の報告をそのまま要約せずに提示し（件数・Critical の一覧・ノイズの候補・3層の骨格）、
`AskUserQuestion` で直す範囲を聞く:

| 選択肢 | 動き |
|---|---|
| Critical と Important を直す（推奨） | 指摘単位で直す。構造は変えない |
| 全部直す | Minor まで指摘単位で直す |
| 3層に書き直す | checker が示した骨格で、`ops-manual` の完全版の型へ組み直す（原本は残し、別ディレクトリに書く） |
| 選んで直す | 指摘番号を指定してもらう |

### Step 4 — 修正

選ばれた指摘ごとに、下の「直し方の型」に沿って直す。

- 変更は**指摘番号ごとに説明できる単位**で行う（何をどう変えたかを、あとで指摘番号と対応づけて返す）
- 直すうちに事前条件・完了条件・I/O が変わったら、中核ルール6の範囲まで広げる
- 読んで決められない箇所は `【要確認】` にして先へ進む（中核ルール4）
- 冒頭の「最終更新」に日付と理由（「ops-manual-check の指摘 #N を反映」）を書く。
  簡易版・通し版があれば同じ変更で直す

### Step 5 — 再検査（1回まで）

変更したファイルだけを対象に、もう一度 `ops-manual-checker` を起動する。

- 直したはずの指摘が残っている、または修正で新しい Critical が出たら、もう1回だけ直して終える
- 2回目の再検査はしない。残ったものは「残った指摘」として返す（ループさせない）

### Step 6 — 返す

- 直した指摘（番号・場所・何をどう変えたか）
- 直さなかった指摘と理由（ユーザーが選ばなかった／`【要確認】` にした）
- 再検査の結果（Critical の残数）と `【要確認】` の一覧
- ノイズの候補（消すかはユーザーが決める）
- **試走の勧め**: 直した手順書は、書いていない人が本番以外で試走するまで「検証済み」ではない。
  事前条件を1つわざと崩して始め、手順書どおりに止まれるかを確かめる

## フロー — 改訂（変更を反映する）

手順書の事故の多くは修正の積み重ね（その場しのぎの追記）で起きる。変更は次の順で入れる。

1. 変更を**どのタスクの変更か**に落とす。新しい分岐が要るならシナリオの分岐表に足し、タスクの中に
   「〜の場合は」を追記しない。型を持たない単構造の手順書なら、変更箇所の前後だけを対象にする
2. 変更が事前条件・完了条件・I/O に及ぶなら、前後のタスクと同じタスクを呼ぶ他のシナリオを Grep で洗い出して一緒に直す
3. 変更したファイルを `ops-manual-checker` で検査する（checklist のレベル1・2と「改訂」の項目を重点に、と伝える）。
   Critical があれば直して終える（再検査は1回まで）
4. 最終更新の日付と理由を書く

## 直し方の型

| 指摘の種類 | 直し方 |
|---|---|
| タスクの中の分岐（L1-1・R-1） | 分岐ごとにタスクを分け、シナリオの分岐表に条件と行き先を書く |
| 同じ手順の重複（L1-2） | 1タスクにまとめ、元の2か所はシナリオからそのタスクを呼ぶ形にする |
| 事前条件と前のタスクの完了条件の不一致（L1-4・R-2） | どちらが正しいかを手順の目的から決め、両方を同じ文言にそろえる。決められなければ `【要確認】` |
| 行き止まりの分岐（L1-5・L1-6） | 「中止 → 戻し方 → 連絡先」を行き先として足す。連絡先が分からなければ `【要確認】` |
| 設定値の直書き（L1-8） | 設定値表（シナリオまたはタスク冒頭）に集め、本文は `${変数名}` で参照する |
| 完了条件・確認の欠落（L2-1・L2-2・L2-6・G-1） | 確認コマンド（または画面・項目）と期待結果を足す。期待結果が資料から決まらなければ `【要確認】` |
| 判定できない期待結果（L2-3・N-2） | 具体的な出力・表示・数値に書き換える |
| 事前条件・前処理の欠落（L2-4・L2-5） | 権限・ツール・先行作業・対象の状態を事前条件に足し、満たさないときに止まる指示を書く |
| 意図の欠落（L3-1・L3-3） | 資料から読み取れれば「なぜ」を1行足す。読み取れなければ `【要確認】`（創作しない） |
| 取り消し不可の無警告（G-3・G-4） | 直前に `⚠ 取り消し不可` と、直前の確認手順を置く |
| 戻し方の欠落（G-2） | 戻し方を足す。戻せないなら「戻せない」と書き、備え（バックアップ等）を事前条件に足す |
| 推測語（G-7） | 条件と確認方法に書き換える |
| 秘密の直書き（G-10） | 値を消し、取得元（シークレット管理の場所）への参照に置き換える。**最優先で直す** |

## やらないこと

- 手順の実行・試走の代行（中核ルール1）
- 自分で検査して自分で合格を出す（中核ルール2）
- 選ばれていない指摘の修正、ノイズの削除、承認なしの原本の書き換え
- 書き手の意図・判断基準・値の創作（`【要確認】` を使う）
- 再検査の3回目以降（残った指摘として返す）
- 手順書の新規作成（`ops-manual` の役割）

## 連携

| 相手 | 関係 |
|---|---|
| `ops-manual` | 手順書を新しく書く・自動化済み作業の手動版を起こす。書き上げたものはこのスキルの checker で検査される。「3層に書き直す」を選んだときの型の供給元 |
| `ops-manual-checker` | 検査役（read-only・別の文脈）。このスキルの Step 2・Step 5 と改訂の Step 3 で起動する |
| `grilling` | `【要確認】` が多く残ったとき、書き手に詰めて回収する |
| `design-docs` / `design-doc-checker` | 設計書の検査。手順書と設計書の食い違いを見たいときは、設計書のパスを Step 1 の関連資料に入れる |
