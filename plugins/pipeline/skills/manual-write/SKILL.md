# manual-write — 「あるべき」マニュアルを書く

マニュアルが役に立たなくなる原因は、だいたい決まっている。**種類が混ざっている**（手順の途中に経緯や設計思想が
長々と入る）、**読者に合っていない**（書いた人にしか分からない）、**うまくいかなかったときのことが書いていない**、
**古いまま誰も直さない**。手順書の不備・入手できない手順・現場と合わない手順は、手順からの逸脱の主要な原因として
挙げられている（[Flight Safety Foundation, 2018](https://flightsafety.org/asw-article/procedural-drift-causes-and-consequences/)）。

このスキルは、規格・公的ガイド・現場の実践から集めた原則（下の「原則」節。出典つき）に沿ってマニュアルを**書く**。
書いたものの検査は、書き手の意図を知らない別の文脈の `manual-checker` に任せる。**既存のマニュアルのチェック・修正・改訂は
`manual-check`**（同じプラグイン）の役割。根拠の一覧と採否の経緯は
[`docs/decisions/2026-10-10-manual-skills.md`](../../../../docs/decisions/2026-10-10-manual-skills.md)。

## 中核ルール（これを守れないなら書かない）

1. **手順を実行しない。** 書く・検査に回すまでが守備範囲。コマンドの実行・環境へのログイン・画面操作はしない。
   Claude が書いたことを「検証済み」と言わない（検証は人の試走で行う）
2. **1つの文書には1つの種類だけを書く。** 手順（ハウツー）・教育（チュートリアル）・一覧（リファレンス）・解説（なぜ）を
   混ぜない。手順の理由が長くなるなら解説として別の節・別の文書に分ける
3. **読者を決めてから書く。** 既定の読者は「その作業の経験は浅いが基本は分かっている人」で、その人が**監督なしで
   再現できる**詳しさにする
4. **作業を知っている人の言葉を正にする。** マニュアルの中身を決めるのは実際にその作業をする人（主題専門家）。
   Claude は聞き取りと資料から草案を作る。資料で確かめられることは確かめて根拠つきで書き、確かめられないこと・人が決める
   こと（判断基準・値・連絡先）は `【要確認】確認先: 〜 / 現在の仮定: 〜` を残す（仮置きしない）
5. **うまくいかなかったときを書く。** 状態を変えるステップには期待結果を書き、期待結果にならないときの行き先
   （対処・戻し方・中止と連絡先）を書く
6. **作業の重さで形式を選ぶ。** 小さい定型作業に重い型を強いない。空欄だらけの型は、短い手順書より悪い

## 使い方

`/manual-write [作りたいマニュアル]`（例: `/manual-write 経費精算システムの申請手順`、`/manual-write DB フェイルオーバーの runbook`）。

## フロー

### Step 1 — 種類と形式を決める

依頼と資料から、次の2つを決めて**理由を1行添えて**ユーザーに示す（判定できなければ質問して止まる）。

**種類**（原則1）— 1文書1種類。依頼が複数にまたがるなら文書を分ける提案をする。

| 種類 | 問い | 例 |
|---|---|---|
| 手順（ハウツー） | 「〜するにはどうする？」 | SOP・作業手順書・操作手順・runbook |
| 教育（チュートリアル） | 「初めての人が一通り体験するには？」 | 新人向けの通し演習 |
| 一覧（リファレンス） | 「〜の値・意味は？」 | 設定値一覧・エラーコード表・画面項目の説明 |
| 解説 | 「なぜこうなっている？」 | 設計の背景・業務ルールの理由 |

**形式**（手順の場合）— [`references/templates.md`](references/templates.md) から選ぶ。

| 形式 | 選ぶ条件 |
|---|---|
| 基本の手順書 | 大半の作業。前提・手順・結果・戻し方 |
| 2列形式 | 確認と判断が多い作業。各ステップの「期待結果」と「得られない場合」を左右に対にする（原則12） |
| runbook | アラート・障害の対応。きっかけ（アラート名・症状）から引く（原則16・22） |
| チェックリスト | 抜け漏れ防止が主目的。do-list か check-list かを先に決める（原則19） |
| 業務マニュアル | 複数の手順・一覧・解説を束ねる。各章は1種類にし、目次で束ねる |
| 構造化（シナリオ／タスク／I/O） | 分岐・共通手順の再利用・途中での中断が多い作業（[`references/structured.md`](references/structured.md)）。CLI 作業で誤操作の影響が大きければ実行ガードも添える（[`references/shell-guard.md`](references/shell-guard.md)） |

### Step 2 — 聞き取り（足りなければ質問して止まる）

会話・資料から読み取れるものは聞き直さない。

- **目的**（何が終われば完了か — 手順全体の「結果」になる）と**使われる場面**（定常・障害時・年1回など）
- **読者**（経験・権限・作業端末。既定は中核ルール3）
- **対象**（システム・画面・機器・環境。本番か否か）
- **前提**（権限・道具・先に終わっているべき作業・対象の状態）
- **既存の資料**（旧マニュアル・画面・設定ファイル・スクリプト・チケット・作業ログ）のパス
- **改訂の担当者と見直しの周期**（版管理欄に入る。決まっていなければ `【要確認】`）

**作業を知っている人にしか答えられない質問**を必ず混ぜる（答えはステップの期待結果・注意・得られない場合に入る）:

- 「この作業で失敗した・ヒヤリとしたのはどこか。そのとき何が起きたか」
- 「経験者が書かずに見ている・確かめていることは何か」
- 「手順どおりにやらない人がいるなら、どこを、なぜ飛ばすのか」（原則23 — 現場と合っていない箇所の候補）

### Step 3 — 骨格を見せる

見出しとステップの一覧だけ（本文なし）を示して承認を得る。構造化を選んだならタスク一覧と分岐も。

### Step 4 — 執筆

[`references/templates.md`](references/templates.md) の選んだ形式の章立てをそのまま使い、原則の表に従って書く。特に:

- 各ステップ: 1動作・命令形・対象を名指し・数値は単位つき（原則7〜9）。状態を変えるステップには「確認: [方法] → 期待結果: [具体的な出力・表示]」
- 条件は先頭に（原則11）。分岐の行き先はすべて決める（次のステップ・別の手順・中止と連絡先）
- 注意は該当ステップの直前に、操作を含めずに（原則13）。取り消せない操作には `⚠ 取り消し不可` と直前の確認
- 理由が要る箇所は「（なぜ: 〜）」を1行だけ。それ以上は解説として分ける（原則3）
- 用語は文書内・文書間で統一し（原則15・17）、推測語（「たぶん」「通常は」「適宜」「問題なければ」）を使わない
- 冒頭に版管理欄（版・作成者・確認者・承認者・作成日・最終見直し日・次回見直し・改訂理由）を置く（原則21）

### Step 5 — 検査（manual-checker を起動）

書いた本人は検査しない。Task ツールで `manual-checker` を起動し、**書いたファイルのパス・種類と形式・想定読者・
関連資料のパス**を渡す（検査項目は checker の定義に入っている）。Critical があれば直し、直したファイルだけをもう一度
checker に通す（再検査は1回まで）。直し方は `manual-check` の「直し方の型」に揃える。

### Step 6 — 試走の計画を添えて返す

- **机上の確認**: 作業に経験のある、書いた人以外の人が内容を確認する（原則20）
- **試走**: 標準の訓練しか受けていない、書いていない人が、本番以外で手順どおりに実施する。迷った・聞き返した・
  書いていない権限や値が要った箇所を記録する
- **得られない場合の試験**: 前提を1つわざと満たさない状態で始め、手順書の指示どおりに止まれるかを確かめる
- 試走で見つかった誤りは `/manual-check [パス] 改訂 [内容]` で直す

返すもの: パス・種類と形式と理由・checker の結果（件数）・`【要確認】` の一覧・試走の計画。

## やらないこと

- 手順の実行・試走の代行（中核ルール1）
- 1文書への複数種類の混在、手順の途中への長い経緯の挿入
- 人が決めること（判断基準・値・連絡先・承認者）の創作（`【要確認】` を使う）
- 自分で書いたものを自分で検査して合格を出す（checker に任せる）
- 既存のマニュアルのチェック・修正・改訂（`manual-check` の役割）
- 製品の API リファレンスの自動生成（コードから作るものはコード側の道具に任せる）

## 連携

| 相手 | 関係 |
|---|---|
| `manual-check` | 既存のマニュアルのチェック・修正・改訂。同じ原則と同じ検査項目を使う |
| `manual-checker` | 検査役（read-only・別の文脈）。Step 5 で起動する |
| `task-pipeline` | 調査・要件承認・ブリーフ承認・最終レビューの工程を踏んでマニュアルを作るときの入れ物。ブリーフの構成案に本スキルの形式を転記する |
| `design-docs` | 設計書。運用設計書からマニュアルを起こすときは、そのパスを Step 2 の既存資料に入れる |
| `grilling` | `【要確認】` が多いとき、作業を知っている人に詰めて回収する |
