# templates — マニュアルの形式

## 目次

- 版管理欄（全形式共通）
- A 基本の手順書
- B 2列形式（期待結果／得られない場合）
- C runbook（アラート・障害対応）
- D チェックリスト（do-list／check-list）
- E 業務マニュアル（複数の文書を束ねる）
- 書き方の約束（全形式共通）

SKILL.md で選んだ形式の節だけを読む。見出し・表の列はそのまま使う。分岐・共通手順の再利用・中断が多い作業の
構造化（シナリオ／タスク／I/O）は [`structured.md`](structured.md)。原則番号は SKILL.md の「原則」表を指す。

## 版管理欄（全形式共通・冒頭に置く）

原則21（EPA 2.3）。見直しの周期は組織が決める（EPA は例として1〜2年）。

```markdown
| 項目 | 内容 |
|---|---|
| 文書番号・版 | [番号] 第[N]版 |
| 種類 | [手順 / 教育 / 一覧 / 解説] |
| 作成者 | [作業を知っている人] |
| 確認者 | [作業に経験のある、作成者以外の人] |
| 承認者 | [役割] |
| 作成日 / 最終見直し日 / 次回見直し | [日付] / [日付] / [日付] |
| 改訂理由 | [今回の版で何を変えたか] |
| 試走の記録 | [日付・実施者・見つかった問題の件数] |
```

## A 基本の手順書

DITA の task の順序（前提 → 背景 → 手順 → 結果 → 後続作業）に、戻し方を足したもの（原則4）。

````markdown
# [〜する]（例: 経費精算を申請する）

[版管理欄]

## この手順でできること
[結果を1〜2文。読者の目標の言葉で]

## 始める前に（前提）
| # | 条件 | 確認方法 | 期待結果 |
|---|---|---|---|
| 1 | [権限・道具・先行作業・対象の状態] | [方法] | [具体的な出力・表示] |

1つでも期待結果にならなければ始めない。[止まったときの連絡先]

## 背景（任意・3行まで）
[この手順を使う場面。長くなるなら解説の文書へのリンクにする]

## 手順
⚠ [手順全体にかかる注意。操作を含めない]

1. [操作]（なぜ: [1行。省略できるなら書かない]）
   ```
   [コピーしてそのまま使えるコマンド・入力値]
   ```
   確認: [方法] → 期待結果: [具体的な出力・表示]
   期待結果にならない場合: [対処 / 手順 N の戻し方へ / 中止して [連絡先] へ]

2. ⚠ 取り消し不可 — [この操作で何が失われるか]
   直前の確認: [方法] → [期待結果]
   [操作]

3. もし [想定外の条件] なら、[操作]。そうでなければ手順 4 へ。

## 結果（完了の確認）
| # | 確認方法 | 期待結果 |
|---|---|---|
| 1 | [目的が達成されたことを確かめる方法] | [具体的な出力・表示] |

## 戻し方
[どの手順まで進んでいたら何をすれば戻るか。戻せない手順は「戻せない」と書き、備えを前提に入れる]

## 次に行うこと（後続作業）
[この手順のあとに必要な作業・連絡]
````

## B 2列形式（期待結果／得られない場合）

確認と判断が多い作業に使う（原則12・EOI 4.4）。左列が操作と期待結果、右列が期待結果を得られない場合の対処。

```markdown
| # | 操作 / 期待結果 | 期待結果を得られない場合 |
|---|---|---|
| 1 | [操作] を行う。<br>→ [表示・値] になる | [対処]。それでも [表示・値] にならなければ手順 [N] へ |
| 2 | [状態] になったら、[操作] を行う。<br>→ [表示・値] | [対処] |
```

- 右列が空の行は「得られない場合を考えていない」のか「無い」のかを区別する（無いなら「—」）
- 条件の語（もし〜なら・〜したら・かつ・または・〜でない）は太字にする（原則11）

## C runbook（アラート・障害対応）

アラートごとに1項目（原則22・SRE）。きっかけ（アラート名・症状）で引けるように題名をつける（原則16）。

````markdown
# [アラート名 / 症状]（例: DB レプリケーション遅延 > 300 秒）

[版管理欄]

## このアラートの意味
[何が起きているか・放置すると何が起きるか。2〜3文]

## 影響の確認（最初の5分）
1. [確認] → [期待結果 / 異常の判定基準]

## 判断
| 条件 | 進む先 |
|---|---|
| [確認結果 A] | 対処 1 へ |
| [確認結果 B] | 対処 2 へ |
| [判断がつかない / N 分で解消しない] | エスカレーション へ |

## 対処 1: [名前]
[A の手順書と同じ書き方。各ステップに期待結果と得られない場合]

## エスカレーション
[誰に・どの手段で・何を伝えるか（確認した値・実施した対処・時刻）]

## 関連
[関連する runbook・ダッシュボード・過去の障害記録]

## 更新の記録
[呼び出されたときに見つかった誤り・不足と、直した日付（呼び出された人が更新する）]
````

## D チェックリスト（do-list／check-list）

先に種類を決める（原則19・NASA 2.4.5）。

| 種類 | 使い方 | 向いている作業 | 中身 |
|---|---|---|---|
| do-list | 1項目を読み、行い、次へ（read-and-do） | まれな作業・重大な作業・異常時 | **すべての操作**を順に |
| check-list | 記憶で作業したあと、項目で確かめる | 頻繁な定型作業 | 抜けると重大な影響がある**重要項目**と、作業のまとまりを代表する**代表項目**だけ |

```markdown
# [チェックリスト名]（[do-list / check-list]）

開始のきっかけ: [明確な出来事。例: 「リリース承認のメールを受けたら」]
実施者: [役割] / 読み上げ: [ひとり黙読 / 読み上げと応答]

- [ ] [項目] — [確かめる状態・値]
- [ ] [項目] — [確かめる状態・値]

全項目を確かめたら: [次の作業 / 記録先]
```

- check-list に項目を足すときは、それが重要項目か代表項目かを書く（長くなるほど使われなくなる）
- 開始のきっかけを「〜の間に」「適宜」にしない。作業を中断せずに確かめられる区切り（pause point）に置く

## E 業務マニュアル（複数の文書を束ねる）

業務全体を1冊にするときも、**章ごとに種類を1つ**にする（原則1）。

```markdown
# [業務名] マニュアル

[版管理欄]

## 目次
1. 業務の概要（解説）
2. 手順
   2.1 [〜する]（手順・形式 A）
   2.2 [〜する]（手順・形式 A）
3. 困ったとき（runbook・形式 C／症状で引ける）
4. 一覧（リファレンス）
   4.1 用語集
   4.2 [設定値・コード・画面項目] 一覧
5. 背景と理由（解説）

## 索引
[同じ手順を複数の呼び方で引けるように。例: 「申請の取り消し」「差し戻し」「取り下げ」→ 2.3]
```

- 用語集は1か所にだけ置き、各章はそこを参照する（原則17）
- 手順の章に「なぜ」を長く書かない。5章へリンクする（原則3）

## 書き方の約束（全形式共通）

| 約束 | 原則 |
|---|---|
| 1ステップ1動作。短い文。一文一義（「〜して、〜したら、〜する」とつなげない） | 7・18 |
| 命令形・肯定形・能動態（「〜する」「〜を押す」） | 8 |
| 対象を名指しする（「サーバで」ではなく「`web01` で」）。指す先のない「それ」「これ」を使わない | 9 |
| 数値は単位つき。必要以上の精度にしない | 9 |
| きっかけは時刻ではなく状態で（「5分待つ」より「ステータスが `Ready` になったら」。時間が必要なら上限と超えたときの行き先を書く） | 10 |
| 条件は文頭に。想定外は「もし〜なら」、想定内は「〜したら」 | 11 |
| 注意は該当ステップの直前に、操作を含めずに | 13 |
| 推測語（「たぶん」「通常は」「適宜」「問題なければ」「必要に応じて」）を使わない | 6・14 |
| 「問題があれば担当者へ」で終わらせない。何が出たら、誰に、何を伝えるか | 5・14 |
| 秘密の値（パスワード・鍵）を書かない。取得元への参照にする | — |
| 他の手順への参照は最小限に。参照するなら戻る場所も書く | 16 |
