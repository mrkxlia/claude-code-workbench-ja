# judge-eval — Judge の検定（/judge-eval）

自己修正ループでは、`loop-judge` が品質の唯一の物差しになります。**Judge が間違えば、
ループは動いているように見えたまま壊れます** — 見逃せば欠陥が「合格」として出荷され、
過検出すれば Builder が問題のない箇所を書き換えて成果物を壊します。

このスキルは、**正解が分かっているサンプル**に Judge をかけ、その判定を `judge-auditor` に
採点させて、その評価基準と Judge を本番で使ってよいかを決めます。

## いつ走らせるか

- `self-correct` を**重要な判断に初めて使う前**（本番投入前チェックの必須項目）
- **評価基準を変えたとき**（基準が変われば Judge の挙動も変わる）
- **モデルや Ground Truth の構成を変えたとき**
- ループの結果に違和感があるとき（「毎回同じ指摘しか出ない」「いつも一発 PASS する」）

## フロー

### Step 1 — ゴールデンセットを作る

同じタスク種別のサンプルを**合格例5件・不合格例5件**用意する（最低でも各3件）。

- **合格例** — 評価基準をすべて満たす成果物。**過検出**の検出に使う
- **不合格例** — 欠陥を1件だけ仕込んだ成果物。**見逃し**の検出に使う

**欠陥は想像で作らない。** 過去に実際に起きた失敗から取る:

| 欠陥の種類 | 例 | 期待重大度 |
|-----------|-----|-----------|
| 事実の不一致 | 元資料が12,800円なのに本文が9,800円 | Critical |
| 根拠のない断定 | 出典のない市場シェアの数値 | Critical |
| 必須要件の欠落 | required なセクションが無い | Critical |
| 機械的検査の失敗 | テストが1件落ちている・文字数超過 | Critical |
| 構成の破綻 | 結論が本文と矛盾している | Major |
| 表現の粗さ | 用語の揺れ・冗長な言い回し | Minor |

サンプルごとに「パス／期待される判定／仕込んだ欠陥の内容・場所・期待重大度」を控える。
**Judge にはこの答えを渡さない。**

### Step 2 — Judge をブラインドで走らせる

サンプル1件ごとに `loop-judge` を Task で起動する。渡すのは、本番のループで渡すのと
**まったく同じもの**（成果物の場所／評価基準／Ground Truth）だけ。

- 「これは不合格例です」「どこかに欠陥があります」と**言わない**（言えば検定にならない）
- 1件ずつ独立したコンテキストで走らせる（前のサンプルの記憶を持ち込ませない）
- 並列上限3で回してよい

### Step 3 — judge-auditor に採点させる

`judge-auditor` を Task で起動し、ゴールデンセットの期待値・Judge の全判定・評価基準を渡す。
採点の分類（正検出／見逃し／過検出／重大度誤り／根拠欠落／妥当な UNVERIFIED）と合否の
既定しきい値は `judge-auditor` の定義にある。

確認する4点は次のとおり:

1. **本物の FAIL を見つけられたか**（見逃しゼロが最低ライン）
2. **正しいものを無理に FAIL にしていないか**（過検出）
3. **Critical と Minor を区別できたか**（重大度誤り）
4. **根拠を示せたか**（示した path:line が実在するか。auditor が実際に開いて照合する）

### Step 4 — 判定と手当て

| auditor の判定 | 次にすること |
|---------------|-------------|
| `使用可` | そのまま `self-correct` を本番タスクに使ってよい |
| `要修正` | 誤りのパターンに応じて**基準・Ground Truth・Judge 定義のどれか1つ**を直し、Step 2 から再検定する |
| `本番投入不可` | ループを重要な判断に使わない。人間の最終確認を必ず挟む運用に戻す |

**直す順番は 基準 → Ground Truth → Judge 定義。** 見逃しの大半は Judge の性能ではなく
「基準が曖昧」「根拠の指定が曖昧」で起きる。プロンプトを盛る前に、基準と根拠を疑う。

**Judge の判定に合わせてゴールデンセットの期待値を書き換えない。** 検定が自分に都合よく
通るだけになる。期待値を変えるのは、期待値そのものが誤りだと根拠つきで示せたときだけ。

### Step 5 — 記録する

結果を `docs/self-correct/judge-eval/YYYYMMDD-slug.md` に残す。次に基準やモデルを変えたとき、
**前回との差分**が Judge の劣化・改善を教えてくれる。

```
# judge-eval YYYY-MM-DD — <タスク種別>

対象の評価基準: <パス or 本文>
サンプル: 合格例 N件 / 不合格例 N件

## 採点表
| サンプル | 期待 | Judge の判定 | 分類 | 備考 |

## 集計
正検出 x / 見逃し x / 過検出 x / 重大度誤り x / 根拠欠落 x

## 判定
使用可 / 要修正 / 本番投入不可

## 原因の仮説と手当て
（何を直したか。直していないなら、なぜ直さないか）
```

## このスキルがやらないこと

- サンプルの成果物そのものをレビューする（対象は Judge の判定であって成果物ではない）
- Judge の定義ファイルを自動で書き換える（改善案は提示するが、適用はユーザーの承認後）
- ゴールデンセットの期待値を Judge の判定に合わせて調整する
- 検定を1件のサンプルで済ませる（合格例が無いと過検出を検出できない）
