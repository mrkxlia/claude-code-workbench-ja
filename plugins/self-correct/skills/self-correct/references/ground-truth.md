# Ground Truth の設計 — Judge は何を根拠に判定するか

自己修正ループの品質を決めるのは Builder の性能ではなく、**Judge が何を根拠に合否を出すか**である。
根拠のない判定は「AI の感想」であり、それを基準に修正を重ねても、成果物は最初の思い込みから
一歩も出ない。

Ground Truth とは、**成果物の外側にあって、正しさを確かめられる材料**のこと。

- 弱い: 「このコードは問題なさそうです」
- 強い: `pytest 24/24 passed` / `ruff: 0 error` / `tsc: 0 error`（終了コードつき）

- 弱い: 「料金は月額9,800円で合っているはずです」
- 強い: 公式料金ページ（URL・取得日）に 12,800円 とある → 成果物の 9,800円 は `FAIL`

## タスク別の Ground Truth

| タスク | Ground Truth | Judge に渡すもの |
|--------|-------------|-----------------|
| コード修正 | テスト・lint・型チェック・ビルドの**終了コードと出力** | 実行すべきコマンド一式 |
| 記事・原稿 | `references/` の元資料、一次情報の URL、社内の用語・トーン規定 | 元資料のパス、照合すべき項目（数字・日付・固有名詞） |
| 競合調査 | **公式ページ**（料金・機能）、決算・プレスリリース、取得日 | 一次情報の優先順位、取得日を必須にする指示 |
| 仕様・要件との整合 | `SPEC.md`・受け入れ基準・API 契約 | 仕様のパスと該当セクション |
| データ・集計 | 元データ、再計算した集計値、既知の合計との突合 | 元データのパスと検算の手順 |
| 体裁・形式 | スキーマ、文字数、JSON/YAML の構文、必須ファイルの存在 | 実行できる検査コマンド |

**Ground Truth を用意できない基準は、基準として弱い。** Phase 0 で「この基準は何で判定するか」に
答えられなければ、基準の書き方を変える（[`criteria.md`](criteria.md)）か、その基準は
「人間が最後に見る項目」に回す。

## 3層に分けて検査する

全部を1体の Claude に判断させない。層ごとに担当を変えると安定する。

| 層 | 内容 | 担当 |
|----|------|------|
| Layer 1 — 機械的検査 | テスト・lint・型・ビルド・文字数・形式・ファイル存在 | `loop-judge` が `Bash` で**実行**する。判断を挟まない |
| Layer 2 — 意味の検査 | 事実性・論理・要件適合・分かりやすさ・トーン | `loop-judge` が Ground Truth と照合して判定する |
| Layer 3 — 完了判定 | 「本当にもう終わってよいか」 | 本体の `/goal`（会話ベース）＋ Stop フック（状態ファイルベース） |

**機械で測れるものを Claude の感想に任せない。** 文字数を「だいたい2万字くらいです」と
言わせるのではなく、数えさせる。テストの合否を推測させるのではなく、走らせる。

**Layer 3 をツールの使えるフックに任せない。** `type: "agent"` のフックはファイルを読み
コマンドを実行して停止の可否を判断できるが、公式ドキュメントは実験的機能とし、本番の
ワークフローでは command フックを推奨している（[Hooks guide](https://code.claude.com/docs/en/hooks-guide)・
2026-09-06 取得）。したがって**根拠に当たる検査は Layer 1・2（`loop-judge` が実行・照合する）**に置き、
Layer 3 のゲートは状態ファイルを読む command 型（`loop-stop-check.sh`）に留める。

## Judge に持たせるときの注意

1. **根拠の場所まで指定する。** 「元資料を見て」ではなく「`references/pricing.md` の
   料金表と照合して」。曖昧な指定は UNVERIFIED を量産する
2. **一次情報の優先順位を決める。** 公式ページ > 公式ドキュメント > 報道 > ブログ。
   矛盾したときにどちらを採るかを、判定の前に決めておく
3. **取得日を要求する。** 特に競合調査。「いつ時点で正しいか」が抜けた事実は再現できない
4. **確認できないことを FAIL にしない。** 根拠に到達できなかったものは `UNVERIFIED`。
   これを FAIL にすると、Builder が根拠のない修正で辻褄合わせを始める
5. **根拠そのものは変更させない。** 成果物と根拠が食い違ったとき、根拠を成果物に合わせて
   書き換えれば判定は通るが、ループは無意味になる。`state.json` の `protected` に入れ、
   `guard-ground-truth.sh` に機械的に守らせる

## Judge を過信しない

Ground Truth を持たせても、Judge が見逃す・過検出する可能性は残る。**Judge 自身を正解つきの
サンプルで採点する**（`judge-eval` スキル）。ループを本番の判断に使う前に、最低1回は通す。
