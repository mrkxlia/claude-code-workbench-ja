# 人間への引き継ぎ（ESCALATE）と実務テンプレート

## なぜ書式を固定するか

ループが上限に達したとき、「できませんでした」だけを返されると、人間はゼロから調べ直すことに
なる。それでは自己修正ループを回した意味がない。**人間が最初に確認するのは「Claude が最後まで
解消できなかった箇所だけ」**という状態にするのが、引き継ぎ書の目的である。

## 引き継ぎ書式（ESCALATE 時は必ずこの形）

```
## タスク
何を完了しようとしたか（目的・完了条件）

## 現在の成果物
最新版のパス。どこまでは合格しているか

## 試した修正
1回目: 何を直したか → 結果（どの指摘が消え、どれが残ったか）
2回目: 〃
3回目: 〃

## 残課題
Critical: <指摘 ID / 場所 / 何が問題か>
Major:    〃
UNVERIFIED: <確認できなかった項目 / 確認に必要な情報>

## 根拠
参照した元資料の path:line・URL・コマンド出力

## 人間に判断してほしいこと
具体的な論点（「A と B のどちらを採るか」の形まで落とす）
```

**なぜ止まったかの分類も添える。** 同じ FAIL が2回続いた場合、原因はたいてい次のどれかで、
Builder の努力不足ではない。

- **元資料が不足** — 判定に必要な根拠がそもそも存在しない
- **条件が矛盾** — 2つの評価基準が同時には満たせない
- **権限不足** — 必要なファイル・コマンド・外部情報に到達できない
- **基準の解釈違い** — Judge と Builder が同じ基準を別の意味に読んでいる

**停止の引き金も書く。** どの停止ルールで止まったかで、人間が最初に見る場所が変わる。

| 引き金 | 人間が最初に見るところ |
|--------|----------------------|
| 上限到達 | 残っている Critical / Major の中身。基準が多すぎないか |
| **進捗なし**（件数が2ラウンド連続で減らない） | 評価基準どうしの矛盾と、根拠の有無。同じ指示で4回目を回しても結果は変わらない |
| **リグレッション**（直したはずの箇所が壊れ続ける） | 差し戻した変更の中身。基準番号が途中で振り直されていないか（[`criteria.md`](criteria.md)） |
| 重要な UNVERIFIED が残った | 根拠に到達する手段（アクセス権・一次情報の所在） |

## 実務テンプレート1: 記事・原稿

```
/self-correct drafts/article.md を仕上げてください。

Ground Truth: references/ の元資料（一次情報）
変更禁止: references/

評価基準
  1. [Critical] 数字・日付・固有名詞が references/ と一致
  2. [Critical] references/ に無い事実を断定していない（未確認は「未確認」と明記）
  3. [Major] 同じ主張を3回以上繰り返していない
  4. [Major] 各章に具体例が1つ以上ある
  5. [Minor] 専門用語に初出時の説明がある
  6. [Critical] 20,000字以内（Judge が実際に数える）

完了条件: Critical = 0 / Major = 0 / 重要な UNVERIFIED = 0
停止条件: 修正3回で未達なら停止し、残課題を報告
リスク区分: 中（PASS 後に人間の最終確認を挟む）
```

## 実務テンプレート2: 競合調査

調査タスクでは、FAIL が「書き方が悪い」ではなく「**根拠が足りない**」ことが多い。
その場合の修正は書き直しではなく**追加調査**である。

```
/self-correct 競合5社の比較レポートを作ってください。

調査項目: 対象顧客 / 料金 / 主要機能 / 強み / 弱み / 直近の発表

Ground Truth と優先順位: 公式ページ > 公式ドキュメント > 報道 > ブログ
評価基準
  1. [Critical] 事実1件ごとに参照元（URL）と取得日がある
  2. [Critical] 料金は公式ページの値（他ソースとの食い違いは公式を採る）
  3. [Critical] 未確認情報を推測で埋めていない
  4. [Major] 広告表現（「業界No.1」等）と確認済み事実を区別している

修正ルール
  情報不足 → 追加調査（書き直しではない）
  情報が矛盾 → 両方の根拠を残して UNVERIFIED にする（勝手に一方を採らない）
  誤記 → 該当箇所のみ修正

完了条件: Critical = 0 / Major = 0 / 重要な UNVERIFIED = 0（最大3回）
リスク区分: 中
```

## 実務テンプレート3: コード修正

機械的に確認できるので、Judge の所感より**終了コード**を根拠にする。
Level 1（`/goal` だけ）で足りることも多い領域。

```
/goal 次の条件をすべて満たす。
- auth 関連の全テストが PASS（実行結果を会話に出す）
- lint エラー0件・型エラー0件
- auth 以外の既存機能を変更しない
- 新しい依存関係を追加しない
- 最大10ターンで未達なら停止し、残っているエラーを報告する
```

Judge を挟むのは、テストでは測れない基準（設計の妥当性・仕様との整合・後方互換）が
完了条件に含まれるときにする。

```
/self-correct 決済モジュールのリファクタを完了させてください。

Ground Truth: pytest / ruff / mypy の出力、docs/SPEC.md の §決済
変更禁止: docs/SPEC.md, tests/fixtures/

評価基準
  1. [Critical] pytest が全件 PASS（Judge が実行して終了コードを確認）
  2. [Critical] ruff・mypy が0エラー
  3. [Critical] docs/SPEC.md §決済 の記述と実装が一致
  4. [Major] 公開 API のシグネチャを変えていない
  5. [Minor] 重複したヘルパーが残っていない

完了条件: Critical = 0 / Major = 0（最大3回）
リスク区分: 低（ただし本番デプロイは対象外）
```
