# self-correct — 自己修正ループ（/self-correct）

成果物を**作る役**と**検査する役**に分け、FAIL した箇所だけを直して再検査し、合格条件を
満たすか停止条件に当たるまで回すスキルです。あなた（メインの Claude）が **Manager**
（次の一手を決める役）を務めます。

**なぜ分けるのか。** 最初に間違えた人格が、同じ文脈・同じ前提・同じ評価基準で見直しても、
同じ盲点をもう一度見逃します。「見直しました、問題ありません」は、正しいことの証明では
ありません。だからこのスキルは、生成（`loop-builder`）と評価（`loop-judge`）を別コンテキスト
・別ツール権限に分離し、評価には**成果物の外にある根拠**（元資料・テスト結果・公式ページ）を
持たせます。

## 使い方

- `/self-correct drafts/article.md を references/ と突き合わせて仕上げて`
- `/self-correct 競合5社の比較レポートを作って（料金は公式ページ優先）`
- `/self-correct auth のテストが全部通る状態にして`
- 「自己修正ループで回して」「合格するまで直して」等の自然文でも発動します

## 住み分け（重要）

| 状況 | 使うもの |
|------|----------|
| 完了したか**1回だけ**確かめたい | `verify-fresh`（model-setup）。ループも修正もしない |
| 複数の視点で**批評・討論**させたい | `review-panel`（agent-review-panel）。合否ではなく論点を出す |
| 機能を**工程連鎖**で実装したい | `feature-pipeline` / `task-pipeline`（pipeline） |
| このセッションの**完了条件**を宣言したい | 本体の `/goal`（下記のとおり併用する） |
| **作る→検査→直す→再検査**を自動で回したい | **このスキル** |

**本体 `/goal` との関係（再実装しない）。** `/goal` の評価器は**ツールを持たず**、判定材料は
Claude が会話に出した内容だけです。「テストが通った」という**報告**は評価できても、評価器
自身がテストを開くことはできません。したがって:

- **`/goal` はループの外側の完了判定**として使う（会話上で「本当に終わったか」を別モデルが再確認）
- **実ファイル・テスト結果・元資料に基づく検査は `loop-judge`** が行う
- **決定的な停止ゲートは Stop フック**（`loop-stop-check.sh`）が状態ファイルを読んで機械判定する

3つは代替ではなく層です。`/goal` を Judge の代わりにしないでください。

## 段階（いきなり全部やらない）

1. **Level 1** — `/goal` に検証可能な完了条件を書くだけ。まずここで価値を確かめる
2. **Level 1.5** — `loop-judge` だけを立て、**自動修正はまだ回さない**。作る → Judge → **人間が
   指摘の当否を見る**、を数回やって Judge の精度を確かめる。ここを飛ばすと、精度の分からない
   Judge に修正の指揮を渡すことになる（正解つきで採点するなら `/judge-eval`）
3. **Level 2** — `loop-builder` + `loop-judge` + Manager 判断（このスキルの本体）
4. **Level 3** — `self-correct-setup` で CLAUDE.md・フック・状態ファイルを常設化する

## フロー

### Phase 0 — Define（Task 起動なし・ここを飛ばさない）

次の6点を確定し、ユーザーに提示して**着手の承認を得る**。曖昧なまま回すと、Judge が何を
基準に落としているのか誰にも分からないループになる。

1. **目的** — 何のための成果物か（1文）
2. **成果物と出力先** — パス
3. **完了条件と評価基準** — 基準ごとに独立して判定できる形。書き方は
   [`references/criteria.md`](references/criteria.md)
4. **Ground Truth** — Judge が何を根拠に判定するか。設計方法は
   [`references/ground-truth.md`](references/ground-truth.md)。**根拠が無い基準は
   「Judge の感想」にしかならない**ので、ここで見つけたら基準を作り直す
5. **変更禁止範囲** — 元資料など、触ってはいけないパス（フックで機械的に保護される）
6. **最大修正回数とリスク区分** — 既定3回。リスク区分は下表

| リスク | 例 | 完了のさせ方 |
|--------|-----|-------------|
| 低 | 誤字・体裁・ファイル形式・テストを通す修正 | ループ完了で自動終了してよい |
| 中 | 記事・調査レポート・提案資料 | ループ完了後、**人間の最終確認**を必ず挟む |
| 高 | 契約・返金・送金・本番データ削除・対外連絡 | 実行前に**人間の承認**。ループは草案作成までで止める |

確定したら状態ファイルを作る（下記「状態ファイル」）。

### Phase 1 — Build

`loop-builder` を Task で起動する。渡すもの: 目的／入力と Ground Truth の場所／完了条件と
評価基準／変更禁止範囲／**（2回目以降のみ）直前ラウンドの FAIL 指摘だけ**。

- **初回は Judge を使わない。** まず第一稿を作らせる
- **2回目以降は、渡すのは最新の FAIL 指摘だけ。** 過去ラウンドの指摘履歴・討論の経緯は
  渡さない（古い指摘に引きずられて、直った箇所を戻す事故が起きる）

### Phase 2 — Judge

`loop-judge` を Task で起動する。渡すもの: 成果物の場所／評価基準／Ground Truth／
（2回目以降のみ）前ラウンドで FAIL だった基準の ID。

- **Builder の自己評価・作業経緯は渡さない。** アンカリングの不在が Judge の価値
- **「必ず N 件見つけて」と指示しない。** 件数ノルマは、問題が無いときに問題を捏造させる。
  指示するのは「基準ごとに独立に判定し、確認できないものは UNVERIFIED にする」こと
- Judge が返した指摘は**全件受け取る**（Minor も落とさない）

### Phase 3 — Decide（Manager の判断・Task 起動なし）

判定を、次の**閉じた規則**に当てはめる。ここを曖昧にするとループが終わらない。

| 条件 | 次の一手 |
|------|---------|
| Critical が1件以上 | `RETRY`（Phase 4 へ） |
| Major が1件以上 | `RETRY` |
| 重要な基準が UNVERIFIED | `VERIFY` — 追加調査・追加検証で根拠を取りに行く。取れなければ `ESCALATE` |
| 同じ指摘 ID の Critical / Major が**2ラウンド連続**で残った | `ESCALATE`（修正が効いていない） |
| 修正回数が上限に達した | `ESCALATE` |
| Critical = 0 かつ Major = 0 かつ 重要な UNVERIFIED = 0 | `PASS`（Minor は報告に載せて判断を委ねる） |

**UNVERIFIED は「まだ判定できていない」であって PASS ではない。** 情報不足なら、文章を
書き直すのではなく**根拠を取りに戻る**（追加調査も自己修正のうち）。

### Phase 4 — Retry

`RETRY` なら Phase 1 に戻る。守ること:

- **FAIL した箇所だけを直す。PASS した箇所は触らない。** 全文再生成は、Judge が構成そのものを
  Critical と判定した場合に限る。1か所の指摘で全体を作り直すと、前ラウンドで通った基準が壊れる
- 修正後は**必ず再検査**する（Phase 2）。再検査では前回 FAIL の基準を優先しつつ、全基準を見る

### Phase 5 — Stop / 完了

- **PASS** — 状態ファイルを `PASS` にし、成果物・残った Minor・UNVERIFIED を報告する。
  リスク区分が中・高なら、ここで**人間の確認に回す**（自動で完了扱いにしない）
- **ESCALATE** — 状態ファイルを `ESCALATED` にし、[`references/handoff.md`](references/handoff.md) の
  引き継ぎ書式で報告する。**人間がゼロから調べ直さずに済む形**で渡すのが目的

## 状態ファイル（フックと連動する）

`.claude/self-correct/state.json` を Phase 0 で作成し、**ラウンドごとに更新する**。
これは記録用のメモではなく、Stop フック（`loop-stop-check.sh`）とガードフック
（`guard-ground-truth.sh`）が読む**機械可読な現在地**であり、更新を怠るとゲートが正しく効かない。

```json
{
  "status": "ACTIVE",
  "task": "drafts/article.md を references/ と突き合わせて仕上げる",
  "attempt": 1,
  "max_attempts": 3,
  "verdict": "FAIL",
  "open_ids": ["C1", "M2"],
  "protected": ["references/"],
  "updated": "2026-09-05T10:00:00Z"
}
```

- `status` — `ACTIVE` / `PASS` / `ESCALATED`。`ACTIVE` の間だけ2つのフックが効く
- `attempt` — 実施済みの修正ラウンド数。Phase 4 に入るたびに +1
- `verdict` / `open_ids` — 直近の Judge 判定と、未解決の指摘 ID（連続 FAIL の検出に使う）
- `protected` — 変更禁止範囲。ここに書いたパスへの書き込みはフックが exit 2 で拒否する
- `updated` — 更新のたびに必ず変える（Stop フックはこの値で「同じ状態への再通知」を抑止する。
  値を変えないと、次にゲートが必要な場面で通知が出ない）

ループが終わったら `status` を `PASS` か `ESCALATED` にする。**放置して `ACTIVE` のままにしない**。

## /goal との併用（任意・Level 3）

ループが安定したら、外側にセッションの完了条件を置ける:

```
/goal drafts/article.md について、loop-builder と loop-judge を使い次をすべて満たすまで改善する。
- Judge の Critical が0件・Major が0件
- 重要な UNVERIFIED が0件
- references/ を変更していない
- 問題がない箇所を不必要に書き換えていない
- 最大6ターンで未達なら停止し、残課題を報告する
```

`/goal` は1セッションに1つで、新しく設定すると前のものを置き換える。引数なしの `/goal` で
現在の状態を確認でき、`/goal clear` で解除できる。**権限は広がらない**（危険操作は従来どおり
permissions の対象）ので、これを安全機構と考えないこと。

## トークン規律

- 既定は最大3ラウンド（Build+Judge で Task 6回）。上限を最初から大きくしない
- Judge に渡すのは**成果物の場所と基準**。本文の全文をプロンプトに貼らない（Judge に読ませる）
- Builder に渡すのは**最新の FAIL 指摘だけ**。過去ラウンドの履歴を積み上げない
- 機械で判定できる基準（テスト・lint・文字数・形式）は Judge にコマンドを実行させ、
  意味の判定と混ぜない（[`references/ground-truth.md`](references/ground-truth.md) の3層検査）

## このスキルがやらないこと

- Judge に成果物を編集させる（`loop-judge` は Edit / Write を持たない）
- 指摘のない箇所の書き換え・全文再生成
- 上限を超えた自動修正の続行、同じ FAIL の3回目の挑戦
- 根拠（Ground Truth）の書き換え（フックが exit 2 で拒否する）
- 高リスク操作（送信・公開・削除・課金）の自動実行 — ループは草案までで止める
- Judge の判定を検定しないままの本番運用（Judge 自体の検定は `judge-eval`）
