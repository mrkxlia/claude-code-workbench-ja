# プロファイル追補 — Sonnet 単独（会社PC）

## 5. 評価と実行の境界（必ず）

- ユーザーが問題を**報告・記述**しているだけのときは、修正に走らずまず評価（原因・影響・選択肢）を
  返す。修正は頼まれてから。
- 状態を変えるコマンド（削除・上書き・push・設定変更）の直前に、その前提が成り立つ証拠を
  ツールで確認する。既知の障害パターンに似た兆候でも、原因が別のことがある。

## 6. ワークフローの既定（Sonnet 単独・AIDLC 簡易版）

エンドユーザの基本操作は「Plan モードで依頼 → 計画を承認」の2つ。計画も実行も Sonnet
（既定 `medium`、難しい・長い作業は `high`）が担い、上位モデルには逃がせない前提で構造を使う。
スキル名の指定を求めず、依頼内容から以下を自動選択して呼ぶ（設計の背景と対応表は
model-setup/MODEL-GUIDE.md §5）。

- **用件確認**: 成果物が変わる複数解釈・欠落があれば、Plan モードの計画に入る前にまとめて確認する。
  適用範囲（全体か一部か）は自分から明文化して確かめる。要件が深い・利害が割れる →
  `/clarify`〔pipeline 導入時〕。
- **計画と承認ゲート**: Plan モードの計画には、完了条件（ルール1）・実行に使うスキル/エージェント・
  検証チェックポイントを明記する。**承認が唯一のゲート** — 承認後は確認なしで完走する。
  長時間の自律作業で完了条件の判定を機械に任せたいときは本体の `/goal` を使う。
- **実行のルーティング**: 軽微な変更（1〜2ファイル・完了条件が自明）は直接実行する。
  コードの機能開発 → `feature-pipeline`〔pipeline 導入時〕／コード以外の成果物
  （図・ドキュメント・レポート）→ `task-pipeline`〔導入時〕／独立した並列作業は本体の
  サブエージェント委譲・dynamic workflows に任せる。
- **検証チェックポイント（頼まれなくても自動で）**: まとまった成果・完了報告・引き渡しの前に
  `/verify-fresh`（`fresh-verifier`）で自己レビューのバイアスを消す。コード変更で Codex CLI が
  ある環境は外部 CLI へのレビュー委譲で第二のモデルの目を足す。設計・計画・重要文書は `review-panel`
  〔導入時〕で敵対的にレビューする。Critical は修正→再検証（同一問題2回まで＝ルール2）。
- **自由度の高い成果物**（デザイン・設計方針・構成）は、1案目に固定せず方向性の異なる複数案を
  比較してから選ぶ。
- 手戻りが2回続いたら（ルール2）、上位モデルに逃がせない代わりに `/effort high`、それでも
  2回失敗したら `xhigh` への引き上げ（`max` は測定で品質向上を確かめたときだけ）、または Codex への相談にエスカレーションする（MODEL-GUIDE §3）。
