# PROMPTS — Sonnet 単独環境の貼り付けプロンプト集

> 出典: 公式 [Prompting Claude Sonnet 5](https://platform.claude.com/docs/ja/build-with-claude/prompt-engineering/prompting-claude-sonnet-5) /
> [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
> （2026-07時点）のスニペットの翻案。Sonnet 5 だけで運用する環境（会社 PC プロファイル等）で、
> 状況に応じて **そのターンに貼る** ことを想定した都度貼りプロンプト集。
> このファイルはプラグインの自動配信対象外（skills/agents/hooks のいずれでもない）。
> 使う場合は手元にコピーして参照する。

## 使い方 — 常設と都度貼りを区別する

- **常設（CLAUDE.md・スキル・エージェント）**: 毎回必要な行動ルールは本プラグインが既に
  常設化している（ルール1〜9＋追補、スキル6種、エージェント3種）。このファイルのスニペットを
  CLAUDE.md へ二重に貼らないこと（シグナルが薄まる。README「カスタマイズの指針」参照）。
- **都度貼り（このファイル）**: 特定の種類のタスクのときだけ効かせたい指示は、
  そのターンの依頼文に貼る。下表の「常設側の対応」が「—」のものだけが純粋な追加。

| # | スニペット | 使いどころ | 常設側の対応 |
|---|---|---|---|
| 0 | 初回プロンプトテンプレート | Plan モードの最初の依頼 | 追補ルール14/15（ワークフローの既定）と対で使う |
| 1 | 多段推論の促し | effort を low/medium に下げた定型ルート | —（effort 運用は MODEL-GUIDE §2） |
| 2 | 網羅レビュー | レビュー・調査の依頼時 | ルール9 / verify-fresh・fresh-verifier に内蔵 |
| 3 | テスト合わせ込み禁止 | 委譲せず自分で実装するとき | task-worker（ルール5）/ fresh-verifier（観点4）に内蔵 |
| 4 | 推測回答の禁止 | コードベースへの質問時 | 追補ルール10（3点目）に内蔵 |
| 5 | 早期切り上げ禁止 | 長時間の自律作業 | long-run に内蔵 |
| 6 | 複数方向の提案 | デザイン・設計など自由度の高い依頼 | 追補ルール14/15 の行動ルール（本文はここ） |
| 7 | フロントエンド美学 | UI・デザイン生成時 | —（本格運用は公式 frontend-design スキル） |
| 8 | 冗長性の制御 | 出力が長すぎる／短すぎるとき | — |
| 9 | 行動既定の切り替え | 「提案だけ」「即実装」を明示したいとき | 追補ルール12（評価と実行の境界） |

常設側に内蔵済みの #2〜#5 は、**スキル・エージェント・追補を導入していない環境**への
持ち出し用として本文を残してある。

## 0. 初回プロンプトテンプレート（Plan モード用）

Plan モードの最初の依頼に貼る型。追補ルール14/15（AIDLC 簡易版ワークフロー）と対で使うと、
「依頼 → 承認」の2アクションで用件確認〜実行〜検証まで流れる。テンプレートなしの普通の
依頼でも動くが、貼ると確認の往復が減る。

```text
## ゴール（1行）
〇〇

## 完了条件（機械的に判定できる形で）
- 〇〇（例: このテストが通る / このコマンドが exit 0 / この見出しが本文にある）

## スコープ
- 対象: 〇〇 / 非対象: 〇〇

## 制約
- 〇〇（依存追加の可否・既存パターンへの追従など）

## 検証方法
- 〇〇

## 報告形式
- 完了時は検証の証拠（実行コマンド・戻り値・テスト結果）つき。不確かな箇所は確信度 高/中/低 を明記

## 進め方
1. 上記に成果物が変わる曖昧さがあれば、選択肢＋推奨値つきの構造化質問でまず確認する
2. 実行計画には、使うスキル/エージェントの分担と検証チェックポイントを明記して承認を待つ
3. 承認後は独立した作業単位に分割し、確認を挟まず完走する
4. 完了報告の前に、経緯を知らない検証役による敵対的検証を実施し、証拠つきで報告する
```

数時間規模・タスクリスト消化型の長時間ループは、公式プラグイン **ralph-wiggum**
（stop-hook で完了まで同じプロンプトを再投入する）の利用も検討する（`docs/skills-guide/` 参照）。

## 1. 多段推論の促し（低 effort 時）

Sonnet 5 は effort レベルを（特に低い側で）字義どおり守り、`low`/`medium` では求められた
以上のことをしない。複雑な問題で推論が浅いときの第一手は effort を上げることだが、
レイテンシやコストの都合で低 effort を維持する場合はこれを貼る:

```text
このタスクは多段階の推論を要します。応答の前に、問題を段階を追って注意深く検討してください。
```

## 2. 網羅レビュー（自己選別の抑止）

Sonnet 5 は「重要なものだけ報告して」と言うと、調査の深さは保ったまま**報告だけを絞り込む**
（見かけの再現率が下がる）。レビュー・調査を依頼するときはこれを貼る（ルール9の完全版）:

```text
見つけた問題は、確信が持てないもの・低重要度と思うものも含めて全件報告してください。
この段階では重要度や確信度で絞り込まないこと — フィルタリングは後工程が行います。
目標は網羅です。後で捨てられる指摘を出すほうが、本物の問題を黙って落とすより良い。
各指摘には、後工程がランク付けできるよう確信度と推定重大度を付けてください。
```

1パスで自己選別までさせたい場合は、「重要」のような定性語でなく基準を具体化する:
「誤動作・テスト失敗・誤解を招く結果につながり得るバグは全件報告。純粋なスタイル・命名の
好みだけ省略してよい」。

## 3. テスト合わせ込み・ハードコード禁止

テストを通すことに過剰適合し、汎用性のない解やヘルパースクリプトでの回避に走るのを防ぐ
（fan-out 経由の実装では task-worker / fresh-verifier に内蔵済み。自分で直接実装するときに貼る）:

```text
標準のツールを使って、汎用的で高品質な解を実装してください。タスクを効率的に済ませるための
ヘルパースクリプトや回避策を作らないこと。テストケースだけでなく、すべての妥当な入力に対して
正しく動く解を実装すること。値のハードコードや、特定のテスト入力にだけ通る解は禁止です。
テストは正しさの検証手段であって、解の定義ではありません。タスクが不合理・実行不能だったり、
テスト自体が誤っている場合は、回避せずにその旨を報告してください。
```

## 4. 推測回答の禁止（コードベースへの質問）

開いていないコードについての推測・幻覚を抑える（追補ルール10に内蔵済み。追補を導入して
いない環境への持ち出し用）:

```text
開いていないコードについて推測しないでください。特定のファイルに言及した質問には、
必ずそのファイルを読んでから答えること。コードベースについての主張は、調査してから
行うこと。根拠のある、幻覚のない回答だけを返してください。
```

## 5. 早期切り上げ禁止（長時間作業・long-run 未導入環境向け）

コンテキスト残量を理由に作業を切り上げるのを防ぐ（Claude Code のようにコンパクションが
ある環境で有効。`/long-run` が使えるならそちらを推奨）:

```text
コンテキストウィンドウは限界に近づくと自動的に圧縮され、そこから作業を継続できます。
トークン残量を理由にタスクを早期に切り上げないでください。残量が少なくなったら、現在の
進捗と状態をファイルに保存してから続けること。可能な限り自律的・粘り強く、タスクを
完全に完了させてください。
```

## 6. 複数方向の提案（1案目に固定しない）

Sonnet 5 は `temperature` が指定できないため、出力の多様性はプロンプト構造で作るしかない。
公式ガイドは「構築前に複数の方向性を提案させ、ユーザーに選ばせる」ことをデザイン既定を破る
確実な方法として推奨している（追補ルール14/15 の「複数案比較」行動ルールの本文）:

```text
作り始める前に、この依頼に合わせた方向性の異なる案を3〜4つ提案してください
（デザインなら各案: 背景色 hex / アクセント色 hex / 書体、＋狙いの1行。それ以外なら
各案: 概要1〜2行＋強み・弱み・リスク）。どれか1つを選んでもらい、選ばれた案だけを
実装すること。無難な平均案・全案の折衷案には逃げないでください。
```

アイデア出しから設計書まで詰める本格運用は superpowers の `brainstorming`、フロントエンドの
品質底上げは公式 `frontend-design` スキルを使う（`docs/skills-guide/` 参照）。

## 7. フロントエンド美学（AI slop 回避）

一般的な指示（「その色は使わないで」「クリーンでミニマルに」）は別の固定パレットに
移るだけで多様性を生まない。UI 生成時はこれを貼る（#6 の複数方向提案と併用可）:

```text
<frontend_aesthetics>
定番の書体（Inter・Roboto・Arial・システムフォント）、クリシェな配色（特に白背景や
暗背景への紫グラデーション）、予測可能なレイアウトやコンポーネントパターンなど、
「AIが生成した」と分かる一般的な美学を使わないこと。文脈に固有の個性を持つ、独自の書体・
まとまりのある配色とテーマ・効果とマイクロインタラクションのためのアニメーションを
使ってください。
</frontend_aesthetics>
```

より確実なのは仕様の明示（hex・書体・角丸・余白まで指定する）。

## 8. 冗長性の制御

Sonnet 5 はタスクの複雑さに応じて応答の長さを変える。特定の長さ・スタイルに寄せたいとき:

```text
簡潔で焦点の絞られた応答をしてください。本質的でない文脈は省き、例は最小限にすること。
```

逆に、ツール実行後に何も言わず次へ進んでしまうのが不安なとき:

```text
ツールを使うタスクを終えたら、行った作業の短いサマリを添えてください。
```

## 9. 行動既定の切り替え

「提案だけ欲しい」のに実装される／「直して」と言ったのに提案だけ返る、のミスマッチを防ぐ。
どちらを既定にするかをタスク冒頭で明示する:

**即実装させたいとき:**

```text
既定では、提案だけでなく変更を実装してください。意図が不明確な場合は、最も有用と思われる
行動を推測して進め、不足する詳細は推測ではなくツールで調べること。
```

**提案・評価に留めたいとき:**

```text
明確に変更を指示されるまで、実装やファイル変更に踏み込まないでください。意図が曖昧な
場合は、情報提供・調査・推奨の提示を既定とすること。編集・修正・実装は、明示的に
依頼されたときだけ行ってください。
```

## 補足 — API から Sonnet 5 を使う場合の注意（プロンプト外）

Claude Code ではなく API 直で Sonnet 5 を使うアプリ開発（MODEL-GUIDE §6 の領域）では、
プロンプト以前に次の仕様変更に注意する（出典:
[Prompting Claude Sonnet 5](https://platform.claude.com/docs/ja/build-with-claude/prompt-engineering/prompting-claude-sonnet-5)）:

- **adaptive thinking が既定 ON**。`thinking` 未指定でも思考する（Sonnet 4.6 からの変更）。
  完全にオフにするには `thinking: {type: "disabled"}`。`budget_tokens` 指定は 400 エラー。
- **`temperature` / `top_p` / `top_k` の非既定値は 400 エラー**。スタイルの多様性は
  プロンプト構造で作る（→ #6 複数方向の提案）。
- **新トークナイザで同じテキストが約30%多くトークン化される**。`max_tokens` は 4.6 時代の
  値から余裕を持たせないと、思考で予算を使い切って応答が切り詰められることがある。
