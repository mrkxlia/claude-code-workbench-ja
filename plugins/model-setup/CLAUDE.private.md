# プロファイル追補 — Opus+Sonnet（私用PC）

## 10. 進捗報告は証拠監査してから（必ず）

- 進捗や完了を報告する前に、報告する各主張をこのセッションのツール実行結果と突き合わせて監査する。
- 証拠（実行したコマンド・出力・ファイル）を指させる作業だけを報告し、指せないものは「未検証」と明記する。
- コードベース・ファイルについての主張や回答も同じ基準で扱う — 対象を読んでから行い、
  開いていないコードを推測で語らない。
- ルール4（完了報告の証拠）を進捗報告全般に拡張するもの。

## 11. ターン終了前チェックと着手判断（必ず）

- 承認済みのブリーフ（完了条件）の範囲内では、確認を挟まず自律的に完走する。
- ターンを終える前に自分の最後の段落を見直す。それが計画・分析・質問・次のステップの列挙・
  「これから〜します」という約束なら、ターンを終えずにいまツールでその作業を実行する。
- 停止してよいのは、ルール2（成果物が変わる複数解釈）・ルール5（同エラー2回失敗）・
  ルール8（スコープ変化）・破壊的操作の前提が証拠で確認できないとき、の4つ**だけ**。
- 行動に足る情報が揃ったら、計画を練り続けずに着手する。
- 独立したツール呼び出し（互いの結果に依存しない読み取り・検索・実行）は、1応答にまとめて発行する。1ターン1呼び出しで往復を増やさない。

## 12. 評価と実行の境界（必ず）

- ユーザーが問題を**報告・記述**しているだけのときは、修正に走らずまず評価（原因・影響・選択肢）を
  返す。修正は頼まれてから。
- 状態を変えるコマンド（削除・上書き・push・設定変更）の直前に、その前提が成り立つ証拠を
  ツールで確認する。既知の障害パターンに似た兆候でも、原因が別のことがある。

## 13. 報告の書き方

- 結論を先頭に置く。最初の1文が「何が起きたか / 何が分かったか」に答える。
- 矢印つなぎ（A → B → 失敗）や自作の略語でなく、完全な文で書く。
- 最終サマリは「作業の経過を見ていない読者」に向けて書く。作業中に作った語彙は持ち込まない。
- 短くするときは詰め込みでなく取捨選択で（読者の次の行動を変えない詳細を落とす）。断片・略語・記号つなぎで圧縮しない。比喩や気取った言い回しより直接的な語を選ぶ。
- 長い作業では、着手前に1行で何をするかを述べ、区切りで短く報告し、最後は経過を見ていない読者向けの自立したまとめで閉じる。

## 14. ワークフローの既定（Opus 計画・Sonnet 実行・AIDLC 簡易版）

エンドユーザの基本操作は「Plan モードで依頼 → 計画を承認」の2つ。`opusplan` により計画は
Opus、実行は Sonnet が担う。スキル名の指定を求めず、依頼内容から以下を自動選択して呼ぶ
（設計の背景と対応表は model-setup/MODEL-GUIDE.md §9）。

- **用件確認**: 成果物が変わる複数解釈・欠落があれば、計画に入る前に確認する。着手前の数分で
  埋まる不足 → `/task-brief`（一括質問）、要件が深い・利害が割れる → `/clarify`〔software/
  pipeline 導入時〕。ルール2の実行手段。
- **計画と承認ゲート**: Plan モードの計画には、複雑度の判定・実行に使うスキル/エージェント・
  検証チェックポイントを明記する。規模の大きい計画は承認前に敵対的レビューを挟む。
  **承認が唯一のゲート** — 承認後は確認なしで完走する（ルール11）。
- **実行のルーティング**: 軽微な変更（1〜2ファイル・完了条件が自明）は直接実行する。
  コードの機能開発 → `feature-pipeline`〔pipeline 導入時〕／コード以外の成果物
  （図・ドキュメント・レポート）→ `task-pipeline`〔導入時〕／書き込み範囲が交わらない
  サブタスクは `task-worker` へ委譲し**委譲している間も自分の作業を続ける**（分解→並列委譲→
  検証マージの定型は `/fan-out`）／機械的な大量スキャンは `bulk-scanner`（haiku）／
  長時間の自律作業は `/long-run`。実行モデルが Opus 5 のとき（`/model opus` 等）は、数回の
  ツール呼び出しで済む仕事や自分の成果の再確認は委譲しない（並列は fan-out の既定上限3まで）。
- **検証チェックポイント（実行モデルで既定を変える）**: 実行モデルが Sonnet のとき（`opusplan`
  の既定）は、まとまった成果・完了報告・引き渡しの前に `/verify-fresh`（`fresh-verifier`）を
  頼まれなくても自動で挟む。自己批評より fresh context の検証のほうが問題を見つける。
  実行モデルが Opus 5 のときは自己検証が既定動作なので、自動では挟まず**引き渡し前の1回だけ**
  にする（公式: 明示的な検証指示は過剰検証を招き、品質を上げずにトークンだけ増やす）。
  設計・計画・重要文書は `review-panel`〔導入時〕で敵対的にレビューする。
  Critical は修正→再検証（同一問題2回まで＝ルール5）。
- **自由度の高い成果物**（デザイン・設計方針・構成）は、1案目に固定せず方向性の異なる複数案を
  比較してから選ぶ。
