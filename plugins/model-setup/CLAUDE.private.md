# プロファイル追補 — Opus+Sonnet（私用PC）

## 5. 評価と実行の境界（必ず）

- ユーザーが問題を**報告・記述**しているだけのときは、修正に走らずまず評価（原因・影響・選択肢）を
  返す。修正は頼まれてから。
- 状態を変えるコマンド（削除・上書き・push・設定変更）の直前に、その前提が成り立つ証拠を
  ツールで確認する。既知の障害パターンに似た兆候でも、原因が別のことがある。

## 6. ワークフローの既定（Opus 計画・Sonnet 実行・AIDLC 簡易版）

エンドユーザの基本操作は「Plan モードで依頼 → 計画を承認」の2つ。`opusplan` により計画は
Opus、実行は Sonnet が担う。スキル名の指定を求めず、依頼内容から以下を自動選択して呼ぶ
（設計の背景と対応表は model-setup/MODEL-GUIDE.md §5）。

- **用件確認**: 成果物が変わる複数解釈・欠落があれば、Plan モードの計画に入る前にまとめて確認する。
  要件が深い・利害が割れる → `/clarify`〔pipeline 導入時〕。
- **計画と承認ゲート**: Plan モードの計画には、完了条件（ルール1）・実行に使うスキル/エージェント・
  検証チェックポイントを明記する。**承認が唯一のゲート** — 承認後は確認なしで完走する。
  長時間の自律作業で完了条件の判定を機械に任せたいときは本体の `/goal` を使う。
- **実行のルーティング**: 軽微な変更（1〜2ファイル・完了条件が自明）は直接実行する。
  コードの機能開発 → `feature-pipeline`〔pipeline 導入時〕／コード以外の成果物
  （図・ドキュメント・レポート）→ `task-pipeline`〔導入時〕／独立した並列作業は本体の
  サブエージェント委譲・dynamic workflows・`/batch` に任せる（このテンプレートでは作業員を持たない）。
- **検証チェックポイント（実行モデルで既定を変える）**: 実行モデルが Sonnet のとき（`opusplan`
  の既定）は、まとまった成果・完了報告・引き渡しの前に `/verify-fresh`（`fresh-verifier`）を
  頼まれなくても自動で挟む。実行モデルが Opus 5 のときは自己検証が既定動作なので、
  **引き渡し前の1回だけ**にし、ルール3 の初見レビューも省略してよい（公式 Opus 5 ガイド:
  明示的な検証指示は過剰検証を招く）。自分がどちらのモデルかはシステムプロンプトのモデル名で
  判定し、判定できなければ Sonnet 側（自動検証あり）で動く。設計・計画・重要文書は
  `review-panel`〔導入時〕で敵対的にレビューする。Critical は修正→再検証（同一問題2回まで＝ルール2）。
- **自由度の高い成果物**（デザイン・設計方針・構成）は、1案目に固定せず方向性の異なる複数案を
  比較してから選ぶ。
