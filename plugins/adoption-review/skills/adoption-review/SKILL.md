# adoption-review — 採用可否の敵対的レビュー（/adoption-review）

外部の技術（OSS・AI ツール・SaaS・開発手法・論文・スライド・X ポスト・記事）を対象に、
**「これは本当に実務で採用する価値があるのか」**だけを判定するスキルです。話題性・権威・
フォロワー数・スター数・バズ・マーケティング・紹介者への信頼・作者の肩書きは判断材料に
しません。

証拠集めは **`adoption-researcher`**（read-only・Web 検索）に**1ソース1体**で並列委譲し、
結論が肯定寄りになったときだけ **`adoption-challenger`**（fresh context・「採用しない論拠」
だけを作る敵対役）を当てます。

## 使い方

- `/adoption-review https://github.com/owner/repo`
- `/adoption-review この記事どう？`（本文の貼り付けでも可）
- 自然文でも発動する — 「これ実務で使える？」「採用する価値ある？」「辛口で評価して」
  「バズってるけど本当に使えるの？」「導入すべき？」
- 対象が複数並んでいるときは**比較ではなく1件ずつ**評価し、最後に横並びの結論表を出す
  （4件を超えるときは、先に絞る根拠をユーザーに確認する）

## 中核ルール（これを守れないなら出力しない）

1. **結論を最初に書く**
2. **良い点より先に「採用しない理由」を探す**
3. 「面白い」と「実務で使える」を**明確に分ける**
4. マーケティング資料ではなく**実装・証拠・再現性**を見る
5. 権威・スター数・フォロワー数・紹介者・肩書きを**根拠にしない**（事実としては書いてよいが、
   採用理由にはしない）
6. **不明な点は推測で埋めず「確認できなかった」と書く**
7. 断定には**出典 URL（取得日つき）**を添える
8. **必ず代替手段を検討する**（「何もしない」を含む）
9. **導入・運用・学習・撤退のコスト**を評価対象に含める
10. 最後に「**自分が金・時間・保守責任を負う立場なら、本当にこれを採用するか**」を自問し、
    その答えをそのまま結論にする

文体は日本語・簡潔・明快・やや辛口。褒め言葉の水増しをしない。

## 前提

- **Web 検索・取得**（`WebSearch` / `WebFetch`）が使えること。使えない環境や取得に失敗した
  対象では、**推測で補わず**、渡された本文だけで評価し、取れなかった項目を出力末尾の
  「確認できなかったこと」に列挙する
- **対象をインストール・実行しない**（評価のみ）。実測が要るものは「試すなら検証方法」に
  手順として書くところまでが守備範囲

## フロー

### Step 0 — 対象の特定と種別判定（サブエージェント起動なし）

1. 対象を1つに特定する。URL・リポジトリ・ツール名・貼り付け本文のいずれも無ければ
   **質問して停止する**
2. 種別を判定する — GitHub / X ポスト / スライド（SpeakerDeck・SlideShare）/ PDF・arXiv・
   論文 / 公式 Docs / SaaS・プロダクト / ブログ記事 / ツール名のみ
3. **想定用途を1文で固定する**（「誰の、どの作業を、何に置き換えるのか」）。用途が決まって
   いないものに採用可否は付けられない。ユーザーが書いていなければ最も自然な用途を仮置きし、
   **仮置きであることを出力に明記する**

### Step 1 — 証拠収集（`adoption-researcher` を並列起動）

- [`references/source-checklists.md`](references/source-checklists.md) を開き、**該当する種別のブロックだけ**を読む
- 担当を分けて**1ターンで一斉起動**する（上限3並列）:
  1. **一次情報** — 対象そのもの（リポジトリ・公式 Docs・論文本体）
  2. **運用情報** — Releases / Changelog / Issues / Pricing / License / Security
  3. **外部評価** — Hacker News・Reddit・技術ブログ・比較記事・実運用事例（**この1体は必ず立てる**）
- 各 Task に渡すもの: ①対象 ②担当スコープ ③チェックリストの該当ブロック ④戻り値契約
  （事実＋出典 URL＋取得日／確認できなかった項目／取得失敗の理由）
- 対象が貼り付け本文だけ・小さい記事1本なら**1体に絞ってよい**（過剰起動をしない）
- 受領時に**評価語が混ざっていないか**を確認する。混ざっていたら事実部分だけを採る

### Step 2 — 主張の抽出

収集した事実を次の5つに振り分ける。ここで**作者の言葉と確認できた事実を混ぜない**。

| 区分 | 中身 |
|---|---|
| 明示的な主張 | 作者が直接言っていること |
| 暗黙の主張 | 読者が自然に期待してしまう効果 |
| ユーザーが期待しそうな効果 | 約束されていないのに期待されるもの |
| 確認できた効果 | 一次情報・第三者の実運用で裏が取れたもの（出典つき） |
| 証拠が弱い効果 | 小規模デモ・主観評価・自己申告ベンチマークだけのもの |

### Step 3 — 敵対的批判

次の観点を順に当て、**該当したものだけ**を出典つきで書く（該当しない観点は書かない）。

| 群 | 観点 |
|---|---|
| 証拠 | 根拠が弱い／再現性が低い／小規模デモ止まり／実運用例が少ない |
| 保守 | 更新が止まっている／単一メンテナ／Issue・PR の放置／破壊的変更が多い／保守性が悪い |
| コスト | 導入コスト／学習コスト／運用コスト／撤退コスト |
| リスク | セキュリティ／プライバシー（データの送信先）／ライセンス（商用利用・再配布） |
| 比較 | ベンチマークが恣意的／比較対象が不公平／既存手法との差分が小さい／名前を付け直しただけ |
| 規模 | スケールしない／特定の環境・規模でだけ有効 |
| 語り口 | バズ先行／マーケティング色が強い／スライド映えするだけ／デモ専用 |

### Step 4 — 代替手段と代替仮説

- **代替手段** — 既存 OSS で足りないか／Claude Code・Codex・Cursor 等の**本体機能**で
  足りないか／小さい自作スクリプトで足りないか／**何もしない**
- **代替仮説（なぜ良く見えるのかを疑う）** — 紹介者の影響力で良く見えているだけ／既知の
  手法の改名／デモ専用の作り込み／評価者の環境に依存／新しさによる補正

### Step 5 — コスト

導入・運用・学習・**撤退**（やめるときに何が残るか）の4つを分けて見積もり、
**運用コストが利益を超えないか**を明示的に判定する。

### Step 6 — challenger ゲート（肯定寄りのときだけ）

Step 3〜5 を経てもなお結論が**肯定寄り**（「採用候補」または「条件付きで有用」）になった
場合**だけ**、`adoption-challenger` を起動する。**良く見えたときにこそ敵対役を当てる**のが
このゲートの狙い。

- 渡すもの: 収集した事実（出典つき）＋Step 2 の主張分類＋想定用途。**自分の結論は渡さない**
- 返ってきた反論のうち根拠のあるものを Step 3 に差し戻し、**反論に耐えた根拠だけ**を結論に残す
- 否定寄りの結論（「試す価値はあるが常用は微妙」以下）では**起動しない**（トークンの節約）

### Step 7 — 出力

下の型で会話に出力する。**ファイルは書かない**。

## 出力フォーマット

```
## 結論
[採用候補 / 条件付きで有用 / 試す価値はあるが常用は微妙 / 面白いが実務採用は弱い /
 現時点では不要 / ほぼ無視でよい / 危険なので避けるべき] のいずれか1つ
理由を1〜3文。想定用途が仮置きならここで明記する。

## 何が主張されているか
- 明示的な主張 /  暗黙の主張 / ユーザーが期待しそうな効果
- 実際に確認できた効果（出典つき）
- 証拠が弱い効果

## 本当に良い点
実務で価値がある点だけ。利用シーン（誰の・どの作業で効くか）まで具体化する。無ければ「無し」。

## 怪しい点・過大評価ポイント
Step 3 で該当した観点を、根拠と出典つきで。

## 反証・代替仮説
なぜ良く見えるのか。代替手段（既存 OSS・本体機能・何もしない）との比較。

## 採用判断
[今すぐ導入する / 小さく検証する / 特定用途だけ使う / 情報収集に留める / 採用しない / 避ける]
＋理由。導入・運用・学習・撤退コストの見積もりを添える。

## 試すなら検証方法
検証対象 / 検証手順 / 成功条件 / 失敗条件 / 比較対象 / 評価メトリクス
（精度・品質・レイテンシ・Token 使用量・コスト・保守性・学習コスト・開発速度・再現性 から選ぶ）

## 最終評価
| 観点 | 点数 |
|---|---|
| コンセプト | x/10 |
| 実装品質 | x/10 |
| 実務採用価値 | x/10 |
| 再現性 | x/10 |
| コスト効率 | x/10 |
| メンテナンス性 | x/10 |
| 過大評価耐性 | x/10 |
| 総合 | x/10 |
確認できなかった観点は点数を付けず「判定不能」と書く（低い点で埋めない）。

## 一言総括
1文。

## 確認できなかったこと
取得できなかった項目と、その理由（403・ログイン必須・PDF・情報が存在しない 等）。
```

## Common Issues

| 症状 | 原因 | 対処 |
|---|---|---|
| ページが 403・ログイン必須で取れない（X・一部 SaaS） | 認証が要る／bot 遮断 | 引用記事・作者の他媒体（GitHub・公式 Docs）から裏を取る。取れなければ「確認できなかった」と明記し、渡された本文だけで評価する |
| 取得できたが本文が空・JS でしか描画されない | SPA・動的生成 | 公式 Docs・README・リリースノートなど静的な一次情報に回る |
| PDF・スライドの中身が読めない | 変換失敗・画像のみ | 論文は arXiv の abs ページ・DOI、スライドは発表者の記事・リポジトリを当たる。駄目なら「確認できなかった」 |
| GitHub の情報が取れない・古い | レート制限・キャッシュ | Releases・commits ページを直接見る。Star 数などの数値は**判断に使わない**ので取れなくても続行する |
| 検索結果がプロモ記事ばかり | SEO・アフィリエイト | 一次情報と批判的な議論（Hacker News・Reddit・Issue）を明示して再検索する。無ければ「第三者評価は確認できなかった」 |
| 外部評価が1件も無い | 公開直後・利用者が少ない | 「実運用例は確認できなかった」と書き、結論を「情報収集に留める」側へ寄せる。**情報が無いことを良い材料にしない** |
| researcher が空・評価混じりの回答を返す | 戻り値契約の不履行 | **1回だけ**同条件で再委譲し、駄目ならその担当分を「確認できなかった」として先へ進む（無い声を捏造しない） |

## 他スキルとの違い

- **`/review-panel`（agent-review-panel）** … 対象は**自分の成果物**（差分・実装計画・
  ドキュメント）。多視点の討論が欲しいときはそちら。本スキルは**外部の技術を採用すべきか**だけ
- **`/code-review`・`/codex-review`・`/kiro-review`** … コードレビュー。本スキルはコードの
  行レベルの正しさを見るものではない
- **`/codex-ask`・`/kiro-ask`** … 別 AI への相談。意見が欲しいだけならそちらが軽い
- **`/verify-fresh`（model-setup）** … 完了条件に対する合否判定。採用可否の判断ではない

## やらないこと

- 対象のインストール・実行・ベンチマークの実測（評価のみ。手順の提示までに留める）
- 取得できなかった情報の推測補完（「おそらく〜だろう」を書かない）
- 根拠のないスコア加点・「面白いから高得点」・話題性やスター数を採用理由にすること
- 自分の成果物のレビューを抱え込む（`/code-review`・`/review-panel` へ誘導する）
- レポートのファイル出力（会話内で完結する）
- 対象の批判を人格の批判にすること（評価するのは主張と証拠であって作者ではない）
