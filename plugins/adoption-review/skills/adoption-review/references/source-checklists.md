# source-checklists — 対象種別ごとの確認項目

`adoption-review` の Step 1 で読む。**該当する種別のブロックだけ**をサブエージェントの
プロンプトに注入する（全部読まない）。

**注入してよいのは各表の「項目」「見るもの」列だけ**。A の「何が分かるか」列は
呼び出し側（メイン）の判断用であり、サブエージェントには渡さない — 良し悪しの含意を注入すると、
`adoption-researcher` の「評価語を書かない」契約がその場で壊れる。

共通の書式ルール:

- 各項目は「**確認できた事実＋出典 URL＋取得日**」で返す
- 取れなかった項目は**推測で埋めず**「確認できなかった（理由）」と返す
- 数値（Star 数・フォロワー数・引用数）は**事実として記録するだけ**で、採用理由には使わない

---

## A. GitHub リポジトリ

| 項目 | 見るもの | 何が分かるか |
|---|---|---|
| README | 主張・前提・制限の記載 | 何を約束しているか。制限の記載の有無 |
| 最新更新 | 直近コミット日 | 更新が続いているか。止まっている場合は理由（完成・移行・放棄）を探す |
| Releases | タグの間隔・リリースノートの粒度 | 変更が管理されているか。破壊的変更の頻度 |
| Issues | 未対応の件数・古い Issue・反応の有無 | 保守されているか。既知の欠陥 |
| Pull Requests | 外部 PR が取り込まれているか | 単一メンテナの属人性 |
| Contributors | 実質的な貢献者数 | バス係数（1人なら明記する） |
| commit 頻度 | 直近3か月の分布 | 一時的な熱量か継続か |
| License | SPDX 表記・商用利用・再配布 | 業務で使えるか。LICENSE ファイルの有無（無い場合は「無い」と記録する） |
| CI | ワークフローの有無・成否 | 変更が検証されているか |
| テスト | テストディレクトリ・カバレッジ | 主張が守られているか |
| Security | SECURITY.md・依存の脆弱性・秘密情報の扱い | 導入時のリスク |
| Discussions | 実利用者の質問・回答の質 | 実運用されているか |
| Star / Fork | 数値 | **記録のみ。採用理由にしない** |

## B. プロダクト・SaaS

| 項目 | 見るもの |
|---|---|
| 公式 Docs | 機能の実体・制限・レート制限・SLA |
| Pricing | 無料枠・従量課金の単価と上限・チーム単価・別課金の項目 |
| Changelog | 直近の更新日・更新の頻度と粒度 |
| Security / Privacy | データの送信先・保存期間・学習利用の有無・第三者認証 |
| Enterprise | SSO・監査ログ・データ所在地（業務要件を満たすか） |
| API | 公開 API の有無・データのエクスポート手段の有無 |
| OSS か | ライセンス・セルフホストの可否・データ移行手段の有無 |

## C. 論文・arXiv・PDF

| 項目 | 見るもの |
|---|---|
| 一次情報 | arXiv abs ページ・DOI・査読の有無（プレプリントなら明記する） |
| 実装 | 公式実装の有無・再現コードの有無（無ければ「再現性は確認できなかった」） |
| ベンチマーク | データセット・比較対象・実験条件・再現に必要な環境 |
| 追試 | 第三者による再現報告・反証 |
| Citation | 数値（記録のみ） |
| 適用範囲 | 実験環境（規模・データ・前提）と、渡された想定用途との一致点・相違点 |

## D. スライド（SpeakerDeck・SlideShare）・X ポスト・ブログ記事

| 項目 | 見るもの |
|---|---|
| 一次情報へのリンク | リポジトリ・論文・公式 Docs へのリンクの有無 |
| 主張の出所 | 実測か、伝聞か、体験談か |
| 数値の条件 | 「N 倍速い」の測定条件・母数・期間 |
| 発表の文脈 | 発表の場（登壇・宣伝・アフィリエイトの表示）の有無 |
| 取得できない場合 | X はログイン必須で取れないことが多い。**取得失敗を明記**し、引用記事・作者の GitHub など別経路で裏を取る |

**この種別に固有の注意（呼び出し側の判断用。注入しない）** — スライドと X ポストは
「主張の要約」であって証拠ではない。ここで確認できた事実は、原則として「証拠が弱い効果」に
分類する。

## E. ツール名だけを渡された場合

**対象の同定は Step 0 で呼び出し側（メイン）が行う** — サブエージェントはユーザーに質問できない
ので、候補が複数残る場合の「候補を提示して停止」はメインの仕事。researcher は**同定済みの対象**を
受け取り、A または B のブロックで調べる。

同定後に追加で1件だけ拾うもの: **同名・類似名の代替ツールを1〜2件**（Step 4 の代替手段に使う）。

## F. 外部評価（全種別で必ず1体を割り当てる）

| 項目 | 見るもの |
|---|---|
| Hacker News / Reddit | 批判側の具体的な指摘（「使ってみたら〜だった」）を優先して拾う |
| 技術ブログ | 実運用の報告（規模・期間・撤退したかどうか） |
| 比較記事 | 比較対象と条件。アフィリエイト表示の有無を併記する |
| Issue / Discussions | 実利用者がつまずいた箇所 |
| 実運用報告の有無 | 見つかった件数（0件なら「0件」と記録する。0件であることも事実として返す） |
