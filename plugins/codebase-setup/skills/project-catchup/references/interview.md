# interview — コードから読めないことを人に聞く

`project-catchup` の Step 6 で使う。**聞ける相手がいるときだけ**読む。

レポートの9章「未確認」は、放っておくと埋まらない。コードに書いていないからそこに残っている。
この別冊は、未確認の項目を**答えやすい質問**に変換するためのもの。

## 原則

1. **Yes/No か、選択肢つきで聞く。** 「認証はどうなっていますか」ではなく
   「Cognito の `sub` と `Member.email` で照合していると読みましたが、合っていますか」
2. **自分の読みを先に出す。** 相手は訂正するだけで済む。ゼロから説明させない
3. **根拠を添える。** 「`src/auth/jwt-auth.guard.ts:24` を見るとこう読めました」
4. **1回にまとめる。** 小出しに聞くと相手の時間を細切れに奪う
5. **聞いた答えは、レポートの該当章に反映してから9章から消す。** 9章に答えを書き足さない

## 未確認 → 質問への変換

| 9章に残っているもの | 質問の形 |
|---|---|
| 用途が分からないディレクトリ・テーブル | 「`legacy_sync` は今も使われていますか。使われていないなら、いつ止まったか分かりますか」 |
| 2つのやり方が混在している | 「`formatDate` と `formatDateTz` が両方ありますが、新規コードはどちらを使いますか」 |
| 設定値の入手先が不明 | 「`COGNITO_USER_POOL_ID` のローカル用の値は、どこから貰えばよいですか」 |
| 実行できなかった手順 | 「README の `npm run seed` が失敗しました（エラー: ...）。今も動く手順ですか」 |
| 意図が読めない実装 | 「ここで意図的にトランザクションを分けているように見えますが、理由がありますか」 |

## コードには絶対に書いていないこと（聞くしかない項目）

**運用**

- 本番でのデプロイは誰が・いつ・どういう手順で行うか。ロールバックの手段は何か
- 監視は何を見ているか。アラートは誰に飛ぶか。当番はあるか
- 定期作業（バッチの監視・証明書更新・棚卸し）は何があるか

**歴史**

- 直近1年で大きく変えた部分はどこか（そこは書き方が新しい／古いが混在している）
- 過去に起きた障害と、その結果として入った制約はあるか
- 「触ると危ない」と言われている箇所はどこか、なぜか

**判断の理由**

- この構成を選んだ理由（制約・コスト・組織の事情）。**代替案を却下した理由**があれば特に価値が高い
- 今の設計で不満に思っている点はどこか（次に直す候補）

**人と担当**

- どの領域を誰が見ているか。レビュアーは誰か
- 質問はどこに投げるのが早いか（チャンネル・issue・直接）

## 聞いたあとにすること

- 答えを**該当する章に反映する**（3章の話なら3章へ）。9章には残さない
- 「聞いて分かった」ことは、根拠の代わりに `（YYYY-MM-DD・◯◯さんに確認）` を添える。
  コードが根拠ではないと後から分かるようにする
- 答えが得られなかった項目は9章に残し、**誰に聞いても分からなかったのか**を書く
