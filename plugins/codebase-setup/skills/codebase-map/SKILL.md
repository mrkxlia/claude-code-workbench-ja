# codebase-map — リポジトリの地図をつくる

トップレベルが数十以上あるリポジトリや、命名から中身が読めないリポジトリでは、Claude は
「どこを見ればいいか」を探すためだけにファイルを開き続けることになる。**1行説明つきの目次が
1枚あれば、開く前に当たりが付く。**

このスキルは、その目次を read-only の測量で作り、`docs/codebase-map.md` に置く。

出典: [How Claude Code works in large codebases](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)

## 使いどころ／住み分け

- 対象: トップレベルの項目が概ね15以上、または命名が独特（社内略語・歴史的経緯）なリポジトリ
- **その必要が無いリポジトリには作らない。** `src/`・`tests/`・`docs/` しか無いなら地図は
  ただの負債になる。作らない判断も成果物として報告する
- 単発の「◯◯はどこに実装されている？」 → 内蔵の Explore / Task サブエージェント（地図は要らない）
- 参画した案件を「実装者として動ける水準」まで理解したい → `project-catchup`
  （地図が「どこに何があるか」なのに対し、あちらは「どう動いているか」を図つきで書く）
- 既存コードから仕様書を逆引きしたい → cc-rsg 等の外部ツール（このスキルは仕様を書かない）
- 常時ロードされる指示（CLAUDE.md）の棚卸し → `context-audit`
- 設定の足場づくり全体 → `codebase-onboard`（このスキルはその Step の一部としても呼ばれる）

## 中核ルール

1. **地図を CLAUDE.md に書かない。** ディレクトリ一覧はコードから導ける情報であり、常時
   コンテキストに載せる価値が最も低い部類。地図は独立ファイルに置き、CLAUDE.md からは
   **1行のポインタ**（「全体構成は `docs/codebase-map.md` を参照」）だけを張る。
   `@` 記法の import は起動時に本文ごと読み込まれてしまうので、**バッククォートで囲んだ
   ただのパス表記**にする
2. **1行説明には根拠を持つ。** 実際に読んだファイル（README・エントリポイント・マニフェスト）を
   根拠にする。ディレクトリ名からの推測で埋めない。分からないものは「不明」と書く
3. **調査はサブエージェントに委譲する。** 地図づくりは大量のファイルを開く作業なので、
   メインの文脈でやると次の作業のためのコンテキストが残らない
4. **1行は1行。** 説明が2行以上要るサブツリーは、その中の階層に降ろす（下記の層別）
5. **更新は差分で。** 既に地図がある場合は作り直さず、消えたディレクトリ・増えたディレクトリ・
   説明が実態と合わなくなった項目だけを直す

## ワークフロー

1. **規模を測る** — `ls -1 | wc -l`、`git ls-files | wc -l`、既存の `docs/codebase-map.md` の有無。
   トップレベルが少なく命名も素直なら、ここで「地図は不要」と報告して終わる
2. **層を決める**

   | トップレベルの項目数 | 構成 |
   |---|---|
   | 15〜40 | 1層。トップレベル項目を1行ずつ |
   | 40以上 | 2層。まずグループ（例: `services/`・`libs/`・`tools/`）を1行ずつ、各グループの中身は見出しを分けて1行ずつ |
   | 深いモノレポ | 2層＋各パッケージの入口ファイルだけ |

3. **測量を委譲する** — 対象サブツリーごとに `subtree-surveyor` サブエージェントを起動する
   （3つ以上あるなら並列）。依頼文:

   ```
   担当サブツリー: <パス>
   このサブツリーだけを調べ、出力書式どおりに返してください。担当外は読まないこと。
   特に知りたい: 1行要約・主要ディレクトリ・入口ファイル・テスト/ビルドのコマンド。
   ```

4. **統合して書く** — 下記のテンプレートで `docs/codebase-map.md` を作る（既存があれば差分更新）
5. **ポインタを張る** — ルート CLAUDE.md に「全体構成は `docs/codebase-map.md`」の1行が
   無ければ、追記する差分を提示して承認を得る（本文の取り込みはしない）
6. **報告する** — 地図のパス、掲載件数、「不明」のまま残した項目、次に埋めるべき箇所

## 出力テンプレート

````markdown
# コードベース地図

<!-- codebase-map スキルで生成。更新日: YYYY-MM-DD -->
<!-- 1行説明は実ファイルを根拠にしている。推測は「不明」と書く -->

## 全体像

<3〜5行。このリポジトリが何であるか、主要な流れ>

## トップレベル

| パス | 役割 | 入口 |
|---|---|---|
| `services/api/` | 顧客向け REST API | `services/api/src/main.ts` |
| `libs/auth/` | 認証・認可の共有ライブラリ | `libs/auth/index.ts` |

## <グループ名>（2層構成のときだけ）

| パス | 役割 | 入口 |
|---|---|---|

## コマンド

| 目的 | コマンド | 実行場所 |
|---|---|---|
| テスト | `npm test` | 各パッケージ |

## 不明・未調査

- `tools/legacy-sync/` — 参照元が見つからず用途不明（2026-09-05 時点）
````

`<>` の箇所は実測値で埋める。埋まらない項目は「不明・未調査」節に落とす。

## やらないこと

- ディレクトリ名からの推測で1行説明を埋めること
- 地図の本文を CLAUDE.md に取り込むこと（常時ロードの肥大化）
- 仕様・設計の記述（このスキルは「どこに何があるか」だけを書く）
- 地図が要らないリポジトリに地図を作ること

## 連携

- 足場づくり全体 → `codebase-onboard`（Step 2 の測量結果をそのまま地図にできる）
- 案件キャッチアップのレポート → `project-catchup`（この地図を調査の入力として使える）
- 常時ロードされる指示の棚卸し → `context-audit`
- 測量の実行役 → `subtree-surveyor` サブエージェント
