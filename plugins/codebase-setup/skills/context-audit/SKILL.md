# context-audit — 常時ロードされる指示の棚卸し

CLAUDE.md は一度書くと消されない。プロジェクトが育つほど積み上がり、**指示の量が増えるほど
個々の指示の遵守率は下がる。** さらにモデルが更新されると、旧モデルの弱点を埋めるために
書かれた指示（「リファクタは1ファイルずつ」等）は、そのまま足かせに変わる。

このスキルは「正しいか」ではなく **「毎回コンテキストに載せる価値があるか」** で仕分ける。

対象は CLAUDE.md 階層だけではない。**本体の auto memory が書く `MEMORY.md` も、セッション開始時に
先頭200行（または 25KB）までがコンテキストに載る**（[Memory](https://code.claude.com/docs/en/memory)）。
こちらは Claude が自分で書き足し、**git 管理外なので差分に出ない** — 人がレビューしないまま
CLAUDE.md やスキルと食い違う「第2の規約レイヤー」になりうる。指示ファイルと同じ棚に載せて扱う。

出典: [How Claude Code works in large codebases](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)（設定はモデルの進化に合わせて見直す）

## 使いどころ／住み分け

- 実施の目安: **3〜6か月ごと**、および**大きなモデル更新の直後**。加えて「CLAUDE.md に書いた
  のに守られない」「セッション開始時点でコンテキストが重い」と感じたとき
- **いま困っているなら棚卸しを待たない** — 特定の記憶が原因で作業が壊れている（同じ誤りを
  繰り返す・不要な手順を強制される）なら、周期を待たずその場で `/memory` から該当ファイルを
  開いて消す。auto memory ごと切るなら `autoMemoryEnabled: false`（設定）か
  `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`（環境変数）。このスキルが引き受けるのは**横断照合**のほうで、
  緊急の切り分けではない
- 1ファイルを機械的に短くするだけ → 本体の `/doctor`（このスキルも Step 2 で参考にする）
- パイプラインのエージェント定義・スキル本文の改善 → `pipeline-improve`（pipeline プラグイン）
- スキルの書き方（frontmatter 規約・分冊基準） → `docs/skill-authoring.md`
- コード差分のレビュー → 本体の `/code-review`
- 足場そのものがまだ無い → 先に `codebase-onboard`

## 5分類（判定基準）

| 分類 | 意味 | 処置 |
|---|---|---|
| **A 陳腐化** | 旧モデルの制約を回避するための指示 | 削除を提案 |
| **B 矛盾** | 他ファイル・同一ファイル内の別項目と食い違う | どちらが正かを確認して片方を削除 |
| **C 導出可能** | コードを読めば分かる事実（ディレクトリ一覧・依存列挙・アーキ概説） | 削除を提案。必要なら別ファイル＋ポインタへ |
| **D 常時ロードが過剰** | 正しいが特定の領域・作業のときだけ要る | 移設（下表） |
| **E 保持** | 落とし穴・ツール既定と異なる規約・禁止事項・コマンド・理由 | そのまま |

**D の移設先**:

| 内容 | 移設先 |
|---|---|
| 特定ディレクトリで常に効く規約 | そのディレクトリの `CLAUDE.md` |
| 散在するパスに効かせたい規約 | `.claude/rules/*.md` に `paths:` 付きで |
| 手順・チェックリスト | スキル（`.claude/skills/`） |
| 絶対にさせない操作 | フック（PreToolUse）。CLAUDE.md は強制力を持たない |

**A の判定は保守的に。** 「モデルが弱かった頃の回避策」と「このリポジトリ固有の本物の制約」は
似て見える。指示文の中に根拠が無ければ A ではなく E とし、確信度「低」を付けて報告する。
**迷ったら残す側に倒す。** 消した規約が原因の事故は、コンテキストが数百トークン重いことより高くつく。

## ワークフロー

1. **対象を洗い出す**（読み取りのみ）

   ```bash
   find . -name 'CLAUDE.md' -o -name 'CLAUDE.local.md' -not -path './.git/*'
   ls .claude/rules/ .claude/skills/ 2>/dev/null
   ```

   併せて、**新しいセッションで `/context` を実行して Memory files に実際に載っている
   ファイルを確認する**。ディスク上にあるのに載っていないファイル（除外設定・起動位置の
   都合で読まれていない）は、棚卸し以前に「効いていない」ので別枠で報告する。
   各ファイルの行数も控える（**1ファイル200行が目安の上限**）

   **auto memory の `MEMORY.md` も対象に含める。** `/memory` で開けるほか、実体は
   `~/.claude/projects/<project>/memory/` にある平文の Markdown。`<project>` は
   **git リポジトリから導出される**ため、同じリポジトリの worktree・サブディレクトリは
   1つの auto memory を共有する。読むのは**内容だけでよい** — 200行 / 25KB の上限と、
   超過時のインデックス書き直しは本体が自分で面倒を見るので、**分量は棚卸しの論点にしない**
   （出典: [Memory](https://code.claude.com/docs/en/memory)）。
   起動時にロードされないトピック別ファイルは、`MEMORY.md` から参照されているものだけ見る

2. **仕分ける** — 対象ファイルが3つ以上あるなら `instruction-auditor` サブエージェントに
   並列で委譲する。依頼文:

   ```
   監査対象: <ファイルパス>
   現在の実行モデル: <モデル名>
   リポジトリの言語・スタック: <一言>
   他の指示ファイル: <一覧>
   出力書式どおり、全項目を A〜E に仕分けて行番号と確信度つきで返してください。
   ```

   1〜2ファイルなら自分で読む。`/doctor` の CLAUDE.md 短縮提案が使えるなら、その結果も
   材料に加える（採否はこのスキルの基準で判断する）

3. **矛盾を突き合わせる**（B の確定）— ファイル横断でしか見つからないので、ここは
   サブエージェントではなく統合側でやる。ルートとサブ、CLAUDE.md と `.claude/rules/` の
   間で同じ話題に別のことを書いていないかを照合する。
   **`MEMORY.md` との照合はここでしかできない。** 本体は「CLAUDE.md に既に書いてあることは
   memory に書かない」建て付けだが、実際には食い違いが入りうるし、`/memory` は閲覧と削除は
   できても指示ファイルとの突き合わせはしない。撤回済みの方針が memory 側にだけ残っている
   ケース（A 分類）は git 差分に出ないので、**この照合を飛ばすと永久に見つからない**

4. **🛑 差分を提示して承認を得る** — 下記の報告テンプレートで提示する。
   **承認前に1ファイルも変更しない。** 削除量が多い場合は、A・B（明確なもの）と
   C・D（判断が要るもの）を分けて提示し、段階的に承認を取る

5. **適用する** — 承認された分だけ編集する。D の移設は「削除」と「移設先への追加」を
   セットで行い、片方だけにならないようにする。
   `MEMORY.md` の項目は `/memory` で開いて該当行を消す（平文の Markdown なので直接編集してもよい）。
   **消した内容を CLAUDE.md へ書き写さない** — 本体は「CLAUDE.md に書いてあることは memory に
   書かない」ので写した分だけ CLAUDE.md が太り、遵守率を下げる側に働く。残す価値があるなら
   E 判定にして memory に置いたままにする

6. **効果を確認する** — 新しいセッションで `/context` を実行し、Memory files と
   コンテキスト使用量が意図どおり減ったことを確認して報告する

7. **次回を予約する** — 実施日と次回の目安（3〜6か月後、または次の大きなモデル更新後）を
   ルート CLAUDE.md のコメント（`<!-- -->` は context に載らない）か issue に残す

## 報告テンプレート

```
## context-audit 結果（対象 N ファイル / 合計 M 行）

### 効いていないファイル（/context に載っていない）
- <パス> — 理由（claudeMdExcludes / 起動位置）

### 削除提案
| ファイル:行 | 分類 | 内容（要約） | 理由 | 確信度 |

### 移設提案
| ファイル:行 | 移設先 | 内容（要約） | 理由 | 確信度 |

### 保持（件数のみ・確信度「低」のものは列挙）

### 見込み
- 行数: 合計 M 行 → M' 行
```

削減率だけを成果として語らない。**何を守り、何を捨てたか**を書く。

## やらないこと

- 承認前の編集（削除は取り返しがつきにくい。git 管理外なら特に）
- 「短くする」ことの自己目的化。E を削って行数を稼がない
- 根拠のない A 判定（旧モデル向けだと断定するには指示文中の根拠が要る）
- 移設先を決めないままの削除（D は必ず行き先とセット）
- **auto memory の内容を CLAUDE.md へ丸ごと書き写すこと**（棚卸しの目的と逆行する）
- auto memory の**分量**を論点にすること（上限と是正は本体が持っている。見るのは内容だけ）
- コード・テストの変更（このスキルは指示ファイルだけを触る）

## 連携

- 足場づくり（階層化・遮断・LSP） → `codebase-onboard`（Step 8 でこのスキルの実施を予約する）
- リポジトリの地図 → `codebase-map`（C 分類で削ったディレクトリ説明の受け皿になる）
- 仕分けの実行役 → `instruction-auditor` サブエージェント
