# codebase-onboard — 大規模リポジトリの足場づくり

あなたは「足場技師」です。**Claude Code の性能は、モデルの強さより「関連する文脈を見つけ
られるか（legibility）」に効きます。** 小規模リポジトリ向けの既定のまま巨大なリポジトリで
使うと、コンテキストが無関係な指示とファイル読み込みで埋まります。

このスキルは、そのリポジトリで**実際に測った数字**をもとに、効く設定だけを順に入れます。
テンプレートを丸ごと配るのではなく、要らない設定は入れないのが仕事です。

出典: [How Claude Code works in large codebases](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)（組織的な展開・所有の型）と
公式ドキュメント [Monorepos and large repos](https://code.claude.com/docs/en/large-codebases)（設定キーの一次情報）。

## 使いどころ／住み分け

- 対象: 既存の大きなリポジトリで「Claude が的外れなファイルを読む」「CLAUDE.md が長すぎる」
  「grep が同名シンボルで数百件ヒットする」「セッション開始時点でコンテキストが重い」とき
- **ルート CLAUDE.md を1枚作りたいだけ** → 本体の `/init`（このスキルも Step 4 でこれを呼ぶ）
- **1つの CLAUDE.md を機械的に短くしたいだけ** → 本体の `/doctor`
- **常時ロードされる指示が古くなっていないかの定期棚卸し** → `context-audit`（このスキルの Step 8 で予約する）
- **リポジトリの地図（目次）が欲しい** → `codebase-map`
- **エージェント連鎖の開発パイプラインを入れたい** → `pipeline-setup`（pipeline プラグイン。
  目的が違うので併用できる。順序はこのスキル → pipeline-setup）

## 全体の流れ

```
Step 0  前提チェック（どこで Claude を起動するかを決める）
Step 1  実測（規模・言語・生成物・既存設定。書き込みはしない）
Step 2  サブツリーの測量（多い場合は subtree-surveyor に並列委譲）
Step 3  🛑 チェックポイント1: 診断結果と導入プランの承認（ここまで1ファイルも書かない）
Step 4  CLAUDE.md の階層化（ルートを削り、サブディレクトリに足す）
Step 5  読ませないものを決める（permissions.deny / claudeMdExcludes）
Step 6  コードインテリジェンス（LSP）プラグイン
Step 7  ディレクトリ別スキル・worktree sparse（該当する場合だけ）
Step 8  🛑 チェックポイント2: 検証・所有者・次回棚卸しの予約
```

進行に合わせてこのチェックリストをコピーして使うこと:

```
codebase-onboard 進行状況:
- [ ] Step 0: 前提チェック
- [ ] Step 1: 実測
- [ ] Step 2: サブツリー測量
- [ ] Step 3: 🛑 診断とプランの承認
- [ ] Step 4: CLAUDE.md 階層化
- [ ] Step 5: 読ませないものの遮断
- [ ] Step 6: LSP プラグイン
- [ ] Step 7: ディレクトリ別スキル・worktree
- [ ] Step 8: 🛑 検証・所有者・棚卸し予約
```

## Step 0: 前提チェック

1. **workbench リポジトリ自身の中で実行していないこと**を確認する。ルートに
   `.claude-plugin/marketplace.json` と `plugins/` があればテンプレート元なので、
   「導入先のリポジトリで実行してください」と案内して停止する
2. git リポジトリかを確認する（`git rev-parse --is-inside-work-tree`）。git 管理外でも
   続行できるが、Step 5 の「`.gitignore` にあるものは追加設定が要らない」判定が効かなくなる
   （その場合は生成物パスをユーザーに確認する）
3. 作業ツリーがクリーンかを確認する（`git status --porcelain`）。未コミットの変更があれば、
   巻き戻せるよう先にコミットすることを勧める（強制はしない）
4. **どこで Claude を起動するかを決める。** これが以降の設定ファイルの置き場所を決めるので、
   最初に確認する:

   | 起動位置 | 起動時に読まれる CLAUDE.md | 設定ファイルの置き場所 | 向くケース |
   |---|---|---|---|
   | リポジトリルート | ルートのみ（サブは読んだときに随時） | ルートの `.claude/settings.json` | 変更が複数パッケージにまたがる |
   | サブディレクトリ | そのディレクトリ＋全祖先 | **そのサブディレクトリの** `.claude/settings.json` | 作業が1パッケージに閉じる |

   `.claude/settings.json` は CLAUDE.md と違い**親から継承されない**。サブディレクトリ起動を
   常用するなら、そのディレクトリの設定ファイルは自己完結させる必要がある。

## Step 1: 実測（書き込みはしない）

推測でプランを作らない。次を実際に測り、数字を控える:

| 項目 | 測り方 | 使いみち |
|---|---|---|
| 追跡ファイル数 | `git ls-files \| wc -l` | 規模の判定 |
| トップレベル項目数 | `ls -1 \| wc -l` | 地図が要るか（数十以上なら `codebase-map` を勧める） |
| 言語構成 | 拡張子別の件数（`git ls-files \| sed 's/.*\.//' \| sort \| uniq -c \| sort -rn \| head`） | Step 6 の LSP 選定 |
| モノレポか | `packages/`・`apps/`・`services/`・ワークスペース定義（`pnpm-workspace.yaml`・`go.work`・`Cargo.toml` の `[workspace]`） | Step 4 の分割単位 |
| 既存の CLAUDE.md | `find . -name 'CLAUDE.md' -not -path './.git/*'` と各ファイルの行数 | Step 4 の起点（200行が目安の上限） |
| 既存の `.claude/` | `settings.json`・`rules/`・`skills/`・`agents/` の有無と中身 | 上書きしないため |
| チェックインされた生成物 | `git ls-files` から `dist/`・`build/`・`*.generated.*`・`vendor/`・`third_party/`・`*_pb2.py`・`*.pb.go` 等を検索 | Step 5 の deny 対象 |
| `.gitignore` の内容 | そのまま読む | **既に無視されているものは deny 不要**（検索は既定で .gitignore を尊重する） |

**測れなかった項目は空欄のまま Step 3 で質問する。それらしい値で埋めない。**

## Step 2: サブツリーの測量

Step 1 でモノレポ／サブシステム分割が見つかった場合、各サブツリーの規約・コマンド・生成物を
調べる。**サブツリーが3つ以上あるときは `subtree-surveyor` サブエージェントに1つずつ並列で
委譲する**（読み取り専用・要約だけを返すため、メインの文脈に大量のファイル読み込みが入らない）。

委譲するときの依頼文:

```
担当サブツリー: <パス>
このサブツリーだけを調べ、出力書式どおりに返してください。担当外は読まないこと。
特に知りたい: ローカル規約の候補・テスト/リント/ビルドのコマンド・チェックインされた生成物のパス。
```

サブツリーが1〜2個、または単一ツリーのリポジトリなら委譲せず自分で読む。

## Step 3: 🛑 チェックポイント1 — 診断とプランの承認

次の形式で提示する:

1. **実測値** — Step 1 の表（数字つき）
2. **サブツリー一覧** — Step 2 の要約（1行要約・コマンド・規約候補）
3. **導入プラン** — Step 4〜7 のうち**このリポジトリで効くものだけ**を、効果の大きい順に。
   入れないと判断した項目は「入れない理由」を1行で添える（例: 「単一言語・単一ツリーのため
   claudeMdExcludes は不要」）
4. **❓ 未確定の質問** — Step 1 で埋まらなかった項目

**STOP. ユーザーの明示的な承認があるまで、1ファイルも作成・変更してはならない。**

## Step 4: CLAUDE.md の階層化

**原則: ルートは「どこでも効くルール」だけに削り、領域固有の規約はその領域のファイルに置く。**

Claude Code はルートと祖先の CLAUDE.md を起動時に読み、サブディレクトリのものは
**そのディレクトリのファイルを読んだときに**追加で読む。つまり階層化すると、いま触っている
領域の規約だけがコンテキストに載る。

1. **ルートが無い場合** — 本体の `/init` で下地を作らせてから、下記の基準で削る
   （このスキルで白紙から書き起こさない。`/init` のほうがコードベース解析に長けている）
2. **ルートがある場合** — 次の基準で仕分け、**削る差分**を提示して承認を得てから適用する:

   | 残す | 移す・消す |
   |---|---|
   | どのパッケージでも効くルール（コミット規約・「生成物は手で編集しない」） | 特定パッケージだけの規約 → そのパッケージの `CLAUDE.md` |
   | 落とし穴・ツール既定と異なる規約・理由 | ディレクトリ一覧・依存パッケージ列挙・アーキ概説 → **消す**（コードから読める） |
   | 全体のビルド/テストコマンド | 手順書・特定作業のときだけ要る知識 → スキルへ |

   仕分けの実務は `context-audit` と同じ基準。ファイル数が多いなら
   `instruction-auditor` サブエージェントに並列で仕分けさせる。
   1ファイルの機械的な短縮だけで済むなら本体の `/doctor` の提案を使う

3. **サブディレクトリの CLAUDE.md を作る** — Step 2 の測量結果から、そのサブツリーでだけ
   通用する規約・`.env` 等の前提・コマンドを書く。**目安は各200行以内**
4. **迷ったら「置き場所」の判断表**:

   | 内容 | 置き場所 |
   |---|---|
   | その領域のファイルを触るとき常に効く規約 | サブディレクトリの `CLAUDE.md` |
   | 散在するパスに同じ規約を効かせたい（例: `**/migrations/**`） | ルートの `.claude/rules/*.md` に `paths:` 付きで |
   | 手順・チェックリスト（毎回は要らない） | スキル（`.claude/skills/`。Step 7） |
   | 「絶対にさせない」 | 指示ではなくフック（PreToolUse）。CLAUDE.md は強制力ではない |

生成したファイルはコミットする（チーム全員に効かせるため）。

## Step 5: 読ませないものを決める

具体的な JSON は [`references/settings-recipes.md`](references/settings-recipes.md) を参照して書く。

1. **`.gitignore` にあるものは何もしない。** 検索は既定で `.gitignore` を尊重するので、
   `node_modules/`・`dist/` が既に無視されているなら設定は不要。ここを二重に書かない
2. **チェックインされた生成物・vendor だけを `permissions.deny` の `Read(...)` で塞ぐ**
   （Step 1 で洗い出したパス）。`.claudeignore` というファイルは現行の Claude Code に無い。
   バージョン管理して共有する方法は `.claude/settings.json` の `permissions.deny` である
3. **他チームのパッケージの CLAUDE.md が混ざるなら `claudeMdExcludes`。** ただしこれは
   静的な除外リストで、日替わりの切り替えには向かない。今日は API、明日は Web という
   使い方なら、除外ではなく**そのパッケージから Claude を起動する**（Step 0 の表）

適用したら、`Read` の deny が効きすぎていないか（本当に読みたいコードまで塞いでいないか）を
1つ確かめる。`Read` の deny は Edit / Write も同じパスで塞ぐ。

## Step 6: コードインテリジェンス（LSP）

grep は同名の関数が数百ある大規模コードベースで誤ヒットを大量に返す。言語サーバーは
シンボルの同一性で絞るため、ファイルを読む前に候補が減る。

言語別のプラグイン名・必要なバイナリ・注意点（クラウドセッションでは起動しないこと等）は
[`references/lsp-plugins.md`](references/lsp-plugins.md) を参照する。

Step 1 の言語構成で**上位を占める言語だけ**入れる。全言語を入れない（メモリを食う）。

## Step 7: ディレクトリ別スキル・worktree（該当する場合だけ）

- **ディレクトリ別スキル** — Step 2 で「手順」として出てきたもの（そのパッケージのテストの
  書き方・移行の手順）は、`<サブツリー>/.claude/skills/<名前>/SKILL.md` に置く。常時ロード
  される CLAUDE.md から、必要なときだけ読まれるスキルへ移すのが目的。
  スキルの書き方は [`docs/skill-authoring.md`](https://github.com/mrkxlia/claude-code-workbench-ja/blob/main/docs/skill-authoring.md) に従う
  （説明文は短く、依頼に出てくる言葉を先頭に置く。多数のスキルがあると説明文は短縮される）
- **`worktree.sparsePaths`** — `--worktree` を日常的に使い、かつリポジトリが巨大な場合だけ。
  チェックアウトするディレクトリを列挙する（`.claude` を必ず含める）。JSON は
  [`references/settings-recipes.md`](references/settings-recipes.md)
- **`permissions.additionalDirectories`** — サブディレクトリ起動で兄弟パッケージも触る場合だけ

該当しないものは入れない。**入れなかった項目は Step 8 で「入れなかった」と明示する。**

## Step 8: 🛑 チェックポイント2 — 検証・所有者・棚卸し

1. **検証**（実際に実行して結果を報告する）:

```
導入検証:
- [ ] 変更した .claude/settings.json が妥当な JSON である（`python3 -m json.tool` 等）
- [ ] 新しいセッションで `/context` を実行し、Memory files に意図したファイルだけが載っている
- [ ] deny で塞いだパスが実際に読めない／読みたいコードは読める
- [ ] LSP を入れた場合、`/plugin` の Errors タブにバイナリ不足のエラーが無い
- [ ] 既存の CLAUDE.md・settings.json を上書きしていない（削除は差分提示と承認を経ている）
```

2. **作成・変更したファイル一覧**（新規／編集／削除の別つき）と、**入れなかった設定とその理由**
3. **所有者を決める。** 設定を誰も持たないと、規約は各自の手元に散り、リポジトリの設定は
   古びる。「このリポジトリの Claude Code 設定（`.claude/`・CLAUDE.md 階層・プラグイン）を
   誰が見るか」を1人決めて、ルート CLAUDE.md か CODEOWNERS に書くことを提案する
   （組織全体の展開まで踏み込む場合の型は本スキル冒頭の出典ブログを参照）
4. **次回の棚卸しを予約する。** モデルが更新されると、旧モデルの弱点を埋めるための指示は
   足かせに変わる。「3〜6か月ごと、および大きなモデル更新の直後に `/context-audit` を回す」
   ことを提案し、合意した時期をルート CLAUDE.md のコメントか issue に残す
5. **STOP. ユーザーがレビューして承認するまで完了扱いにしない。**

## Common Issues

| 症状 | 原因 | 対処 |
|---|---|---|
| `/context` に意図しない CLAUDE.md が載る | ルートから起動していてサブの CLAUDE.md が随時読まれている | 触らないパッケージを `claudeMdExcludes` で除外するか、作業するパッケージから起動する |
| deny を入れたのにファイルが読める | パターンのアンカーがずれている（相対パターンは起動ディレクトリ基準） | サブディレクトリ起動を常用するなら `//` の絶対パスで書く（`references/settings-recipes.md`） |
| LSP プラグインが動かない | 言語サーバーのバイナリが未導入 | `/plugin` の Errors タブを見て、該当バイナリを入れる（`references/lsp-plugins.md`） |
| クラウドセッションで LSP が効かない | 仕様（クラウドではプラグインの言語サーバーを起動しない） | ローカルでのみ有効と割り切る。設定は残してよい |
| CLAUDE.md を削ったら必要な規約まで消えた | 「導出可能」と誤判定した | git で戻す。判定に迷うものは残す側に倒す（`context-audit` の判定基準） |
| サブディレクトリで settings が効かない | `.claude/settings.json` は親から継承されない | そのディレクトリの設定ファイルを自己完結させる（Step 0 の表） |
| 途中で失敗した | 任意のステップでの中断 | **どこまで適用したかを明示して報告する。** 中途半端な状態を「完了」と言わない |

## 足場技師のルール

- 実測していない数字でプランを作らない。測れなかった項目は質問する
- **効かない設定は入れない。** 単一言語・単一ツリーのリポジトリに monorepo 向けの設定を配らない
- 既存の CLAUDE.md・`.claude/settings.json` を上書きしない。削る場合は差分を見せて承認を得る
- チェックポイント1の承認前に1ファイルも書かない。チェックポイント2の承認前に完了と言わない
- 入れなかった設定も報告する（何を検討して見送ったかが、次の棚卸しの入力になる）

## 連携

- 地図（目次）が要るほどトップレベルが多い → `codebase-map`
- 導入後の定期棚卸し → `context-audit`
- エージェント連鎖の開発パイプライン → `pipeline-setup`（pipeline プラグイン）
