# feedback-rule — 指摘をルールにする

「同じ指摘を二度させない」ための唯一の入り口です。**口頭の指摘をファイルにする**ことで、
Claude に読ませるだけでなく、フックが機械的に評価できるようになります。

**先に読むもの**: frontmatter の完全仕様は
[`references/rule-format.md`](references/rule-format.md)。

## 大原則

1. **count は人間の指摘回数であって、違反回数ではない。** フックが検知した違反は
   `.violations.jsonl` に記録されるだけで、count は自動で上がりません。
   count を上げてよいのは「人間が同じ指摘をもう一度した」ときだけです。
2. **1指摘 = 1ファイル。** 既存ルールに継ぎ足すのではなく、話題（topic）ごとに分けます。
   関連するルールは本文で `[[別のルール名]]` のように相互リンクします。
3. **いきなり禁止にしない。** 1〜2回目は warn（記録するが縛らない）、3回目で確定ルール、
   5回目で deny。誤検知で作業不能になるほうが、検知漏れより害が大きい。

## 手順

### Step 1 — 既存ルールを探す

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/hooks/feedback_rules.py" doctor
```

置き場所は `~/.claude/feedback/`（個人）と `.claude/feedback/`（プロジェクト）の2つ。
**同じ話題のルールが既にあれば、新規作成ではなく count の引き上げ**です。
判断がつかないときは、既存ルールの description をユーザーに見せて確認します。

### Step 2 — 既存ルールがある場合（更新）

1. `count` を **+1** する。
2. 本文の **言い訳** の節を更新する（後述）。今回どんな理屈で破ろうとしたのかを書き足す。
3. count が 3 または 5 をまたいだら、severity が変わることをユーザーに伝える
   （3 で ask / block、5 で deny）。
4. `enforce` がまだ無いなら、この機会に書けないか検討する（Step 4）。

### Step 3 — 新規ルールを作る

`~/.claude/feedback/[topic].md` を作る。topic は小文字スネークケースの短い名前
（`tdd`・`dont_run_tests_manually`・`pin_action_sha` など）。

```markdown
---
name: topic名
description: 一行で「何をすべきか」（フックの警告文と注入文に使われる）
type: feedback
count: 1
enforce: []
---

本文（Claude が読む説明）

**Why:** なぜ指摘されたのか。ユーザーの意図・背景。

**How to apply:** いつ・どこで適用するのか。境界条件。

**言い訳:** このルールを破りたくなるときに先に立つ理屈と、それが通らない理由。
```

**言い訳の節は必ず書く。** ルールを破りたくなる場面では、たいてい「今回は特別だから」と
いう理屈が先に立ちます。その理屈をあらかじめ潰した文章が同じファイルにあると、逃げ道が
塞がれます。ユーザーの指摘の中に「〜だからやった」という弁明があれば、それをそのまま書きます。

### Step 4 — 機械的に検知できる形に翻訳する（enforce）

**ここがこのスキルの本体です。** 「お願い」を「条件式」に落とせるかを検討します。

| 指摘の型 | event | 書き方 |
|---|---|---|
| このコマンドを実行しないでほしい | `pre_bash` | `when:` に正規表現。例外は `unless:` |
| このファイルを書く前に別のファイルが要る | `pre_edit` | `path:` glob ＋ `absent_sibling: '{stem}_test.go'` |
| この内容を書かないでほしい | `pre_edit` | `path:` glob ＋ `when:`（書き込む内容への正規表現） |
| 終わる前にこの検査を通してほしい | `stop_check` | `changed:` glob ＋ `check:`（`$FILE` を使うシェル）または `when:` |

翻訳できたら `doctor` で正規表現と glob の妥当性を確認します。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/hooks/feedback_rules.py" doctor
```

**翻訳できない指摘もあります。** たとえば「実装を先に書いてから呼び出し元を書く」のような
*順序* のルールは、ファイル単体を見ても違反判定ができません。その場合は `enforce: []` のまま
にします。count が 3 以上になれば毎ターン文脈に注入されるので、無意味ではありません。
無理に正規表現をひねり出して誤検知を作るより、注入だけに留めるほうが良い判断です。

### Step 5 — 未確定候補の処理

フックはユーザーの訂正らしき発言を `.candidates.jsonl` に自動で溜めています
（「前も言った」「そうじゃない」「〜しないで」等を検出）。ユーザーが「溜まっている指摘を
ルールにして」と言ったときは、未確定のものを一覧で見せ、**1件ずつ昇格するか破棄するかを
確認**します。勝手にまとめてルール化しない（誤検出が混ざっているため）。

処理した候補は、その行の `"promoted"` を `true` に書き換えます（行の削除でも可）。

### Step 6 — 報告する

- どのファイルを作った・更新したか（パス）
- count が何になったか、その結果 severity がどう変わったか
- enforce を書けたか、書けなかったならなぜか
- 3 をまたいだ場合は「次のターンから毎回文脈に注入される」ことを伝える

## 誤検知が出たときの逃がし方（優先順）

1. `unless:` に例外パターンを足す（最も安全。ルールの意図は保たれる）
2. `severity:` を明示して count による自動昇格を止める（例: count 6 でも `warn` に固定）
3. `enabled: false` にする（緊急停止。理由を本文に書き残す）
4. `expires: YYYY-MM-DD` を入れる（期間限定のルールだったと分かった場合）

**ルールファイルを削除するのは最後の手段**です。削除すると「なぜこのルールがあったのか」の
記録も消えます。無効化して理由を書き残すほうが、同じ議論を繰り返さずに済みます。
